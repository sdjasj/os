# 逐讲详解写作与验收规范

本目录把课程 30 份讲义逐讲扩写。每一章必须以对应的 `sources/notes/lectNN.md` 为事实和结构主线，不能只根据课程标题写一篇泛化的 OS 文章。

## 每讲必须包含

1. **本讲定位**：上一讲留下了什么问题，本讲解决什么，下一讲从哪里接续。
2. **学习目标与问题地图**：读者学完后能解释、观察或实现什么。
3. **按原讲义顺序的完整讲解**：覆盖所有非重复的一级幻灯片标题、课堂案例、历史线索、API 和 Takeaways。重复的 `(cont'd)` 可以合并，但内容不能漏。
4. **机制推导**：说明“为什么需要它、最小模型是什么、真实系统怎样扩展、代价和边界在哪里”。
5. **生动代码/命令实验**：每讲至少两个可操作观察点；代码需解释预期输出、系统调用或状态变化，不能只贴代码。
6. **概念辨析和常见误区**：尤其区分语言语义、libc、系统调用、内核实现和硬件行为。
7. **小结、思考题与下一讲衔接**。
8. **PPT 内容覆盖表**：章末列出原讲义主要标题及其在本章对应的小节，便于机械审计。

## 详细程度

- 目标是让没有听课堂口述的读者也能顺着推导学会，而不是把 bullet point 改写成完整句子。
- 每讲通常需要约 700–1200 行 Markdown 才能把 PPT 的论证、机制和实验讲透；内容密集的讲次可以超过千行。行数不是凑字数指标，验收仍以覆盖度、推导质量和可操作性为准。
- 课堂图片不必逐像素描述，但图片承担的论证、历史案例或反直觉结论必须讲清。
- 课程中的交互 Demo 要解释它想观察什么、怎样自行复现实验、结果如何解读。
- Hacking Day 和课程总结也要完整讲解其方法论与课程关联，不能以“非 OS 核心”略过。
- 允许查阅外部资料补足背景与真实系统细节，优先使用标准、官方文档、项目源码和论文，并给出可核查链接；必须明确区分 PPT 主线与扩展阅读，不能让外部材料喧宾夺主。

## 代码规范

- 默认 Linux/POSIX；注明依赖和可能需要的权限。
- C 代码必须检查关键系统调用返回值；故意错误的代码要明确标注“反例”及其错误性质。
- 不提供 MiniLab 的直接答案；可以给独立的最小示例和调试方法。
- 优先复用 `examples/` 中已有完整示例，并给出相对链接。

## 串联原则

课程主线是：

```text
程序/硬件状态机
  → 进程与地址空间虚拟化
  → 操作系统对象、libc、链接加载与应用生态
  → 共享内存并发、同步、并行与异步
  → 设备、存储、文件系统和数据库
  → 安全、虚拟机、容器与完整系统观
```

每一讲都应明确自己在这条链上的位置，并使用前面已经建立的术语，避免 30 篇互不相关的百科文章。
