# 第 1 讲：操作系统概述——在硬件、程序与抽象之间建立坐标系

> 对应原始讲义：[sources/notes/lect01.md](../../sources/notes/lect01.md)  
> 后一讲：[应用视角的操作系统](02-application-view.md)  
> 本讲关键词：状态机、抽象、硬件—软件共演化、资源虚拟化、UNIX 哲学、Content as Code、AI Agent

## 本讲定位

这是整门课的“地图课”。

它不急着让你背 `fork`、`mmap` 或 `open` 的参数，也暂时不深入某个内核子系统；它先回答三个更根本的问题：为什么 AI 时代还要学操作系统，课程所说的“操作系统”到底处在什么位置，以及我们将用什么方法把它学明白。

作为第 1 讲，它没有需要承接的上一讲，但它要建立后续 29 讲共同使用的语言：

```text
硬件：由时钟或事件推动的数字状态机
  ↑
操作系统：管理并抽象单机硬件，支撑应用生态
  ↓
软件：有顺序、有状态、有副作用的程序
```

这三者不是各自独立的百科词条。

硬件能力变化会让新的操作系统机制成为可能，应用需求又会逼迫操作系统提供新的对象与 API；操作系统恰好位于二者之间，因此理解它的最好方式之一，就是沿着硬件、软件与 OS 的历史共同演化一路追问“当时究竟遇到了什么困难”。

第 2 讲将把这张地图收紧到一个精确问题：**操作系统上运行的程序到底是什么**。届时会从 C 程序的解释执行、函数调用、编译器和最小系统调用程序出发，把本讲的“Everything is a state machine”变成可逐步执行的严格模型。

## 学习目标与问题地图

学完本讲，你应该能够：

1. 说明课程的目标、考核方式、学习边界与 AIGC Policy，而不是把这门课误解为“背内核数据结构”。
2. 解释 AI 为什么削弱了“手写普通代码”的稀缺性，却放大了抽象设计、系统边界与验证能力的重要性。
3. 分别用状态机描述数字电路、处理器和有副作用的程序，并指出数学函数与 C/C++ 函数的差异。
4. 从应用视角给出一个够用的操作系统定义，同时理解为什么这里不追求一句无懈可击的定义。
5. 沿 1940s、1950s—1960s、1960s—1970s、1970s+ 四个阶段，解释操作系统如何从“不存在”演化为资源虚拟化与应用生态的基座。
6. 说明批处理、分时、文件、任务、进程、信号、管道、socket 和 procfs 不是凭空出现的名词，而是特定矛盾沉淀成的抽象。
7. 用可重复实验观察状态迁移、程序副作用、文本管道和系统调用边界。
8. 建立一套 AI 时代的 OS 学习循环：提出模型、做最小实验、收集证据、修正模型。

可以先把全讲压缩成四个连续问题：

```text
Why：AI 都会写代码了，为什么还学 CS/OS？
  ↓
What：程序、硬件与 OS 各是什么，它们怎样咬合？
  ↓
History：今天的抽象为什么长成现在这样？
  ↓
How：怎样借助 AI 和实验真正获得系统能力？
```

## 1. 个人简介：为什么这门课从“程序”一侧看 OS

原讲义先介绍教师的学术与教学背景：教授操作系统、研究程序语言（PL），同时以软件工程视角思考系统，也保留算法与理论训练的传统。

这段信息和课程内容有关，因为它解释了本课的观察角度。

传统 OS 课程常从内核内部开始：进程控制块有哪些字段、调度器有几条队列、页表如何遍历。那些知识当然有价值，但这门课把主要视角放在**程序和抽象边界**上：

- 应用程序怎样表达“创建另一个程序”“连接两个工具”“保存数据”“访问设备”？
- 一个 API 为什么被设计成这样，它允许哪些组合，又故意禁止什么？
- 一组简单而稳定的对象，怎样支撑浏览器、编译器、IDE、游戏、数据库与 Agent？
- 当我们只看到调用接口时，如何用实验推断接口背后的系统行为？

课程主线按 3 学分建设，并明确削减了传统的内核实现内容。

这里的“砍掉内核内容”不等于“忽略底层”。更准确地说，它是在做观察层级的选择：本课先把应用可见的契约、历史动机和设计理念讲清楚；当接口行为需要硬件机制解释时，再引入足够的状态机、异常、中断、MMU 和设备知识。

这一选择也呼应教师参与培养方案建设的背景：课时有限时，必须优先保留能迁移到不同系统、不同实现和不同时代的思维框架。

## 2. 课程简介：这门课希望你最终获得什么

### 2.1 课程目标不是“知道 OS 名词”，而是知道它带来了什么

讲义把核心目标概括为：真正理解“操作系统给我们带来了什么”。

这句话可以拆成三个层次：

1. **能力层**：程序原本做不到或很难安全做到的事，经由 OS 对象和 API 变得可表达。
2. **设计层**：复杂的硬件细节被压到抽象层之下，应用可以围绕较稳定的接口演化。
3. **生态层**：接口不仅服务一个程序，还允许不同程序相互组合，从而形成远大于单个工具的应用生态。

因此每节课都会尽量带着“实现一点什么”的目标。

实现并非为了堆代码量，而是因为一个抽象只有在你尝试调用、组合、破坏和调试它时，边界才会显现。例如，读过“管道连接两个进程”还不算理解；真正建立模型需要你观察文件描述符如何重定向、哪一端未关闭会导致谁等不到 EOF、错误又从哪里返回。

课程还会不断增加 UNIX Philosophy 的“含金量”。第 1 讲先给出三条直觉：

- Make each program do one thing well：让每个程序把一件事做好。
- Expect the output of every program to become the input to another：默认输出可能成为别人的输入。
- Use text interface：优先使用可观察、可记录、可组合的文本接口。

后续学习 Shell、文件描述符、管道、libc、进程和设备时，我们会反复看到这三条并非口号，而是由 OS 对象支撑的工程结构。

## 3. AC 05 年：AI 时代改变了什么

“AC”是 Anno ChatGPT，即以 ChatGPT 出现为纪元；AC 05 年对应讲义所处的 2026 年语境。

### 3.1 模型能力、速度与上下文都在跨越阈值

讲义列出的三个变化是：

- 更强的指令遵循与幻觉抑制，模型在 IMO、IOI、ICPC 等复杂任务上展示出很强能力。
- Agent 从“勉强能用”走向“非常能用”。
- Context 从 128K 扩展到 1M 量级。

推理速度同样重要。讲义以 LLaMA3 8B 达到约 15,000 token/s 的演示为例，要求读者思考速度阈值意味着什么。

答案不只是“聊天更快”：

- 延迟足够低时，模型可以进入编辑—运行—观察的实时闭环。
- 上下文足够大时，Agent 可以同时看到项目结构、日志、规范和历史修改。
- 采样足够便宜时，可以搜索多个候选方案、交叉检查或做 beam search。
- 接口足够自然时，模型可以成为脑机接口、交互 UI 或工具编排器的一部分。

Claude Code 与 Clawdbot 被列为现象级应用。它们共同说明：LLM 一旦能读取项目、运行命令、调用服务并修改文件，就不再只是一个聊天框，而成为了 OS 资源的**新型用户**。

### 3.2 模型很强，不等于系统问题消失

模型输出仍要落到现实约束上：

```text
模型意图
  → 工具调用
  → 进程、文件、网络、窗口、设备
  → OS 的权限、隔离、调度与持久化
  → 物理世界中的 CPU、GPU、磁盘和网络
```

如果没有 OS，Agent 既没有可控的“手和脚”，也没有安全边界。

能生成一条 `rm` 命令不等于它有权删除文件；能写并发程序不等于程序没有数据竞争；能启动很多任务不等于 CPU/GPU 被高效利用。系统抽象负责把能力变成**安全、可靠、高效、有保障**的服务。

## 4. 从算法时代到 AI 时代：问题形态发生变化

### 4.1 算法时代：先把现实变成 well-formed 问题

传统计算机擅长 mathematically well-formed 的问题：

- 数据持久化要求定义记录、查询和一致性。
- 约束求解要求列出变量、取值域和约束。
- 优化要求给出目标函数。
- 加密要求明确威胁模型、密钥和算法。

软件工程师的重要工作，是把现实世界中模糊的需求建模成这些可计算对象，再通过 App、GUI 或 API 交给用户。

讲义用一句很有解释力的话概括：**软件是物理世界过程在信息世界中的投影。**

一个外卖应用不是“现实中的餐馆”，它是商家、菜单、库存、订单、骑手位置和支付过程的数据模型；模型遗漏或错误，软件行为就会偏离现实。

### 4.2 AI 时代：ill-formed 问题也能成为输入

自然语言需求通常不完备、含歧义，属于 mathematically ill-formed 问题。

LLM 可以先从模糊描述中提取较明确的子问题，再调用搜索、编译器、数据库、求解器或脚本处理 well-formed 的部分；它还能动态生成文本、声音、图像和界面。

但“能处理模糊输入”没有取消抽象，反而引入了更多抽象边界：

- 如何把自然语言意图转成有类型、有权限的工具调用？
- 如何隔离不可信生成代码？
- 如何记录 Agent 做过的每一步，使结果可审计？
- 如何在失败后恢复，而不是留下半写入文件或悬挂进程？
- 如何让多个 Agent 共享资源而不互相破坏？

这些依旧是系统问题。

## 5. 学 CS 还有意义吗：抽象为何仍不可替代

“软件已死，氛围当立”是讲义用来制造冲击的说法：顶级模型正在降低普通代码劳动的稀缺性，甚至许多研究型任务也开始自动化。

真正的转折词是“但是”：**复杂系统的实现仍然需要抽象。**

### 5.1 抽象是在隔离复杂性，不是在隐藏真相

抽象把一个复杂系统划成边界明确的部分：

- 调用者只依赖接口承诺，不依赖每个实现细节。
- 实现者可以在不破坏承诺的情况下优化内部。
- 故障被限制在较小范围，便于测试和替换。
- 团队和 Agent 可以围绕接口并行工作。

以文件为例，应用看到的是名字、字节序列和读写操作；它无须每次关心磁盘磁头、闪存擦除块、缓存一致性或网络副本。OS 与存储栈没有让这些物理事实消失，而是把它们封装在有代价、有边界的契约后面。

### 5.2 Claude Code、Skills 与 OS 的关系

讲义把 Claude Code 看作 CLI 的“用户”，把 Skills 看作编程语言里的抽象与复用机制。

这个类比很准确：

- CLI 把 OS 对象组织成可组合命令。
- Skill 把多步工作流封装成可复用能力。
- 权限系统决定工具能访问哪些资源。
- 进程与虚拟环境隔离不同任务。
- 日志、退出码和文件 diff 提供可观察性。

因此 AI 并没有绕过操作系统；AI 是在继承几十年系统抽象后，才获得显示界面、网络通信、虚拟环境和算力调度能力。

## 6. 舞台已经搭好：把 OS 当作“最后一门编程课”

原讲义称《操作系统》是“最后一门编程课”，意思不是学完以后不再写程序，而是此前分散的知识将在这里汇合：

- 程序设计告诉你怎样表达计算。
- 数据结构与算法告诉你怎样组织并高效求解。
- 数字电路告诉你机器状态怎样更新。
- 计算机系统基础告诉你高级语言怎样成为指令和二进制。
- 操作系统则追问：程序怎样获得资源、与外界交互、彼此协作并受到隔离。

讲义列出一组“为什么”：

- 为什么程序能创建窗口？
- 为什么 `Ctrl-C` 有时不能退出程序？
- Code Agent 里面是什么？
- 怎样把服务器 CPU 和 GPU 都用满？

这些问题表面不同，背后都涉及 OS 提供的对象、事件与策略。

例如 `Ctrl-C` 并不是键盘给进程发送一个“强制退出”硬件信号。终端驱动通常把控制字符解释为信号，再由内核把信号送到前台进程组；进程可以捕获或忽略某些信号，也可能正处在特殊状态。这一条问题就会串起终端、进程组、信号、系统调用与调度。

浏览器、编译器、IDE、游戏、外挂、杀毒软件和病毒都运行在同一套系统接口之上。理解接口后，你不仅更会“使用软件”，还开始具备拆解和实现这些软件的能力。

讲义改写了那句著名的话：“Code is cheap, show me the talk。”代码越来越便宜，但你首先要能**掌控代码**：知道它能访问什么、为什么这样运行、失败后留下什么，以及怎样用证据确认它做对了。

## 7. 操作系统：定义，以及为什么不迷信定义

### 7.1 OSTEP 的工作定义

讲义引用 OSTEP 的定义：操作系统是一组让程序更容易运行的软件；它让多个程序看起来可以同时运行，让程序共享内存、与设备交互，并完成其他相关工作。

这个定义抓住了几个核心动作：

- **运行**程序；
- **复用**处理器等资源；
- **共享**数据与内存；
- **访问**设备；
- 把困难机制包装成更易用的服务。

但它也留下疑问：“programs”似乎包揽了一切——窗口管理器 Sway、终端、浏览器、虚拟机、Claude Code 都是程序；“共享内存”“与设备交互”又只是大量系统能力中的几个例子。

### 7.2 本课采用的够用定义

与其争论边界，不如先使用一个可工作的定义：

> 狭义操作系统是硬件与软件之间的中间层；它抽象和管理一台单机（含多个处理器）的资源，为应用程序生态提供稳定运行基础。

站在应用一侧，可以先记住三项职责：

1. **抽象**：把物理资源变成进程、地址空间、文件、socket、窗口或设备对象。
2. **复用**：让多个程序在时间上共享 CPU，在空间上共享内存和存储。
3. **隔离与保护**：限制一个程序能破坏的状态，并仲裁权限。

```text
应用生态       Shell / 浏览器 / 数据库 / 编译器 / Agent
                         │ API / 系统调用
操作系统       进程 / 地址空间 / 文件 / socket / 设备
                         │ 指令 / MMU / 中断 / I/O
硬件                CPU / 内存 / 磁盘 / 网卡 / GPU
```

### 7.3 为什么“不需要精准定义”

内核、驱动、libc、Shell、桌面、系统服务和虚拟机监控器的边界，在不同系统中并不完全相同。

如果一开始就执着于“某段代码究竟算不算 OS”，容易失去真正的问题：它为程序提供了什么抽象，管理了什么资源，处在哪个信任边界，又承担什么失败责任。

所以讲义说“操作系统是来帮我们的，不是来折磨我们的”。定义是导航工具，不是考试陷阱。

更广义的 Systems 思想还能推广：分布式系统抽象多台计算机，存储系统抽象各种持久化设备。尺度变了，但抽象、复用、隔离和故障处理仍是共同主题。

## 8. 复习硬件：数字电路是一台离散状态机

### 8.1 从极简公理系统到复杂计算机

《数字逻辑电路》给出一组很少的基本元素：导线、时钟、逻辑门和触发器/寄存器。

组合逻辑计算“当前输入对应什么输出”，寄存器保存跨周期状态；时钟沿到来时，下一状态被锁存。

可以写成：

\[
S_{t+1}=F(S_t, I_t),\qquad O_t=G(S_t,I_t)
\]

其中 `S` 是寄存器状态，`I` 是输入，`O` 是输出，`F/G` 由逻辑门网络实现。

七段数码管图在讲义中承担的论证是：即使“画出一个数字”也可以还原为若干布尔信号；足够多的简单门和寄存器，可以支撑非常复杂的数字系统。

CPU 并不神秘。它只是一个规模更大的状态机：寄存器和内存保存状态，取指—译码—执行逻辑计算下一状态。

### 8.2 数字电路模拟器：代码也能模拟硬件

课程 Logisim demo 用一小段程序模拟电路执行，其基本思路也对应 nvboard：

```text
读取当前寄存器值和输入
  → 计算组合逻辑
  → 在时钟边沿更新寄存器
  → 输出 A=0; B=1; ... 这样的状态
```

关键不在于画面有多逼真，而在于**模型可执行**。

只要状态集合和迁移函数写得足够准确，宿主机上的 C 程序就能模拟另一套电路；性能可能不同，但每一步的语义相同。

### 8.3 ASCII Art：文本也可以是界面协议

早期打字机和计算机缺乏图形显示能力，人们用字母、数字和符号拼出图像；ASCII Art 后来在 BBS、论坛签名、纯文本游戏中繁荣，如今仍用于终端界面、代码彩蛋、独立游戏和网络文化。

它出现在这里不是单纯的怀旧。

Logisim demo 将“计算状态”和“画出状态”拆为两个程序：前者输出文本，后者解析文本并显示数码管。只要文本协议稳定，后端可换成 TUI、WebUI、日志分析器甚至测试脚本。

这正是 UNIX 组合思想的雏形：一个程序不必包办计算、显示、记录和分析。

### 8.4 RISC-V 处理器模拟器：同一思想可以运行完整软件栈

讲义展示的 `mini-rv32ima` 是用 C 编写的 single-header RISC-V32IMA 系统模拟器。

它维护类似这样的机器状态：

```c
struct CPUState {
    uint32_t regs[32];
    uint32_t pc;
    uint8_t *memory;
};
```

模拟器循环读取 `pc` 指向的指令，译码并修改寄存器、内存与下一条 `pc`。

有了 M-Mode 等必要机器级能力，它甚至可以运行没有 MMU 的 Linux。这里最重要的结论是：

> 复杂软件并没有逃离状态机。只要底层状态迁移被正确模拟，任意复杂程序仍然是一连串机械步骤。

这为后续课程提供了一条统一链路：C 程序可以被解释；编译后的指令可以由处理器执行；处理器可以由另一个程序模拟；内核也只是其中一段在特权状态运行的程序。

### 9.1 一份代码同时生成课堂内容

## 10. 会编程，你就拥有全世界：第一个 UNIX 彩蛋

Logisim 是本课第一个“彩蛋”，因为它同时证明两件事：

1. 程序可以模拟任意定义清楚的数字系统，包括计算机系统。
2. 计算与显示可以通过文本接口组合，体现 UNIX Philosophy。

命令行位于自然语言和编程语言之间：

- 它比自然语言精确，参数、重定向和退出码可重复。
- 它比完整编程语言轻量，几条命令即可组成工作流。
- 它的输入输出通常可记录，既适合人阅读，也适合另一个程序解析。

这正是大语言模型和 Agent 擅长使用 CLI 的原因：模型可以生成近似自然语言的命令，同时从结构化输出、文件 diff 和退出码得到反馈。

### 实验一：把状态机 trace 当作另一程序的输入

配套代码 [`examples/state_machine.c`](../../examples/state_machine.c) 定义了两个任务，每个任务都有 `pc`、累加器 `acc` 和完成标志；调度循环每次只让一个任务执行一步。

在仓库根目录运行：

```bash
make -C examples state_machine
./examples/state_machine | tee /tmp/os-state.trace
awk '/run=A/{print}' /tmp/os-state.trace
```

前几行应类似：

```text
tick=0 run=A before(pc=0, acc=0) -> after(pc=1, acc=1)
tick=1 run=B before(pc=0, acc=0) -> after(pc=1, acc=1)
tick=2 run=A before(pc=1, acc=1) -> after(pc=2, acc=2)
```

请逐项解释：

- `pc` 标识下一步要执行哪条规则。
- `acc` 是任务的数据状态。
- 调度器交替选择 A、B，两个任务各自的状态不会混在一起。
- `tee` 一边把文本交给终端，一边保存 trace。
- `awk` 不懂 `Task` 结构体，却能消费稳定的文本输出并筛出 A 的轨迹。

真实 OS 的上下文远比这里多，可能包括通用寄存器、栈指针、程序计数器、向量寄存器、页表关联和调度状态；但“保存状态—选择对象—恢复状态—继续迁移”的最小模型已经出现了。

你还可以把 `tick % task_count` 改为每个任务连续运行两步，预测并验证：中间 trace 的交错顺序会改变，但由于两个任务没有共享可变状态，最终 `acc` 都仍是 5。

## 11. 复习软件：程序同样是一台状态机

### 11.1 从高级语言到机器执行

《计算机系统基础》建立过这条链：

```text
高级语言代码 → 指令序列 → 二进制文件 → 处理器执行
```

如果每条指令都把机器状态 `S` 变成下一状态 `S'`，程序执行就是：

\[
S_0\rightarrow S_1\rightarrow S_2\rightarrow\cdots
\]

顺序程序的状态可粗略写成 `(PC, Registers, Memory, I/O)`，但这只是硬件视角的近似。

从语言语义看，函数调用栈、对象生命周期、未定义行为和外部 API 也是模型的一部分；第 2 讲会把它精化为栈帧序列、全局状态与待执行语句。

### 11.2 汉诺塔：C 函数不是数学函数

Fibonacci 的数学定义关注返回值。在没有可观察副作用时，先求 `f(n-1)` 还是先求 `f(n-2)`，通常不改变最终加法结果。

汉诺塔程序却通过 `printf` 输出移动步骤；输出流属于全局可观察状态。改变两次递归调用的先后，移动序列就变了，甚至不再是合法解。

这揭示了三层差异：

- **数学函数**：相同输入映射到相同输出，求值顺序通常不属于结果。
- **C/C++ 函数**：可能修改内存、文件、终端或设备，调用顺序可被观察。
- **外部 API 调用**：把程序内部计算投射到 OS 管理的外界，是编译器必须保留的可观察行为。

尤其不要误以为 `return f(n - 1) + f(n - 2);` 在 C 中承诺左边先调用。该表达式的两个操作数求值顺序并不由语言保证；现代编译器在许多场景下可能呈现自然顺序，但“我这次看到如此”不是语言契约。

### 实验二：亲眼看见副作用为何让顺序变得重要

下面用 Python 把递归结构缩到最小。两种函数都能递归，但只有第一种输出合法汉诺塔步骤：

```bash
python3 - <<'PY'
def hanoi(n, src, dst, spare):
    if n == 0:
        return
    hanoi(n - 1, src, spare, dst)
    print(f"move {src} -> {dst}")
    hanoi(n - 1, spare, dst, src)

def reordered(n, src, dst, spare):
    if n == 0:
        return
    # 故意调换两个递归阶段；print 的副作用让结果不能等价交换。
    reordered(n - 1, spare, dst, src)
    print(f"move {src} -> {dst}")
    reordered(n - 1, src, spare, dst)

print("normal:")
hanoi(2, "A", "C", "B")
print("reordered:")
reordered(2, "A", "C", "B")
PY
```

正常版本应输出：

```text
move A -> B
move A -> C
move B -> C
```

第二组输出的顺序不同。不要只看“都打印了三行”；拿纸画出 A、B、C 三根柱子的状态，就会发现重排版第一步可能试图移动一块根本不在相应柱子上的盘。

实验说明：程序的“结果”不仅是返回值，还包括每一步对外界造成的可观察变化。

这也为编译器优化划出边界：内部、不可观察的计算可以被重排或删除；`write`、文件修改和设备交互等外部行为必须满足语言与 API 所规定的等价性。

## 12. 到底什么是操作系统：夹在两种状态机之间

现在可以更准确地理解“硬件和软件的中间层”：

- 下方硬件按指令、中断和设备事件迁移状态。
- 上方程序按语言语义执行计算，并通过 API 请求外部效果。
- OS 接收请求、检查权限、选择资源、配置硬件，再把结果投射回程序状态。

例如应用调用“读文件”时，真实路径可能涉及 libc 包装、系统调用、文件对象、页缓存、文件系统、块设备驱动、中断和 DMA。

应用不必每次控制这一整条链；操作系统提供 `read` 一类接口。但抽象不是魔法：短读、权限错误、设备故障、缓存和并发仍会通过返回值、时序与持久化语义显露出来。

因此本课理解 OS 的方法是：

1. 找到相对简单、可严格描述的硬件。
2. 找到真实、可执行并依赖 OS 的程序。
3. 观察程序与 OS 的 API 边界。
4. 在需要时下钻到硬件机制，解释接口为什么可能成立。

接下来的历史部分会说明这层软件不是一次设计完成的，而是被成本、速度差、用户数量和应用需求逐步“挤”出来的。

## 13. 1940s：当“把程序跑起来”已经足够困难

### 13.1 ENIAC：图灵机的数字电路实现尝试

ENIAC 于 1946 年 2 月 14 日公开，代表电子计算新时代的诞生。

它遵循数字状态机思想，也有类似程序计数进度的概念，但“下一步做什么”很大程度由物理线路 hard-wire；重编程需要重新接线。

与现代存储程序计算机相比，关键差异是：

- 今天，指令也作为数据存放在存储器中，改变程序主要是改变内存里的比特。
- ENIAC 早期编程把控制关系编码在插线和开关上，改变程序就要改变物理连接。

不过二者仍共享状态机本质：一个周期中，电路根据当前状态和输入计算并更新寄存器状态。

### 13.2 1940s 的计算机硬件

当时典型实现包括：

- 逻辑门由真空电子管构成。
- 存储器可能采用水银延迟线。
- 输入输出依赖打孔纸带和指示灯。

逻辑门—存储—I/O 的基本格局已经形成，但每一部分都昂贵、低容量且不可靠。

水银延迟线尤其能提醒我们，“内存”从来不是天然的平坦数组；它只是后来被硬件和软件抽象成可按地址访问的存储。

### 13.3 1940s 的计算机软件

早期软件主要用于打印平方数、素数表和计算弹道等数值任务。

今天程序设计教材里的经典循环题，很多来自那个阶段的实际需求；如果脱离历史，只剩“为了练循环而打印表”，学生自然会怀疑意义。

“bug”在当时甚至可以是一只真正卡在机器里的虫子。这个案例所承载的不是词源趣闻，而是一个系统事实：软硬件边界尚未被充分隔离时，程序错误、电路故障和物理环境可能表现为相似的错误结果，调试必须跨越整个机器。

### 13.4 1940s 的操作系统：没有操作系统

当时甚至没有成熟编程语言；人们画流程图、写机器代码、打孔和接线。

程序直接使用指令控制硬件，因此不需要额外的软件“管理程序”。当一台机器一次只服务一个被人工装入的任务时，进程隔离、文件权限和自动调度都还不是首要矛盾。

这不是说 OS 在逻辑上无用，而是它的成本暂时高于收益：

```text
机器极少 + 程序极少 + 人工全程操作
  → 没有足够多的共享和自动化需求
  → OS 尚未成为必要层
```

讲义把这个阶段类比为今天 Agents、MCP、Skills 的早期：当生态刚出现时，人们先让工具“能工作”；随着用户、工具和组合增多，权限、调度、复用和标准接口才逐渐成为不可回避的基础设施。

## 14. 1950s—1960s：昂贵算力、慢速 I/O 与批处理/分时

### 14.1 计算机硬件：部件变强，速度鸿沟出现

晶体管逐步取代真空管，磁芯内存提供更可靠的随机访问存储，I/O 设备日益丰富。

但 I/O 速度远低于处理器：CPU 如果一直等待纸带、卡片或打印机，会浪费昂贵算力。

中断机制在 1953 年出现，使设备完成工作时可以主动通知 CPU，而不是让 CPU 永远轮询等待。

最小因果链是：

```text
CPU 变快、I/O 相对更慢
  → 同步等待浪费大量处理器时间
  → 让设备并行工作，完成时产生中断
  → 管理“谁在等什么”成为系统软件职责
```

中断不仅是一项硬件功能，也为后来的调度和多任务提供了事件入口。

### 14.2 计算机软件：高级语言和 API 诞生

科学、工程与军事需要更复杂的通用数值计算。Fortran 于 1957 年出现，把许多机器细节隐藏在高级语言和库之后。

“一行代码，一张卡片”留下了 80 列/行的历史约束，它影响了延续至今的文本格式习惯。

讲义中的 Fortran 示例完成这样一个循环：

1. 读取三个整数。
2. 如果三个数都是 0，就跳到结束标签。
3. 计算总和。
4. 按给定格式输出原数和总和。
5. 跳回读取下一组输入。

`READ(5,10)` 中的 `5` 表示输入单元，`10` 指向格式；`WRITE(6,20)` 同理；`GOTO 100/200` 用标签组织控制流；续行符和固定列格式来自卡片时代。

Fortran 足够好用以后，自然科学、工程机械和军事对算力需求暴涨。高级语言不是把问题“做完”了，它降低了使用门槛，反而制造了更多程序和用户，从而加剧共享机器的需求。

### 14.3 操作系统形成：库函数 + 排队调度

一台机器可能价值 5 万到 100 万美元，一个学校通常只有一台；写程序和装入程序又很费事。

于是算力成为服务：多个用户提交任务，由 operator 负责切换；系统软件把常用设备操作封装成库函数，并管理程序排队运行。

早期批处理解决的是“不要让昂贵机器在人类换卡时闲着”：

```text
用户提交卡片作业
  → operator/监控程序按队列装入
  → 程序运行并输出结果
  → 自动切到下一项
```

“Operating system/操作系统/作业系统”这一概念由此形成。

讲义指出今天算力又成为服务：云平台、GPU 集群和模型 API 仍在解决排队、配额、隔离与计费，只是资源规模和接口发生了变化。

### 14.4 CTSS：对象和抽象层开始成形

CTSS（Compatible Time-Sharing System）把多用户共享从“排队等待一批作业”推进到交互式分时。

操作系统里开始出现设备、文件、任务等对象；CTSS Subroutines 提供一层可调用抽象。讲义列举：

| CTSS 例程 | 大意 | 今天可联想到的抽象 |
|---|---|---|
| `RDFLXA` | 从控制台读一行 | 终端输入、标准输入、行编辑 |
| `WRFLX` | 向控制台写一行 | 标准输出、终端设备 |
| `DEAD` | 用户无程序驻留，进入 dead 状态 | 任务生命周期/退出状态 |
| `DORMNT` | 程序仍在内存，用户 dormant | 暂停、会话与驻留状态 |
| `GETMEM` | 查询内存分配大小 | 地址空间/资源查询 |
| `SETMEM` | 设置内存分配大小 | 内存管理接口 |
| `TSSFIL` | 访问 CTSS 系统文件 | 系统命名空间/权限切换 |
| `USRFIL` | 回到用户自己的目录 | 用户目录/命名空间 |
| `GETBRK` | 取得退出时的指令位置计数器 | 调试现场、PC/断点信息 |

不要把右列看成一一对应的现代 API；真正的历史意义是：重复而危险的机器操作，被命名为可复用对象与例程。

许多当时的系统功能后来下沉或上移到编程语言运行库与标准库中。抽象所在层级会变化，但需求不会消失。

## 15. 1960s—1970s：多程序驻留与资源虚拟化

### 15.1 硬件：集成电路、总线和虚拟存储

集成电路带来更快处理器，更快、更大内存；总线让部件以更规则的方式连接；I/O 设备继续丰富，中断和异常机制日益完善。

虚拟存储出现后，系统可以让多个程序同时驻留，不必每次“换卡”才能切换任务。

这里要区分硬件能力与 OS 抽象：

- MMU 提供地址转换和访问检查的机制。
- OS 决定页表如何建立、哪些页属于谁、缺页时怎么办。
- 应用看到的是相对独立、连续的地址空间。

硬件使隔离成为可能，OS 把机制组织成可用的进程抽象。

Sketchpad 图片代表这一时期交互式图形程序的突破：计算机不再只是提交卡片后等待打印结果，而开始成为人与图形实时交互的媒介。交互需求反过来要求更低延迟的调度和更丰富的设备管理。

### 15.2 软件：语言繁荣与惊奇应用

COBOL（1960）、APL（1962）、BASIC（1965）、PASCAL（1970）、C（1972）等语言相继出现。

开发者在今天看来极少的算力下写出惊人的程序，许多思想和工具沿用至今。

Spacewar 图片说明软件需求已从数值表格扩展到交互娱乐；不同语言和应用也要求 OS 提供更通用的进程、输入输出、文件和终端抽象。

### 15.3 个人电脑：Altair 8800

Altair 8800 于 1975 年登上舞台，并与 Bill Gates、Paul Allen 的创业故事相连。

它与《计算机系统基础》的契合点是：个人也可以从很低层理解并控制一台完整计算机。讲义引用 *Fire in the Valley*，并把当下 AI 普及类比为一个更热烈的新“PC 时代”——生产工具突然向更多个人开放。

个人电脑并没有让操作系统变得不重要。相反，当机器从机房走向个人、应用数量暴涨、外设越来越多，稳定接口与生态的价值更高。

### 15.4 资源虚拟化：几乎成为今天的计算机

这一阶段形成现代 OS 的核心轮廓：

- **内存和磁盘的空分复用**：不同对象占据不同空间；MMU 帮助把物理内存映射成进程地址空间。
- **CPU 的时分复用**：定时器中断让 OS 能周期性重新获得控制，选择另一个任务运行。
- **I/O 的事件化**：中断/异常让设备和错误进入统一控制路径。

```text
物理 CPU          时间片 A | 时间片 B | 时间片 C | ...
                         ↓
应用看到          “我的进程一直拥有一台逻辑 CPU”

物理内存          [A 的页][内核][B 的页][缓存]...
                         ↓
应用看到          “我有从固定地址开始的私有地址空间”
```

虚拟化不是凭空制造无限资源：CPU 总时间、物理内存和 I/O 带宽依旧有限。

它提供的是受控的假象与契约；过度竞争仍会导致延迟上升、换页、内存不足或 I/O 拥塞。后续课程会逐一拆开这些代价。

## 16. 1970s+：UNIX 对应用生态的奠基

### 16.1 一组稳定对象如何长出生态

讲义把 UNIX 视为 pre-AI 时代计算机世界的基础，并列出几项里程碑：

- 1973：信号 API、管道对象与 `grep` 应用程序。
- 1983：BSD socket 对象。
- 1984：procfs 对象。

它们共同体现“对象 + 操作 + 组合”：

- 信号把异步事件传给进程。
- 管道把一个程序的字节输出接到另一个程序的字节输入。
- `grep` 只做好文本筛选，却能嵌入无限多工作流。
- socket 把网络通信包装成可读写端点。
- procfs 把进程/内核状态投影为类似文件的命名对象，使已有文本工具能够观察系统。

UNIX 的力量不在于每个 API 单独有多复杂，而在于它们共享少量可组合约定。

### 16.2 UNIX 衍生家族与熟悉的世界

讲义沿时间列出：1BSD（1977）、GNU（1983）、MacOS（1984）、Windows（1985）、AIX（1986）、Minix（1987）、Linux 0.01（1991）、Windows NT（1993）、Debian（1996）、Windows XP（2002）、Ubuntu（2004）、iOS（2007）、Android（2008）、Windows 10（2015）等。

这份清单不是要你背年份，也不意味着所有系统都是 UNIX 的直接后代。

它要表达的是：围绕进程、文件、终端、网络和权限形成的接口与思想，影响了庞大的系统家族；即便内部实现和产品谱系不同，应用需求仍推动它们提供相似能力。

此后 PC 普及、云计算、智能手机和 AI 时代看似不断换舞台，底部仍复用这些经过几十年检验的抽象。

### 实验三：用 trace 看文本管道背后的 OS 对象

若 Linux 安装了 `strace`，在仓库任意目录运行：

```bash
strace -f \
  -e trace=process,pipe,pipe2,dup2,read,write,close \
  -o /tmp/os-pipeline.trace \
  sh -c 'printf "3\n1\n2\n" | sort -n | tail -n 1'
sed -n '1,120p' /tmp/os-pipeline.trace
```

终端应输出 `3`。trace 的确切调用数量会因 Shell、libc 和系统版本而异，但应该能找到其中若干行为：

- Shell 创建管道端点（`pipe` 或 `pipe2`）。
- Shell 创建子进程，或以等价方式安排命令执行。
- `dup2` 一类调用把标准输入/输出指向管道端点。
- 某个进程 `write`，另一个进程从相应管道 `read`。
- 不再使用的端点被 `close`；所有写端关闭后，读者才观察到 EOF。

如果系统没有 `strace`，先直接运行 `printf ... | sort -n | tail -n 1`，仍可观察功能结果；安装调试工具可能需要发行版包管理权限。某些容器或受限沙箱也会禁止 `ptrace`，此时 `strace` 可能报 `Operation not permitted`：这是外层安全策略阻止追踪，不是管道执行失败，可换到允许进程追踪的普通 Linux 环境复现。

这个实验还能帮助区分五层概念：

| 层 | 例子 | 谁规定/实现 |
|---|---|---|
| Shell 语法 | `a \| b` | Shell 解析器和执行器 |
| libc/API 包装 | `pipe()`、`read()` | C 库头文件与包装代码 |
| 系统调用 | 内核接受创建/读写对象的请求 | OS ABI 与内核 |
| 内核对象 | 管道缓冲区、文件描述符引用 | 内核实现 |
| 硬件执行 | 指令、内存访问、陷阱与返回 | CPU/内存系统 |

管道不是竖线字符本身，`read` 也不总等于一条系统调用：库可能缓冲，Shell 可能优化。系统学习必须始终问清“当前结论属于哪一层”。

## 17. 2030s+ 展望：操作系统开始服务 Model Context

传统 OS 接口主要围绕人启动的应用设计；讲义展望，未来 Model context 也会直接与 OS 交互。

底层进程、文件、网络和设备机制也许不会突然消失，但上面会增加面向 Agent 的抽象：

- 一个 model context 类似一个能够调用工具的“人”。
- 它可以创建分身，让多个 Agent 并行探索或互相批评。
- 系统需要限制每个分身的权限、预算、运行时间和可见信息。
- 多个上下文之间需要通信、共享结果、解决冲突并留下审计记录。

可以把未来栈想成：

```text
用户目标
  ↓
Agent / Model Context / Skills
  ↓
工具协议、沙箱、工作流与审计层
  ↓
进程、文件、socket、虚拟机、容器
  ↓
CPU、GPU、内存、存储、网络
```

新抽象并不会取消旧层；它依赖旧层提供执行、隔离和资源控制。

所以本课仍选择把现代 OS 向应用提供的接口讲清楚。掌握这些接口，就获得了一把“理解一切软件”的钥匙，也有能力判断 Agent 的动作在机器上真正意味着什么。

## 18. 怎么学习操作系统：从动机到可重复实验

### 18.1 找到乐趣和动机

讲义把上课描述为理解人类文明的高光时刻：发现基本动机、基本方法、里程碑与弯路，并沿它们走向应用、创新甚至革命。

OS 课的主题可以压缩为“一套 API 支撑起一切了不起的软件”，但学习时不能把 API 变成参数表。

对每个新对象都问四遍：

1. **为什么需要它**：没有它时，程序员面对什么重复、危险或低效工作？
2. **最小模型是什么**：对象保存哪些状态，哪些操作推动它迁移？
3. **真实系统如何扩展**：多核、缓存、权限、故障和兼容性加进来后发生什么？
4. **代价与边界在哪里**：抽象在哪些情况下泄漏，错误如何被观察？

每节课都应带来可立即使用的能力。今天的能力增长不是背下一个系统调用，而是能用状态机和 trace 把一个“神秘软件行为”拆成可验证步骤。

### 18.2 忘掉 Reward Hacking

大学教育服务于 long-term reward：最终能够实现自己的目标，而不是只优化一次测验得分。

Reward hacking 在学习中的表现包括：

- 猜老师会考哪句定义，却不运行示例。
- 背某次输出，却不知道换平台后为何变化。
- 让 AI 直接生成实验答案，只追求 Online Judge 变绿。
- 把未验证的流畅解释当成理解。

本课不以犄角旮旯为重点；细节依然存在，但掌握 first principles 后，很多细节能从模型和文档推导出来。

Academic integrity（“诚朴雄伟”）在 AI 时代不是拒绝工具，而是对自己的认知状态诚实：哪些是我能解释和验证的，哪些只是模型写出的答案？

“世界上没什么学不懂的东西了”意味着解释资源极大丰富；真正稀缺的是时间、注意力和愿意反复验证的耐心。

### 18.3 拥抱 LLM、Agent 与 Copilot

讲义把三者区分为：

- **LLM**：本质上给出 next-token 的概率分布，却能表现为聊天、解题和写代码。
- **Agent**：LLM 获得手和脚，能按需读取项目、调用工具和修改文件。
- **Copilot**：把已经发生的上下文持续提供给模型，使它能判断当前进展并建议下一步。

在 OS 学习中，可以这样使用：

```text
先写预测
  → 请 AI 帮忙缩小实验或查找 API 线索
  → 自己运行程序并保存输出
  → 用 strace/gdb/procfs/perf 收集证据
  → 区分语言、库、内核与硬件层
  → 修正解释并形成可重复测试
```

模型非常适合解释手册、生成调试脚本、枚举反例和对比不同假设；模型不能替代真实运行环境裁决事实。

## 19. AIGC Policy：允许辅助，不允许外包学习目标

### 19.1 日常学习中鼓励的使用

讲义明确鼓励 AI 辅助：

- 解释概念、命令行工具和 API。
- 给出“使用什么工具、怎样调试”的方法指导。
- 生成调试、可视化等辅助代码。
- 把这些能力组成随时可用的 Copilot。

一个好的提问不是“替我做完”，而是：

```text
我预测关闭管道写端后 read 返回 0。
这是最小复现、编译命令和 strace。
请帮我区分短读、EOF 和 EINTR，并建议下一项观察。
```

这样 AI 扩大的是你的观察力。

### 19.2 MiniLab 的边界

MiniLab 仅允许生成“单个 API 的使用方式”，禁止把完整自然语言需求直接翻译成可提交答案。

讲义的例子是：

- 允许：“帮助我调用 `pipe()`，并把读端和写端分别赋给 `read_fd`、`write_fd`。”
- 禁止：“帮我完成实验，测试通过以后直接提交。”

边界背后的学习目标很清晰：查 API 样板不是核心困难；把对象生命周期、错误路径和多个 API 组织成正确系统才是实验要评价的能力。

还要遵守一个工程原则：AI 生成的 C 代码必须检查关键系统调用返回值。否则成功路径看似正确，真实故障却被误解成 OS 的奇怪行为。

## 20. 概念辨析与常见误区

### 20.1 “操作系统就是 Linux 内核”

内核是资源管理和保护的核心，但日常所说的“操作系统环境”还包括 libc、Shell、系统服务和应用生态。

本课讨论狭义 OS 时会明确聚焦内核提供的抽象；讨论 UNIX 生态时又会包含用户态工具。先声明观察层级，比争一个永恒定义更有用。

### 20.2 “虚拟化就是虚拟机”

虚拟机只是虚拟化的一种。

进程让应用仿佛拥有独立 CPU 和地址空间，文件把存储介质抽象成命名字节序列，socket 把网络通信抽象成端点；这些也都是资源虚拟化。

### 20.3 “程序没有输入输出时就没有状态”

局部变量、调用栈、堆、全局变量和 `pc` 都是状态。

没有外部副作用只意味着某些内部迁移可能对观察者不可见，不意味着程序不是状态机。

### 20.4 “C 函数等同于数学函数”

C 函数能修改全局内存、打印、写文件、读时钟甚至与设备交互。

返回值相同并不足以证明两次执行等价；外部 API 调用序列和终止行为也可能是语义的一部分。

### 20.5 “命令行只是过时 UI”

GUI 对人类探索很友好，CLI 则在可组合、可记录、可自动化方面有独特优势。

现代系统常同时提供 GUI、CLI 和 API；关键是让核心能力与具体前端分离。

### 20.6 “AI 会写代码，所以底层细节无须验证”

代码生成降低了实现成本，却没有改变硬件资源、并发交错、权限边界和失败模式。

越容易生成大规模代码，越需要抽象、测试、trace 和最小可信边界。

### 20.7 “系统调用、库函数和命令是一回事”

`sort` 是应用程序，`printf` 通常是 libc 函数，`write` 既可指 POSIX API 包装也可泛指内核系统调用，CPU 最终执行的是指令。

它们可能沿一条调用链相连，却属于不同契约层。后续每一讲都要保持这种区分。

## 21. 本讲 Takeaways

原讲义的结论是：

> 操作系统是软件和硬件之间的桥梁；因此，只要找到合适的软件与相对简单的硬件，理解操作系统就会变得容易。课程通过讲解 OS 上的应用，帮助你实现“编程”的梦想。

把全讲再压缩一次：

1. 硬件和程序都可以视为状态机；OS 夹在二者之间，组织状态、事件和资源。
2. OS 的价值不在一句定义，而在抽象、复用、隔离以及由稳定接口形成的生态。
3. OS 是历史产物：没有共享需求时它不存在；机器昂贵、I/O 缓慢时出现批处理；多程序驻留与中断/MMU 催生资源虚拟化；UNIX 对象与工具塑造应用生态。
4. AI 让代码便宜，却使抽象设计、权限控制、系统验证和可组合工具更加重要。
5. 学 OS 的正确单位不是“背了几个 API”，而是“能否提出模型、运行实验并解释观察结果”。

## 22. 思考题与练习

1. 如果一台机器永远只运行一个完全可信程序，哪些 OS 职责仍然必要，哪些可以省略？请分别讨论设备抽象、调度和隔离。
2. 中断是硬件机制，调度是 OS 策略。为什么“有中断”不自动等于“有多任务”？
3. `printf` 为什么让汉诺塔两次递归调用不可随意交换？如果把所有移动步骤先写入一个不可变列表，情况是否变化？
4. 用“状态、初始状态、迁移规则”描述实验一中的 `Task`；再列出它与真实进程模型至少三处差异。
5. 为什么高级语言降低编程门槛后，反而会增加对操作系统的需求？
6. CTSS 的 `DORMNT` 和 `DEAD` 暗示了哪些不同状态？为什么系统要区分“程序还在内存”和“没有程序在内存”？
7. 管道为什么能让两个互相不知道源代码的程序协作？稳定文本协议的收益和风险分别是什么？
8. `procfs` 把系统状态呈现成文件有什么组合优势？哪些动态状态很难完全符合普通文件直觉？
9. 假设一个 Agent 可以调用 Shell。请列出 OS 必须为它提供的三种保护，以及仅靠提示词无法可靠提供这些保护的原因。
10. 选择日常软件的一个操作，例如“浏览器下载文件”，画出从应用意图到硬件设备的层次，并标出至少两个可能失败的位置。

## 24. 与第 2 讲的衔接

本讲说“程序和硬件都是状态机”，仍然是一幅大图。

下一讲《应用视角的操作系统》将把“程序”精确到每个 bit：

- 用栈帧、全局变量和 PC 描述函数调用状态，而不是停留在“变量 + 栈 + PC”的含糊印象。
- 讨论编译正确究竟意味着什么，以及外部 API 调用序列为何构成可观察行为。
- 从 `_start` 和系统调用开始构造最小程序，观察程序如何把自己的状态机“交给”操作系统。

也就是说，第 1 讲建立三层坐标，第 2 讲会拿最上层“软件”开刀：当我们能机械地解释程序的每一次状态迁移，OS 究竟在什么时刻、通过什么边界进入程序世界，就可以被严格地问出来。
