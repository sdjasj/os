# 第 3 讲：硬件视角的操作系统——从 CPU Reset 到 OpenSBI

> 原始讲义：[sources/notes/lect03.md](../../sources/notes/lect03.md)  
> 前一讲：[应用视角的操作系统](02-application-view.md) · 后一讲：[Scaling Law 和 Agentic AI](04-scaling-agentic-ai.md)  
> 本讲关键词：硬件状态机、内部/外部状态、GPIO、Reset、Firmware、BIOS、UEFI、CIH、Boot Loader、OpenSBI、SBI

## 0. 本讲定位：沿着系统调用继续向下追问

第 2 讲从应用一侧建立了两个关键模型：

1. C 程序可以看成不断执行语句的状态机；
2. 编译器把它变成机器指令，而 `syscall`、`ecall`、`svc` 会把控制权交给操作系统。

但这里留下了一个很自然的问题：执行 `syscall` 的 CPU，真的认识“应用”和“操作系统”吗？

答案是：**硬件根本不知道有没有操作系统。**

CPU 只按照指令集定义修改寄存器、内存和控制状态；所谓“进入内核”，只是硬件按照预先配置好的规则，保存一部分状态、改变特权级并跳到另一个地址。内核之所以特殊，不是因为二进制文件上刻着“OS”，而是因为它先取得了高特权级控制权，并配置了中断、内存和 I/O。

本讲将沿着下面这条链反向追到机器出生的一刻：

```text
应用执行系统调用
    ↓
CPU 按陷阱规则跳到高特权级代码
    ↓
谁最初配置了这些规则、装入了内核？
    ↓
固件与引导程序
    ↓
谁最初运行固件？
    ↓
CPU Reset 与 reset vector
```

下一讲是 Hacking Day，将讨论 Scaling Law、Agent 和复杂系统中的抽象分解。本讲恰好提供一个真实样本：ISA、BIOS/UEFI、SBI、系统调用都是稳定接口；只要接口边界清楚，人或 Agent 才能分工探索复杂系统，并用实验检查结论。

## 1. 学习目标与问题地图

学完本讲，你应该能够：

- 用统一的状态机模型描述 CPU、内存和设备；

- 说明 CPU Reset 明确规定了什么，以及哪些状态不能想当然；
- 画出从 Reset、固件、引导程序到内核的完整控制流；
- 比较 Legacy BIOS、UEFI 和 RISC-V OpenSBI 的角色与接口；
- 解释 CIH 为什么能使一些旧 PC 无法启动，以及现代可信更新如何缓解风险；

## 2. 学习方法：不要只“看过”示例

讲义开场提醒了一件容易被忽略的事：大家都知道应该下载、编译、运行示例，但看到一个陌生项目和一长串构建命令时，很容易只扫一眼页面。

在 Agentic AI 时代，可以把陌生项目变成一种主动学习材料。一个有效的起点是：

> 我正在做 X。如果你是这个领域的专家，你会先检查什么、如何缩小问题、如何验证每一步？

有两种互补用法：

- **被动观察**：看 Agent 先读了哪些文件、执行了哪些探测命令、如何解释失败；
- **主动追问**：让它解释每个选择，再要求给出一个能推翻当前假设的实验。

不过，Agent 的回答不是硬件规范。学习系统时应坚持“概念—预测—实验—手册”闭环：

1. 先用状态机和接口形成概念；
2. 在运行前写下预测；
3. 用模拟器、调试器或真实机器取证；
4. 出现分歧时查对应架构/平台手册；
5. 把可复现命令保留下来，而不是只保留一段聊天记录。

这也是讲义中“只要先有 GPIO、Reset、Firmware 的正确概念，细节就可以继续询问和验证”的准确含义。它不是“细节不重要”，而是先建立能容纳细节的骨架。

## 3. 第一原则：硬件是一台无情执行指令的状态机

### 3.1 硬件不知道“这段代码是操作系统”

从 CPU 看，Linux 内核、GRUB、OpenSBI 和一个裸机 Hello World 都只是内存中的比特。CPU 不会主动寻找文件名为 `vmlinuz` 的文件，也不理解“进程”“文件”和“窗口”。它只提供机制：

- 从程序计数器指定的位置取指；
- 译码并执行指令；
- 在异常或中断发生时按规则跳转；
- 根据当前特权级决定某些操作是否合法；
- 通过普通 load/store 或专门 I/O 指令访问设备。

“操作系统”是软件对这些机制的一种组织方式。它先占据高特权级，管理中断和 I/O，再轮流把应用的状态放到 CPU 上执行。

因此，一台机器在某一时刻运行的是应用还是内核，只能从当前 `PC`、特权级、页表和控制寄存器等状态判断；不能从“硬件是否开启了 OS 模式”判断，因为通常没有这样一个模式。

### 3.2 抽象为什么能隔离复杂性

讲义用组织制度类比抽象层：下层只履行约定的职责，不必知道上层最终如何使用它。

计算机里有多道这样的边界：

```text
应用/库       只依赖系统调用，不必知道页表怎样实现
操作系统      只依赖 ISA 和平台接口，不必知道晶体管怎样实现 add
固件/驱动     只依赖设备规范，不必知道用户会运行什么应用
硬件          只执行 ISA 规定的操作，不必知道哪段代码叫 Linux
```

抽象不是“隐藏一切”，而是**公开一个稳定的接口，同时允许接口两侧独立演化**。x86、AArch64 和 RISC-V 的硬件实现差别巨大，但都能运行相似的 Linux 应用生态；同一个 RISC-V S-mode 内核也可借助 SBI 在不同平台上请求定时器、跨核中断等服务。

这也是下一讲讨论复杂性分解时最重要的系统例子：分工能否成功，取决于接口是否足够精确，而不是参与者数量是否足够多。

## 4. 把“计算机状态”写完整

### 4.1 内部状态：CPU 能直接控制的比特

讲义给出了一个精简的处理器状态：

```c
struct CPUState {
    uint32_t regs[32], csrs[CSR_COUNT];
    uint8_t *mem;
    uint32_t mem_offset, mem_size;
};
```

它表达了处理器模拟器最重要的部分：通用寄存器、控制状态寄存器（CSR）和内存。更完整的模型还可能包括：

- `PC`，即下一条待执行指令的位置；
- 当前特权级；
- 浮点、向量和调试寄存器；
- 页表根、地址转换缓存和缓存状态；
- 多个处理器各自的寄存器状态；
- 设备模型与挂起的事件。

抽象地写，一台单核机器的内部状态可表示为：

\[
S_{in}=(PC, Registers, Control, Memory, Devices)
\]

执行一条指令，就是由当前指令和状态决定下一个状态：

\[
S'_{in}=T(S_{in},\;Instruction)
\]

这个模型很“无情”：`add` 就计算，`store` 就写，`jmp` 就改 `PC`。只要没有异常，CPU 不会追问程序的目的。

### 4.2 外部状态：CPU 无法独占控制的整个世界

只写寄存器和 RAM 仍不完整。键盘按键、网线电信号、时钟、复位按钮和硬盘介质都在 CPU 之外，它们可能自行变化。

讲义特别指出两类外部入口：

- **设备寄存器**：常被映射到地址空间，CPU 可用 load/store 读取或写入；
- **Interrupt/Reset Line**：外部电路能请求中断或让处理器重新进入复位状态。

现实机器还存在 DMA：设备可能在 CPU 不执行 store 的情况下修改内存。于是更贴切的全系统模型是：

\[
(S_{in},S_{world})\rightarrow(S'_{in},S'_{world})
\]

一次迁移既可能来自 CPU 执行指令，也可能来自设备完成请求、定时器到期、另一个核写共享内存或用户按下 Reset。

这一区分非常重要：软件可以请求网卡发送一个包，却不能保证网线另一端一定响应；程序可以清除某个中断状态，却不能阻止未来新的外部事件到来。

### 4.3 三类状态迁移

本讲把硬件状态迁移归纳为三类：

1. **执行指令**：从 `Mem[PC]` 取指、译码、执行并更新 `PC`；
2. **响应中断/异常**：若条件满足，保存必要状态并跳到中断向量；
3. **输入输出**：CPU 与设备交换数据，设备也可异步推进自己的状态。

一个极简中断模型可以写成：

```text
if interrupt_pending && interrupt_enabled:
    saved_pc = pc
    privilege = higher_level
    pc = interrupt_vector
else:
    execute(mem[pc])
```

真实架构还要规定优先级、屏蔽位、委托关系、返回指令和精确异常语义，但操作系统能够实现抢占的关键，已经包含在这几行里。

### 4.4 为什么 `jmp .` 不一定卡死整台机器

`jmp .` 会让 `PC` 不断回到自己。如果只考虑“执行下一条指令”，机器的确永远停在此处；但若定时器中断已经启用，CPU 会在指令边界响应中断并跳入内核。

内核随后可以：

- 记录当前程序用完了时间片；
- 保存它的寄存器；
- 恢复另一个进程的寄存器；
- 通过陷阱返回指令继续运行另一个进程。

这“一点点细节”正是抢占式操作系统存在的基础。

边界也要说清：如果代码运行在足够高的特权级并关闭了可屏蔽中断，一个普通定时器可能无法夺回控制；系统只剩 NMI、watchdog、Reset 等更强机制。因此内核死循环往往比用户态死循环严重得多。

### 4.5 多处理器怎样放进状态机

教学模型可把多核执行简化成“每次任选一个处理器执行一条指令”。这样，所有可能的选择顺序构成并发程序的不同执行轨迹。

真实处理器可以真正同时执行，并且有缓存、乱序和弱内存序；单纯的任意交错不能解释全部硬件行为。不过它是后续并发章节的第一层模型：先理解多个状态机共享内存，再逐步加入原子指令、内存屏障和缓存一致性。

## 5. 实验 1：亲手看见死循环、GPIO 与中断

下面的 Python 程序不是某个真实 ISA，而是一个刻意缩小的硬件模型。它包含程序计数器、一个内存映射的 LED、外部中断线和中断向量。

依赖：Python 3；不会访问真实硬件。

```bash
python3 - <<'PY'
class CPU:
    def __init__(self):
        self.pc = 0
        self.saved_pc = None
        self.interrupt_enabled = True
        self.interrupt_line = False
        self.led = 0

program = {
    0: ("WRITE_LED", 1),  # 类比写 GPIO 的 MMIO 寄存器
    1: ("JMP", 1),        # 永远跳回自己
    4: ("XOR_LED", 1),    # 中断处理程序入口
    5: ("IRET",),
}

def step(cpu, tick):
    if cpu.interrupt_line and cpu.interrupt_enabled:
        cpu.saved_pc = cpu.pc
        cpu.pc = 4
        cpu.interrupt_enabled = False
        cpu.interrupt_line = False
        print(f"tick={tick}: interrupt -> vector 4, saved_pc={cpu.saved_pc}")

    op, *args = program[cpu.pc]
    old_pc = cpu.pc
    if op == "WRITE_LED":
        cpu.led = args[0]
        cpu.pc += 1
    elif op == "XOR_LED":
        cpu.led ^= args[0]
        cpu.pc += 1
    elif op == "JMP":
        cpu.pc = args[0]
    elif op == "IRET":
        cpu.pc = cpu.saved_pc
        cpu.interrupt_enabled = True
    print(f"          execute {op:9s} at pc={old_pc}; next_pc={cpu.pc}, LED={cpu.led}")

cpu = CPU()
for tick in range(8):
    if tick in (3, 6):       # 外部定时器拉高中断线
        cpu.interrupt_line = True
    step(cpu, tick)
PY
```

你会观察到：

1. `WRITE_LED` 把外部可见状态改为 1；
2. `JMP` 让主程序停在 `pc=1`；
3. 第 3、6 个 tick 到来的中断先把原 `PC` 保存起来，再把 `PC` 改为 4；
4. 中断处理程序翻转 LED，并用 `IRET` 回到死循环。

试着把 `self.interrupt_enabled = True` 改成 `False`。此时外部中断线虽然被拉高，CPU 却一直执行 `JMP`。这正好展示“有外部事件”和“处理器允许响应它”是两个不同条件。

## 6. GPIO：一条 store 怎样点亮现实中的灯

GPIO 是 General-Purpose Input/Output 的缩写。一个 GPIO 控制器通常暴露若干寄存器：

- 方向寄存器：引脚作为输入还是输出；
- 数据输入寄存器：采样当前电平；
- 数据输出寄存器：输出高/低电平；
- set/clear 寄存器：原子地置位或清位；
- 中断配置寄存器：选择上升沿、下降沿或电平触发。

如果这些寄存器被 memory-map 到地址 `GPIO_BASE`，裸机代码在概念上可能做：

```c
/* 仅为机制示意；地址、位宽、屏障要求必须查具体 SoC 手册。 */
volatile unsigned int *gpio_out = (void *)(GPIO_BASE + GPIO_OUT_OFFSET);
*gpio_out |= (1u << 23);
```

这一条 C 赋值最终变成 store。互连总线看到目标地址属于 GPIO 控制器，便把写入交给设备，而不是 RAM；控制器再改变引脚电平，经过限流电阻点亮 LED。

Linux 内核中的 `gpio_set_value(GPIO_23, 1)` 表达的是相同意图，但经过 GPIO 子系统和具体控制器驱动。现代内核还推荐 descriptor-based GPIO API；用户态通常使用 `/dev/gpiochipN` 与 `libgpiod`，而不是直接映射物理地址。

可以做一个完全只读的探测：

```bash
ls -l /dev/gpiochip* 2>/dev/null || echo '没有暴露 gpiochip（普通 PC 上很常见）'
if command -v gpioinfo >/dev/null 2>&1; then
  gpioinfo
else
  echo '未安装 libgpiod 工具；这里只做概念观察'
fi
```

在树莓派等开发板上，`gpioinfo` 会列出 line 名称、方向和占用者。不要在不了解电路的情况下照抄“点灯”命令：错误方向、引脚复用、短路或超出电流能力可能损坏设备；系统中的某条 GPIO 还可能连接复位、供电或存储写保护信号。

另外，`volatile` 只约束编译器访问，并不自动满足设备要求的内存顺序、缓存属性和屏障。真实驱动应使用内核提供的 `readl()`、`writel()` 或 GPIO API，而不是把物理地址强转成普通指针。

## 7. CPU Reset：机器的“初始状态”是一份协议

### 7.1 Reset 不等于“所有寄存器清零”

CPU 上电或 Reset line 生效时，体系结构会把关键状态设为规定值，使处理器从某个 reset vector 开始取指。

“规定值”不意味着所有位都是 0。架构可能明确某些寄存器的初值，把另一些标为未指定或实现相关。可靠的固件必须主动初始化自己依赖的状态，不能赌通用寄存器恰好为零。

Reset 至少要解决三个问题：

1. 第一条指令从哪里取？
2. 初始特权级和中断状态是什么？
3. 在 DRAM 尚未初始化时，最早的代码和栈放在哪里？

系统厂商会把 ROM、片上 SRAM 或 Flash 中的固件映射到 reset vector 可访问的位置。于是 CPU 的第一次取指就能得到合法机器码。

### 7.2 三种架构体现的设计取舍

不同架构的具体数值必须以相应版本手册和 SoC 文档为准，但可以先比较设计理念：

| 架构 | Reset 后的典型入口特征 | 体现的取舍 |
| --- | --- | --- |
| x86 | 从架构规定的高地址 reset vector 开始，并保留很强的早期 PC 兼容语义；现代 CPU 的精确隐藏基址状态不能只用“16 位实模式地址”概括 | 把数十年的向后兼容置于中心 |
| AArch64 | 通常进入实现支持的最高异常级；reset 地址和若干行为带有实现/平台属性，由 SoC Boot ROM 接续 | 架构与具体平台启动方案分层 |
| RISC-V | hart 从平台规定的 reset vector 启动，通常先在 M-mode；规范只规定必要机制，平台负责提供启动环境 | 保持 ISA 简洁，把策略交给平台/固件 |

以 x86 为例，早期 8086 常被描述为从物理地址 `0xffff0` 附近开始；现代处理器的复位取指位置通常靠近 4 GiB 顶部，并通过兼容状态跳入固件。两句话对应不同代际，不能把一个数值无条件套到所有 x86。

Arm 和 RISC-V 更强调平台文档：知道“最高特权级 + 平台 reset vector + Boot ROM”这一概念后，再查询具体开发板的 Technical Reference Manual，才能得到可调试的精确地址。

### 7.3 Reset 按钮为什么曾经如此重要

如果软件关闭中断、破坏关键设备状态或让内核陷入不可恢复的循环，普通按键和进程管理器都依赖的软件栈已经无法工作。物理 Reset line 绕过这套软件状态，强迫 CPU 和平台设备回到约定起点。

今天的“重启”可能先由 OS 做同步、卸载文件系统和 ACPI/平台复位；物理复位则更接近硬件机制。二者最终可能都触发平台 reset，但数据一致性和设备清理过程不同。

讲义展示老式机箱的 Reset 按钮，正是为了强调：**Reset 是状态机的初始状态构造器，不是一个抽象的“重新运行程序”按钮。**

## 8. 从 Reset 到固件：第一段代码从哪里来

CPU 自身不会解析磁盘文件系统；上电后 DRAM 甚至可能还不能可靠使用。因此 reset vector 处必须已经存在可执行代码。

这段由系统厂商固定在机器中的代码就是 Firmware（固件）。早期它在不可改写 ROM 中；后来常在 EEPROM 或 Flash 中，可以升级。

典型固件依次完成：

1. 建立最早期执行环境，例如片上 SRAM 或 cache-as-RAM；
2. 初始化时钟、内存控制器与 DRAM；
3. 枚举、检测并配置处理器和设备；
4. 读取持久化设置，选择启动设备；
5. 建立设备描述或配置表；
6. 定位、校验并装入下一阶段程序；
7. 按约定传递参数和控制权；
8. 某些平台上继续提供运行期服务。

所以“不严格地说，固件加载操作系统”是合适的第一层描述。更准确地说，固件经常加载 Boot Loader，Boot Loader 再装入内核；也可能由固件直接装入内核，或由 QEMU 的 `-kernel` 选项绕过通常的固件/引导路径。

### 8.1 为什么固件设置常要求重启

按 Del、F2、F10、F12 等键进入的设置界面本身也是固件代码。它能直接看到 CPU 功能、内存时序、风扇、供电和设备接口，因为它位于操作系统之下。

有些选项改变的是下次硬件初始化采用的参数，或者必须在 CPU/设备离开 reset 前配置；因此保存后需要重启。操作系统里的 GUI 不是这些设置的唯一入口，只是可能通过 ACPI、UEFI 变量等接口间接请求固件。

### 8.2 固件像一个小操作系统，但不要混同二者

固件有驱动、菜单、网络栈、存储访问甚至 Shell，看起来像小型 OS。它和通用 OS 的根本差异主要在使命和生命周期：固件首先负责建立平台、选择启动目标和定义最早的信任根；通用 OS 则长期为应用提供资源抽象、隔离和调度。

固件依然只是代码，也会有越界访问、驱动漏洞、供应链错误和配置缺陷。它执行得更早、权限更高，所以错误的影响反而可能更深。

## 9. Legacy BIOS 与 UEFI：两代 PC 固件接口

### 9.1 Legacy BIOS

IBM PC 的 BIOS 为早期兼容机定义了共同约定：

- 在 16 位启动环境中执行；
- 用 BIOS interrupt services 提供显示、键盘、磁盘等基本 I/O；
- 检查启动设备的引导扇区；
- 把合格的 512 字节扇区装入 `0x7c00` 并跳转执行。

DOS 时代，程序还会直接调用 BIOS 中断完成 I/O。共同规范让不同厂商的主板、显卡和存储设备形成“兼容机”生态，AMI、Phoenix 等固件厂商由此成长。

但 BIOS 的 16 位环境、地址空间和 MBR 分区方案都有历史限制。现代内核通常不会在正常运行期继续依赖 BIOS 完成高性能设备 I/O，而会使用自己的驱动。

### 9.2 UEFI

UEFI 不只是“更漂亮的 BIOS 菜单”。它定义了更现代的可扩展执行环境：

- 以协议和句柄组织设备与服务；
- 能加载 EFI System Partition 中的 PE/COFF 可执行文件；
- 提供 Boot Services，供引导程序分配内存、访问文件和设备；
- 在 `ExitBootServices()` 后把主要硬件控制权交给 OS；
- 保留少量 Runtime Services，如变量和时间服务；
- 可集成驱动、网络启动、图形界面与 Secure Boot。

因此，指纹验证、PXE 网络启动、USB 输入设备等都可能在 OS 运行前可用。代价是固件代码量和攻击面也更大。

### 9.3 两者的共同本质

BIOS interrupt、UEFI protocol 和 Boot Services 形式不同，本质都在回答：**在完整操作系统接管设备之前，下一阶段代码怎样使用最少的平台能力？**

| 维度 | Legacy BIOS | UEFI |
| --- | --- | --- |
| 启动对象 | 磁盘引导扇区中的机器码 | ESP 中的 EFI 可执行文件 |
| 典型接口 | 软件中断与固定历史约定 | 协议、句柄、函数表 |
| 典型分区 | MBR | 常与 GPT/ESP 配合 |
| 扩展能力 | Option ROM 等，约束较强 | 驱动、网络、图形、变量等更丰富 |
| 交接 | 跳入引导扇区/后续加载器 | 引导器调用 `ExitBootServices()` 后接管 |

UEFI 机器常保留兼容支持，但“BIOS 会把 512 字节放到 `0x7c00`”不是所有现代启动方式的普遍定律。

## 10. CIH：固件为何必须被保护

### 10.1 从只读 ROM 到可更新 Flash

真正不可写的 ROM 很难被软件破坏，但也无法修复缺陷。PC 厂商转向可电擦写的 EEPROM/Flash 后，固件更新变得方便，也产生了新的安全问题：如果运行中的恶意代码能解除写保护，它就能改写 CPU Reset 后最先执行的内容。

讲义回到 1998 年的 Intel 430TX/Pentium 时代。当时一些主板允许软件通过芯片组寄存器和特定命令序列开放 Flash 写入；有的主板有物理写保护跳线，却未必默认启用。命令序列写在手册中不是漏洞——硬件接口必须可编程——真正的问题是系统没有把“谁可以使用这个接口”隔离好。

### 10.2 CIH 做了什么

CIH（Chernobyl）感染 Windows 9x 可执行程序，在特定日期触发破坏载荷。课程强调它的历史冲击：年轻作者编写的病毒不仅破坏磁盘数据，还会尝试通过芯片组/Flash 接口擦写兼容主板的 BIOS 区域。

讲义给出的历史背景是：作者当时 23 岁，最初带有让号称“百分之百防毒”的产品出洋相的炫技动机；他后来被捕，但在当时的法律条件下未被定罪。这段历史的教训不是浪漫化病毒作者，而是说明技术能力、接口权限和法律治理曾经严重错位。

因而机器可能在下次 Reset 后取不到有效固件代码，表现为无法启动，只能使用外部编程器重刷芯片或更换 EEPROM/主板。

“破坏硬件”在这里要精确理解：多数情况下并非把硅片物理烧毁，而是破坏了启动所必需的非易失代码，使整机在普通用户眼中像硬件坏掉。它仍然证明了软件可以跨越不当保护的接口，造成恢复成本极高的后果。

课程提供的可读 C 翻译用于理解感染、潜伏和破坏流程。学习时不要在真实机器上复现固件写入载荷；安全的做法是在不含危险 I/O 的代码审阅、反汇编或隔离模拟环境中分析控制流。

### 10.3 现代防护：让“可更新”与“不可任意改写”同时成立

核心原则是：**只接受经过授权的固件映像，并尽量让写保护独立于普通软件。**

常见机制包括：

- 固件更新包的数字签名；
- 固件中的公钥或其哈希作为信任根；
- 芯片组写保护、锁定位或物理写保护；
- 启动时逐级验证下一阶段代码；
- 双映像、恢复分区和失败回滚；
- TPM/度量启动，用于记录而不一定阻止启动。

签名流程可简化为：厂商用私钥对映像摘要签名，设备用内置公钥验证。攻击者即使能下载任意字节，也无法在没有私钥时伪造有效更新。

需要辨析：Diffie–Hellman 主要用于密钥协商，不等同于数字签名；RSA、ECDSA/EdDSA 等可用于签名。HTTPS/TLS 能保护更新传输，但“连接使用 HTTPS”不能替代设备对固件本身的签名验证。

如果厂商私钥泄漏，验证机制会忠实地接受攻击者签出的恶意映像；讲义提到 Intel Boot Guard 密钥泄漏案例，就是在强调安全链最终依赖密钥治理和供应链，而不是只依赖一个密码学算法名称。

### 10.4 今天恶意软件为什么更偏向窃取权限

现代 OS 隔离、应用商店审查、安全启动与云端备份提高了纯破坏的门槛，也降低了攻击者收益。账户、支付、隐私、浏览器 Cookie、云凭据和 LLM Token 则可以直接变现。因此攻击重点常从“炫技式摧毁机器”转向长期驻留、提权和凭据窃取。

这不表示固件攻击已经消失；恰恰因为固件低于 OS、难检测且可持久化，它仍是高价值目标。

## 11. 从固件到 OS：传统 PC 的 512 字节契约

### 11.1 `0x7c00`、`0x55 0xaa` 与 `eb fe`

以 IBM PC/PC-DOS 2.0 时代形成的 Legacy BIOS 约定为例：固件读取启动磁盘的第一个 512 字节扇区，检查末尾两个字节是否为 `0x55, 0xaa`，合格后把扇区放到物理地址 `0x7c00` 并转去执行。

在小端 x86 上，若把末尾两字节看成 16 位数，它是 `0xaa55`；在磁盘字节序列中仍应写成 `55 aa`。

`0x55` 和 `0xaa` 的位模式分别是 `01010101` 与 `10101010`。交替位模式便于识别某些位线/固定电平故障，是合理的工程直觉；最重要、可验证的事实仍是：它们是启动协议规定的 magic number，而不是 CPU 指令集自动赋予的意义。

讲义中的前两个字节 `eb fe` 是 x86 的短跳转：`EB` 表示带 8 位有符号位移的 jump，`FE` 是 `-2`，从下一条指令地址跳回当前指令，因此形成 `jmp .`。

### 11.2 为什么常说只有 446 字节

传统 MBR 布局是：

```text
offset 0                 446             510   512
       +------------------+---------------+-----+
       | bootstrap code   | 4×16B entries |55 AA|
       +------------------+---------------+-----+
                              partition table
```

所以保留分区表时，第一阶段引导代码通常只有 446 字节。若它是无分区介质上的 Volume Boot Record，布局可以不同；“所有 boot sector 都只能写 446 字节”是误解。

## 12. 实验 2：构造并观察一个真的引导扇区

依赖：Python 3、GNU `objdump`；可选 `qemu-system-i386`。实验只写 `/tmp/bootloop.img`。

先生成精确的 512 字节镜像：

```bash
python3 - <<'PY'
from pathlib import Path

image = bytes.fromhex("eb fe") + bytes(508) + bytes.fromhex("55 aa")
assert len(image) == 512
Path("/tmp/bootloop.img").write_bytes(image)
print("size =", len(image), "signature =", image[510:].hex(" "))
PY

xxd -g 1 -l 16 /tmp/bootloop.img
xxd -g 1 -s 496 -l 16 /tmp/bootloop.img
objdump -D -b binary -m i8086 /tmp/bootloop.img | sed -n '1,12p'
```

预期看到开头是 `eb fe`，结尾是 `55 aa`，反汇编的第一条指令跳回地址 0。

若安装了 QEMU，可以让固件真的加载它，并记录翻译过的指令块：

```bash
timeout 3s qemu-system-i386 \
  -drive file=/tmp/bootloop.img,format=raw,if=floppy \
  -display none -serial none -monitor none -no-reboot \
  -d in_asm -D /tmp/bootloop.qemu.log || [ "$?" -eq 124 ]

grep -n -A4 '0x00007c00' /tmp/bootloop.qemu.log | head
```

`timeout` 到期是预期结果，因为引导扇区永不退出。日志中出现 `0x00007c00` 和 `jmp` 说明：

1. CPU 最初并不是从 `0x7c00` Reset；
2. 前面运行的固件把磁盘内容搬到了那里；
3. 固件最终把控制权交给了这两个字节；
4. 之后 CPU 仍然只是执行普通指令。

把签名改成 `00 00` 再运行，BIOS 通常会拒绝把它当作可启动扇区并尝试其他设备。这是检验“magic number 属于固件协议而非 CPU 行为”的对照实验。

## 13. 把“固件加载了它”继续追到具体指令

实验 2 只证明控制流到达 `0x7c00`。讲义进一步问：究竟是哪条固件指令把数据写到了那里？

QEMU 可以在启动时暂停并开放 GDB 端口：

```bash
qemu-system-i386 -S -s \
  -drive file=/tmp/bootloop.img,format=raw,if=floppy \
  -nographic
```

在另一个终端启动 GDB，并把重复操作写入 `/tmp/init.gdb`：

```gdb
set pagination off
set architecture i8086
target remote :1234
awatch *(unsigned short *)0x7c00

define hook-stop
  printf "\n--- stopped ---\n"
  x/6i $pc
  info registers cs eip eax ebx ecx edx esi edi
end

continue
```

然后执行：

```bash
gdb -q -x /tmp/init.gdb
```

思路比命令细节更重要：

- 普通 breakpoint 回答“执行何时到达这个地址”；
- Watch Point 回答“谁读写了这个地址”；
- `hook-stop` 在每次暂停时自动打印最关心的上下文；
- `init.gdb` 把一次性交互变成可重复实验。

不同 QEMU/GDB 版本对实模式地址显示、硬件 Watch Point 和固件符号的支持略有差异；若 `awatch` 没停，可以先 `hbreak *0x7c00` 验证交接，再使用 QEMU 的调试日志或带符号的 SeaBIOS 构建逐步缩小范围。加载动作也可能由一串 PIO/DMA 与内存复制共同完成，不能预设“一定有一条普通 `mov` 指令包办一切”。

这就是《计算机系统基础》中 Watch Point 方法的延伸：把“文档说固件会加载”转化成对具体状态变化的追踪。

## 14. Boot Loader：446 字节怎样长成完整的 GRUB

512 字节不可能容纳友好菜单、多个文件系统驱动和完整内核加载逻辑，所以传统引导器会分阶段：

1. **Stage 1**：驻留 MBR 的极小代码，只负责找到并加载更多代码；
2. **Stage 1.5**：历史上可放在 MBR 后的空隙，包含识别某些文件系统所需能力；
3. **Stage 2**：完整 GRUB，读取配置、显示菜单、理解文件系统；
4. **加载内核**：把 Linux 内核和 initramfs 放到约定位置，准备参数并跳转。

讲义用“扫描附近的 ELF 文件头”帮助建立直觉：小阶段只需找到更强的下一阶段，然后能力逐级增长。具体 GRUB 版本、安装方式和磁盘布局可能不同，不能把这句直觉当成所有版本逐字执行的算法。

UEFI 启动时，GRUB 可以直接作为 ESP 中的 EFI 应用被固件加载，不必从 446 字节 Stage 1 起步。这再次说明：Boot Loader 的目的稳定，具体机制由固件接口决定。

控制权链可以总结为：

```text
CPU reset vector
  → 固件早期代码
  → BIOS boot sector / UEFI EFI application
  → Boot Loader
  → OS kernel entry
  → 内核初始化中断、内存、设备与调度
  → 第一个用户进程
```

每个箭头都是一个接口：入口地址、寄存器含义、内存布局和已初始化设备必须有明确约定。

## 15. RISC-V：OpenSBI 怎样连接固件与内核

### 15.1 三个特权级与两次 `ecall`

典型 RISC-V 系统有三种特权级：

- M-mode（Machine）：最高权限，处理平台最底层控制；
- S-mode（Supervisor）：通常运行通用 OS 内核；
- U-mode（User）：运行应用。

同一条 `ecall` 可以跨越不同边界：

```text
U-mode 应用 --ecall--> S-mode 内核      系统调用 ABI
S-mode 内核 --ecall--> M-mode OpenSBI   SBI ABI
```

二者指令助记符相同，但调用者、接收者、参数 ABI 和服务完全不同。把 SBI 称作“RISC-V 的系统调用”只能作为类比，不能把它和应用的 Linux syscall 编号混为一谈。

### 15.2 OpenSBI 的职责

OpenSBI 是开源的 Supervisor Binary Interface 实现，常作为 RISC-V 平台的 M-mode firmware。它通常负责：

- 完成平台和各 hart（硬件线程）的必要初始化；
- 设置 M-mode 陷阱入口与每 hart 的 scratch 区；
- 委托可由 S-mode 处理的异常和中断；
- 启动或协调其他 hart；
- 选择并进入下一阶段的 S-mode payload；
- 在内核运行期间响应 SBI `ecall`。

常见 SBI 扩展包括定时器、跨核中断、远程 fence、hart 状态管理、系统复位以及调试控制台等。具体扩展是否存在，应由内核探测，不能只凭“使用 OpenSBI”假设全部可用。

这使通用内核无需为每块开发板复制一份最高特权级机器控制代码。平台差异由 OpenSBI 的 platform operations 吸收，S-mode 内核面向标准 SBI。

### 15.3 从 `_start` 到 S-mode

阅读 OpenSBI 时，可以先追一条窄路径，而不是从全仓库逐文件阅读：

1. 从 `firmware/fw_base.S` 一类文件中的 `_start` 找入口；
2. 看它如何区分 cold boot 与其他 hart 的 warm boot；
3. 找每 hart scratch、栈和平台操作的建立过程；
4. 追踪 `sbi_init` 一类初始化主线；
5. 找最终设置 `mepc`、`mstatus` 并执行 `mret` 的位置；
6. 再从 S-mode `ecall` 反向追 M-mode trap handler 和扩展分发。

RISC-V 常见启动约定会把 hart id 放在 `a0`、设备树地址放在 `a1`，再把控制权交给下一阶段；精确约定取决于平台和 boot protocol。

OpenSBI 提供不同固件形态来适配上一级/下一级：

- `FW_PAYLOAD`：把下一阶段 payload 一起封装；
- `FW_JUMP`：跳到构建时约定的下一阶段地址；
- `FW_DYNAMIC`：由前一阶段通过动态信息描述下一阶段。

因此，“OpenSBI 就是 boot loader”也不够准确。它可以参与装载和交接，但其不可替代的角色是实现 M-mode 的 SBI 运行期接口。

### 15.4 实验 3：编译并解剖 OpenSBI

这是扩展实验，需要网络、GNU Make 和 `riscv64-linux-gnu-` 交叉工具链。仓库版本演化时，产物名可能略有变化。

```bash
git clone --depth 1 https://github.com/riscv-software-src/opensbi.git /tmp/opensbi
make -C /tmp/opensbi \
  CROSS_COMPILE=riscv64-linux-gnu- \
  PLATFORM=generic

find /tmp/opensbi/build/platform/generic/firmware -maxdepth 1 \
  -type f -name 'fw_*.elf' -print
riscv64-linux-gnu-readelf -h \
  /tmp/opensbi/build/platform/generic/firmware/fw_dynamic.elf
riscv64-linux-gnu-nm -n \
  /tmp/opensbi/build/platform/generic/firmware/fw_dynamic.elf \
  | grep -E '(_start|sbi_init|trap)' | head -n 20
riscv64-linux-gnu-objdump -d \
  /tmp/opensbi/build/platform/generic/firmware/fw_dynamic.elf \
  | sed -n '/<_start>:/,+30p'
```

观察重点不是记住地址，而是回答：

- ELF 入口是否落到 `_start` 附近？
- 第一批指令在使用栈之前做了什么？
- 哪些符号属于通用 SBI，哪些属于 `generic` 平台？
- `mret` 前写了哪些 CSR，它们共同把 CPU 带到哪个特权级和地址？

若系统安装了 `qemu-system-riscv64`，许多发行版可用下面的命令显示内置 OpenSBI banner：

```bash
qemu-system-riscv64 -machine virt -nographic -bios default
```

没有下一阶段内核时它可能在打印平台、ISA、PMP 和 next address 后停住；按 `Ctrl-a x` 退出。输出字段来自当前 QEMU/OpenSBI 版本，应结合构建产物和设备树解释，而不是机械比对固定截图。

## 16. 把本讲所有“接口”放在一张图里

“接口”不是函数名的同义词，而是两侧共同遵守的状态与行为契约。本讲至少出现了五层接口：

| 接口 | 调用/交接双方 | 契约示例 | 若契约不存在会怎样 |
| --- | --- | --- | --- |
| ISA | 软件 ↔ CPU | 指令编码、寄存器、异常语义 | 二进制无法跨实现运行 |
| 系统调用 ABI | 用户程序/libc ↔ 内核 | 编号、参数寄存器、返回值 | 应用生态无法复用 |
| BIOS/UEFI | Boot Loader ↔ PC 固件 | `0x7c00` 或 UEFI protocols | 每个引导器都要适配每块板 |
| Boot protocol | Boot Loader ↔ 内核 | 入口、内存布局、设备树/initrd | 内核不知道启动参数在哪里 |
| SBI | S-mode OS ↔ M-mode firmware | extension ID、参数和错误码 | 内核要内置平台 M-mode 代码 |

再向下，GPIO 控制器的数据手册也是接口；再向上，POSIX 和 libc 也是接口。复杂系统并没有消失，而是被切割成可独立理解、实现和验证的部分。

接口的代价同样明显：一旦广泛部署就很难改变。x86 reset 与 BIOS 留下大量兼容性包袱；SBI 和 UEFI 则尝试用版本化、可探测的扩展减少硬编码。

## 17. 概念辨析与常见误区

### 误区 1：“CPU Reset 就是把内存和寄存器全清零”

Reset 只保证架构/平台文档明确规定的状态。DRAM 内容、通用寄存器或设备状态可能未定义、保持或由不同 reset 域分别控制。固件必须初始化自己依赖的内容。

### 误区 2：“CPU 上电后直接从 `0x7c00` 执行”

`0x7c00` 是 Legacy BIOS 装入引导扇区的交接地址，不是 x86 CPU reset vector。先有固件执行，后有这次跳转。

### 误区 3：“BIOS、Boot Loader 和内核是同一个东西”

它们都是二进制程序，但职责和接口不同。固件建立平台，Boot Loader 定位并装入内核，内核长期管理资源并服务应用。某些平台会合并阶段，逻辑角色仍可区分。

### 误区 4：“UEFI 只是图形化 BIOS”

UEFI 定义了新的可执行格式、设备协议、Boot/Runtime Services 和启动管理方式；漂亮菜单只是表象。

### 误区 5：“系统调用是一种硬件 I/O 指令”

系统调用指令主要触发受控陷阱，把控制权交给高特权级软件。真正的设备访问可能随后由内核通过 MMIO、端口 I/O 或 DMA 完成。

### 误区 6：“MMIO 就是普通 RAM，所以一个指针加 `volatile` 足够”

设备访问还涉及映射属性、访问宽度、顺序、屏障和设备协议。应使用平台/内核提供的 I/O API。

### 误区 7：“中断会在任意半条指令中间跳走”

架构通常提供精确或可恢复的边界，使处理程序能够返回。微架构内部可能并行、流水和乱序，但架构状态呈现受规范约束。

### 误区 8：“固件不可写，所以不会中毒”

现代固件通常需要更新，因而物理介质可写。安全性来自授权验证、写保护和信任链，不来自“Firmware”这个名字。

### 误区 9：“数字签名就是加密固件”

签名主要验证来源和完整性，不要求隐藏固件内容；加密解决机密性。HTTPS 保护传输，设备端签名验证保护离线映像和镜像源被替换等场景。

### 误区 10：“CIH 把 CPU 烧毁了”

课程所说“破坏硬件”主要指擦写 BIOS 使机器无法启动、恢复需拆机或编程器。它造成硬件级使用后果，但通常不是物理毁坏芯片。

### 误区 11：“OpenSBI 是 RISC-V 版 GRUB”

GRUB 的核心是找到并装入 OS；OpenSBI 的核心是实现 M-mode SBI，并把 S-mode 环境交给下一阶段。某些固件形态可携带 payload，但两者接口位置不同。

### 误区 12：“硬件不知道 OS，所以 OS 没有特殊权限”

硬件不理解“OS”这个人类标签，但理解特权级、页表、陷阱向量和 I/O 权限。内核先配置并占有这些机制，因此在行为上拥有特殊权力。

## 18. 机制推导：为什么系统最终长成这样

可以从需求逐步推导整条启动链，而不是背名词：

1. CPU 必须有确定起点，所以需要 Reset 状态和 reset vector；
2. Reset 时 RAM/设备尚未就绪，所以入口必须连到预置的非易失代码；
3. 不同主板初始化不同，所以需要平台固件；
4. 固件空间和职责有限，所以把复杂 OS 装载交给下一级；
5. 下一级必须能跨平台，因而需要 BIOS、UEFI、SBI 和 boot protocol；
6. 固件可更新才能修 Bug，但可写又带来攻击面，所以需要签名、写保护和恢复；
7. OS 接管后必须从死循环中夺回 CPU，所以需要定时器、中断、特权级和陷阱返回；
8. OS 必须影响外部世界，所以需要设备寄存器、MMIO、DMA 和驱动。

这条推导也说明边界和代价：

- 固定接口带来兼容性，也积累历史包袱；
- 更丰富的固件能支持更多设备，也增加代码量和漏洞面；
- 把底层服务留在固件能提高可移植性，也增加一次特权切换和跨层调试难度；
- 允许更新提高可维护性，也要求维护一条长期可信的密钥与供应链。

## 19. 本讲小结

本讲最值得带走的不是某个 reset 地址，而是一条统一解释：

> 硬件是从 CPU Reset 开始、不断执行指令并响应外部事件的状态机。

固件是 Reset 后最先取得控制权的普通二进制程序。它建立内存和设备环境，再按 BIOS/UEFI 或平台协议把下一阶段放入内存。Boot Loader 继续装入内核；内核配置中断、I/O、页表和特权机制，把应用轮流放到 CPU 上执行。

从硬件看，这条链上从未出现“现在开始运行操作系统”的魔法开关，只有一次次可精确描述的状态迁移和控制权交接。

GPIO 说明一条 store 可以改变现实世界；定时器中断说明死循环并不必然垄断处理器；CIH 说明最早执行的可写代码必须成为信任边界；OpenSBI 则说明一个设计良好的接口可以把平台 M-mode 细节与 S-mode 内核隔离开。

## 20. 思考题与实践题

1. 若 CPU 只有普通指令和 `jmp`，没有中断、异常和特权级，能否实现能抵抗恶意应用的抢占式 OS？为什么？
2. 在实验 1 中，若中断处理程序允许嵌套中断，状态里还必须增加什么，单个 `saved_pc` 为什么不够？
3. DMA 会在 CPU 不执行 store 时修改 RAM。它破坏了哪个简化状态机假设？OS 和驱动如何得知 DMA 完成？
4. 为什么 GPIO 输出不能只考虑软件值 0/1，还必须考虑引脚复用、电压和电流？
5. Reset 后若 DRAM 尚不可用，固件最早的 C 函数为何不能理所当然地使用普通栈？
6. 把 `/tmp/bootloop.img` 的签名改坏后，对比 QEMU 日志。CPU 行为变了吗，还是固件的选择变了？
7. `hbreak *0x7c00` 与 `awatch *(short *)0x7c00` 分别回答什么问题？
8. UEFI `ExitBootServices()` 为什么是清晰的所有权交接点？如果 OS 之后仍随意调用 Boot Services，会有什么一致性问题？
9. 为什么固件更新同时需要设备端签名验证和可靠的掉电恢复？两者分别防什么？
10. 比较 U-mode `ecall` 与 S-mode `ecall`：哪些硬件动作相似，哪些软件 ABI 完全不同？

12. 如果用 QEMU `-kernel` 绕过通常 Boot Loader，这是否意味着 Reset 和固件概念消失了？请区分“模拟器预装内存”与“guest CPU 可见启动状态”。
