>
> 前一讲：[操作系统概述](01-os-overview.md) · 后一讲：[硬件视角的操作系统](03-hardware-view.md)
>
> 建议环境：x86-64 Linux，安装 GCC/Clang、GNU Binutils、GDB 与 `strace`。
> 本讲所有命令默认从仓库根目录执行；不同发行版的路径、地址和系统调用细节可能略有差异。

## 0. 本讲定位：先站到应用一侧

第 1 讲从历史和整体结构出发，把操作系统放在“软件—硬件”之间：
它让程序更容易运行，让多个程序共享处理器、内存和设备，并为应用提供稳定抽象。
但这句话还留下了一个最基本的问题：**这里的“程序”到底是什么？**

如果把程序只理解成一份 C 源代码，便解释不了三个事实：

- CPU 不认识 C，只会取出并执行机器指令；
- `main` 既不是可执行文件中唯一的函数，也通常不是真正入口；
- 浏览器、编译器、Shell 和一个几十字节的汇编程序，看起来天差地别，却受同一套操作系统管理。

本讲选择应用视角，从最小模型逐层扩展：

```text
C 语句的状态机
    ↓ 解释或保持可观察行为地编译
机器指令的状态机
    ↓ syscall：把控制权交给内核
操作系统对象与 API
    ↓ 组合、封装、协议与工程规模
Applications / Utilities / Daemons
```

这条链的核心结论是：

> 任何应用都是一个不断迁移状态的程序；在需要受保护资源时，它通过系统调用请求操作系统服务。

第 3 讲会把观察方向翻转到硬件侧：
既然应用最终是指令，那么 CPU 复位后究竟如何执行指令、响应中断，又如何允许操作系统存在？

## 1. 学习目标与问题地图

学完本讲，你应该能够：

1. 用“状态、初始状态、状态迁移”精确定义一个顺序程序；
2. 解释为什么 C/C++ 函数调用不是数学函数求值，尤其是副作用与调用次序；
3. 区分解释执行、编译执行，并用“可观察行为等价”说明编译正确性；
4. 说明 ELF、入口 `_start`、`main` 与加载器之间的关系；
5. 在 x86-64 Linux 上写出只使用 `write` 和 `exit` 系统调用的最小程序；
6. 解释 `syscall` 为什么是用户程序与操作系统之间的关键边界；
7. 把 Applications、Utilities 与后台守护程序统一理解为“计算 + OS API”；
8. 使用 `file`、`readelf`、`objdump`、`gdb` 和 `strace` 选择性地观察二进制；
9. 根据一段系统调用轨迹，推断程序与文件、进程、内存和设备的交互；
10. 分清语言语义、编译器、libc、系统调用、内核与硬件各自负责什么。

可以把全讲的问题压缩成四问：

```text
程序怎样前进一步？        —— 状态迁移
源代码怎样变成机器能运行？ —— 解释或编译
程序怎样越过自身状态边界？ —— 系统调用
复杂应用怎样由此搭起来？   —— 对象、API、协议和工具组合
```

## 2. 程序首先是一个状态机

### 2.1 一个可操作的操作系统定义

OSTEP 给出的直观定义是：操作系统是一组让程序更容易运行的软件，
它允许多个程序看似同时运行、共享内存、与设备交互。
这个定义的主语其实是“程序”。
如果我们不能精确回答程序在某一刻处于什么状态、下一步会发生什么，
“让程序运行”也只是一句模糊口号。

操作系统课因此也可以看成一门入门的形式语义课：
在选定的抽象层上，每一个 bit、每一步迁移都应有确定含义。
这不等于所有现实 C 程序都容易分析；未定义行为、并发和外部输入会增加困难。
它只强调：**先选定规则，再依规则机械推演，不能靠“代码看起来会这样”猜测。**

### 2.2 从 C 降低到 SimpleC

真实 C 语句常把很多动作压在一行里：

```c
answer = f(a++) + g(*p ? x : y);
```

其中可能包含读内存、写内存、条件选择、两次函数调用和整数运算。
为了暴露迁移过程，可以把它改写成“每行只做一件小事”的 SimpleC：

```c
int old_a = a;
a = a + 1;
int cond = *p;
int arg_g;
if (cond) {
    arg_g = x;
} else {
    arg_g = y;
}
int left = f(old_a);
int right = g(arg_g);
answer = left + right;
```

这只是教学示意，并不是对任意 C 表达式都可随意采用的等价改写。
C 对某些子表达式的求值顺序不作保证；若改写时擅自固定顺序，
遇到互相冲突的副作用甚至未定义行为，就可能改变语义。
成熟工具如 C Intermediate Language（CIL）会按语言规则完成这种 lowering。

一旦每条语句足够简单，解释器的主循环就很朴素：

```c
while (1) {
    Statement stmt = fetch_statement();
    decode_and_execute(stmt);
}
```

PicoC 是小型 C 解释器的代表。
课程并不要求先实现完整解释器；把程序改写得足够简单，
再用 GDB 单步并观察变量，就已经是在人工执行这段循环：
取出当前语句、理解它、修改状态、移动到下一条语句。

### 2.3 状态、初始状态与迁移

对这个简化的顺序语言，可以把状态写成：

\[
S = (G, [F_0, F_1, \ldots, F_k])
\]

其中：

- `G` 是全局状态，包括全局变量；完整模型还要包括堆与运行时对象；
- `F_i` 是一个调用栈帧，保存函数身份、参数、局部变量和该帧自己的程序位置；
- `F_k` 是当前正在执行的栈帧；
- 外部文件、终端或网络不直接塞进进程内状态，而以 API 调用及其返回值连接。

初始状态可以抽象为：

```text
globals = 各全局变量规定的初值
frames  = [ StackFrame(main, argc, argv, PC=0) ]
```

执行普通语句时，解释器读取顶层栈帧 `frames[-1]` 的 PC，
计算并更新局部变量、全局变量或堆，再推进这个栈帧的 PC。

这里有一个精细但重要的点：
不应把函数程序的状态粗暴写成“变量 + 一个调用栈 + 一个全局 PC”。
每个尚未返回的调用都有自己的**继续位置**，它属于相应栈帧。
例如 `main` 调用 `f` 后，`main` 必须记住“等 `f` 返回后从哪里继续”，
而 `f` 又可能调用 `g` 并保存另一处继续位置。

### 2.4 函数调用是一组机械状态迁移

假设当前 SimpleC 语句是：

```c
y = f(x);
```

函数调用可以拆成以下机械步骤：

1. 在当前栈帧中保存返回后要继续的位置；
2. 创建 `f` 的新栈帧，绑定形参 `x`，把其 PC 指向函数开头；
3. 把新栈帧压到栈顶；
4. 后续迁移都发生在 `f` 的栈帧中；
5. `f` 执行 `return v` 时弹出自身栈帧；
6. 把 `v` 写入调用者等待结果的位置，并从保存的继续位置运行。

许多指令集提供 `call`/`ret` 一类指令来协助保存返回地址，
但高级语言栈帧的布局、参数传递和寄存器保存还由 ABI 与编译器约定。
“有 `call` 指令”并不意味着硬件理解 C 函数。

### 2.5 为什么函数不是数学里的函数

数学函数只关心输入到输出的映射，`f(x) + g(y)` 先算哪边通常没有意义。
C 函数则可能修改全局变量、写终端、更新堆或调用系统 API，因而具有副作用。

汉诺塔是很好的例子：

```c
void hanoi(int n, char from, char via, char to) {
    if (n == 0) return;
    hanoi(n - 1, from, to, via);
    printf("%c -> %c\n", from, to);
    hanoi(n - 1, via, from, to);
}
```

三步的先后次序就是算法含义的一部分。
交换两次递归调用，或把 `printf` 移到别处，输出的移动序列就不同。
相反，若递归 Fibonacci 只返回整数且没有副作用，
先计算 `f(n-1)` 还是 `f(n-2)` 不影响数学结果，尽管运行轨迹仍不同。

原讲义中的互相递归 `f`/`g` 是“终极考题”：
真正困难的不是把递归公式读一遍，
而是忠实维护每一个栈帧的参数、局部结果与继续位置，并输出完整调用序列。
状态机定义把“灵感题”变成了“记账题”。

还要留意 C 的规则：

```c
return f(n - 1) + f(n - 2);
```

C 并不普遍保证 `+` 左操作数先于右操作数求值。
若两次调用只有返回值，结果或许一样；若它们写同一个外部状态，
具体先后就可能可观察；若周围表达式还包含对同一标量对象未排序的冲突访问，
甚至可能触发未定义行为。
不要把某个编译器当前常见的自然顺序误认为语言承诺。

### 2.6 实验一：把程序真的当作“一步一步”的机器

仓库已有一个刻意显式化 PC 的模型：
[state_machine.c](../../examples/state_machine.c)。
先编译运行：

```bash
cc -std=c17 -Wall -Wextra -Wpedantic -O0 -g \
  examples/state_machine.c -o /tmp/state-machine
/tmp/state-machine
```

你会看到两个任务交替发生迁移，典型输出开头类似：

```text
tick=0 run=A before(pc=0, acc=0) -> after(pc=1, acc=1)
tick=1 run=B before(pc=0, acc=0) -> after(pc=1, acc=1)
tick=2 run=A before(pc=1, acc=1) -> after(pc=2, acc=2)
```

这里的 `Task` 就是被压平后的状态：`pc` 指明下一步，`acc` 是数据，
`step()` 只做一次迁移。外层循环轮流选择任务，已经展示了调度的最小直觉：
只要每个任务的继续状态保存完整，它就可以暂停并稍后恢复。

再用 GDB 停在一次迁移前：

```bash
gdb -q /tmp/state-machine
(gdb) break step
(gdb) run
(gdb) display task->pc
(gdb) display task->acc
(gdb) next
(gdb) continue
```

观察重点不是记住 GDB 命令，而是验证预测：

- 每次进入 `step`，只选中了一个任务；
- `switch` 的分支由该任务自己的 `pc` 决定；
- 另一个任务的状态在本次迁移中不变；
- 所有任务最终都到达 `finished=true`。

真实 C 程序的 PC 通常在机器寄存器中，调用栈帧也由 ABI 组织，
所以我们看不到如此整齐的 `Task.pc` 字段；抽象关系却相同。

## 3. 解释与编译：两种执行路径，一个等价要求

### 3.1 编译后仍是状态机

解释器直接读取高级语言语句并迁移语言状态。
编译器则先把程序翻译成机器指令，随后 CPU 迁移硬件状态。
对于一个教学用 RISC-V 模拟器，状态可以近似写成：

```c
struct CPUState {
    uint32_t regs[32];
    uint32_t csrs[CSR_COUNT];
    uint8_t *mem;
    uint32_t mem_offset;
    uint32_t mem_size;
};
```

模拟器同样循环执行“取指、译码、执行”。
课程展示的 `mini-rv32ima` 虽然代码很小，
但由于实现了足够的 RISC-V 指令和 M-Mode，甚至能承载无 MMU 的 Linux。
这说明“系统复杂”不意味着最底层模型复杂：
巨大软件栈最终仍落在简单而重复的状态迁移上。

SimpleC 中的一次加法、加载或跳转，通常能降低成少量机器指令；
函数调用则按 ABI 翻译为寄存器传参、保存返回地址、调整栈指针等动作。
两边的状态表示不同，但编译器需要在它们之间维持语义关系。

### 3.2 “编译正确”不是逐行翻译

“编译器把高级语言翻译为低级语言”只描述了输入和输出，
没有说什么结果才算正确。

一个更有力量的定义是：

> 对每个合法输入，源程序与目标程序具有相同的可观察行为。

这里的可观察行为至少包括：

- 是否正常终止，若终止则返回什么状态；
- 对外部 API 的调用序列和参数，例如输出、文件访问；
- 外界提供给程序的输入以及程序对它们的响应；
- 语言标准规定为可观察的其他行为。

这个定义不要求“一行 C 必须对应固定几条汇编”。
编译器可以改变内部表示、合并计算、移动指令甚至删掉整段代码，
只要没有越过语言允许的边界。
这就是著名的 as-if 原则背后的直觉。

原讲义为了凸显外部交互，把等价性说成“相同输入下具有相同 API 调用序列”。
这是极好用的教学模型，但不是全部语言标准的完整形式化定义。
例如性能和普通内部寄存器值一般不属于可观察语义，
`volatile`、原子操作、信号和并发则会扩大需要保留的行为集合。

### 3.3 死代码消除为何合法

假设程序一定终止，某段计算的结果从未参与返回值，也从未影响外部 API，
那么这段计算对外界不可观察，编译器可以执行 Dead Code Elimination（DCE）。

```c
static unsigned long pure_work(unsigned long x) {
    for (int i = 0; i < 1000; i++) {
        x = x * 1664525UL + 1013904223UL;
    }
    return x;
}

int main(void) {
    pure_work(42);  // 返回值没有使用，也没有外部副作用
    return 0;
}
```

在优化开启且编译器证明 `pure_work` 没有可见副作用后，整个调用都可能消失。
若函数改为 `puts("step")`、写 `volatile` 对象或执行系统调用，
这些可观察效果不能随意删除。

“编译器不能把冒泡排序自动改成快速排序”是一个帮助理解的历史说法：
编译器通常只做能可靠证明等价的局部或结构性优化，
不会凭空猜测程序员想解决的高层问题。
AI 代码变换可能更大胆，但同样绕不开验证：
它生成了更快算法，不等于已经证明所有输入上的行为等价。

### 3.4 实验二：亲眼看到无用计算消失

把下面代码保存为 `/tmp/opt.c`：

```c
#include <stdio.h>

static unsigned long pure_work(unsigned long x) {
    for (int i = 0; i < 1000; i++) {
        x = x * 1664525UL + 1013904223UL;
    }
    return x;
}

int main(int argc, char **argv) {
    (void)argv;
    pure_work((unsigned long)argc);  // 结果被直接丢弃
    if (puts("observable") == EOF) {
        return 1;
    }
    return 0;
}
```

生成两份汇编并搜索乘法循环：

```bash
cc -std=c17 -Wall -Wextra -O0 -S /tmp/opt.c -o /tmp/opt-O0.s
cc -std=c17 -Wall -Wextra -O2 -S /tmp/opt.c -o /tmp/opt-O2.s
less /tmp/opt-O0.s
less /tmp/opt-O2.s
```

再编译运行，比较外部可观察结果：

```bash
cc -O0 /tmp/opt.c -o /tmp/opt-O0
cc -O2 /tmp/opt.c -o /tmp/opt-O2
/tmp/opt-O0
/tmp/opt-O2
```

两者都应输出：

```text
observable
```

在常见 GCC/Clang 上，`-O2` 会证明无用计算不影响输出，
从而删除 `pure_work` 及其循环；具体汇编不是标准承诺，所以应以你机器上的结果为准。
`puts` 不能被无条件删除，因为输出是可观察行为。

这个实验同时提示一个边界：
不能通过“某条 C 语句没有对应汇编”断言编译器出错。
必须先问那条语句是否贡献了语言规定的可观察效果。

## 4. 操作系统上的最小程序

### 4.1 从 `_start` 取得第一条用户指令

在通常的 C 开发体验中，我们写的是：

```c
int main(int argc, char **argv) {
    return 0;
}
```

但内核加载 ELF 时需要的是**入口虚拟地址**，并不认识 C 的 `main`。
常规程序入口通常是 C 运行时提供的 `_start`：

```text
内核 execve 并建立初始地址空间、栈和寄存器
                  ↓
ELF 入口 `_start`
                  ↓
运行时解析 argc/argv/envp、完成初始化
                  ↓
调用用户写的 main
                  ↓
处理返回值、清理并请求进程退出
```

动态链接程序还会先经过 ELF 指定的动态加载器。
所以“程序从 `main` 开始”只是 C 程序员视角的便利抽象，
不是操作系统装载协议的事实。

若我们不要标准库和启动文件，可以自己定义 `_start`，
从第一条用户指令开始获得控制权。

### 4.2 程序不能靠普通指令让自己消失

函数 `return` 只是恢复调用者状态。
`_start` 没有普通的 C 调用者；随便执行 `ret` 会从未定义的栈内容取地址，
通常导致故障，而不是“优雅停止”。

无限循环也不是退出：它仍占据一个可运行进程，等待调度。
用户程序更没有权执行关闭整台机器的特权操作。
通常关机工具先经授权请求内核停止进程、刷新存储，
最后由内核借助 ACPI、固件或设备控制接口切断电源。
要结束当前进程，必须请求掌握进程对象的操作系统改变状态。

在 x86-64 Linux 上，最直接的请求是：

```asm
mov $60, %rax       # __NR_exit
mov $0,  %rdi       # status
syscall
```

如果成功，`syscall` 不返回到本程序；内核释放或回收进程资源，
并让等待它的父进程获知退出状态。

### 4.3 实验三：只有两个系统调用的 Hello World

把以下内容保存为 `/tmp/minimal.S`：

```asm
    .section .rodata
message:
    .ascii "hello from _start\n"
    .equ message_len, . - message

    .section .text
    .global _start
_start:
    mov $1, %rax              # x86-64 Linux: __NR_write
    mov $1, %rdi              # fd = STDOUT_FILENO
    lea message(%rip), %rsi   # buf = &message
    mov $message_len, %rdx    # count
    syscall

    test %rax, %rax           # 原始 syscall 失败时返回 -errno
    js write_failed

    mov $60, %rax             # __NR_exit
    xor %rdi, %rdi            # status = 0
    syscall

write_failed:
    mov $60, %rax
    mov $1, %rdi              # status = 1
    syscall
```

汇编、静态链接并运行：

```bash
as --64 /tmp/minimal.S -o /tmp/minimal.o
ld -static -o /tmp/minimal /tmp/minimal.o
/tmp/minimal
printf 'exit status = %d\n' "$?"
```

预期输出是：

```text
hello from _start
exit status = 0
```

确认 ELF 入口确实是 `_start`：

```bash
file /tmp/minimal
readelf -h /tmp/minimal | grep 'Entry point'
nm -n /tmp/minimal | grep ' _start$'
objdump -d /tmp/minimal | less
```

`readelf` 给出入口数值，`nm` 给出 `_start` 的符号地址；
两者应对应。若链接器布局或符号信息不同，以实际 ELF 为准。

最后观察它对内核提出的全部请求：

```bash
strace /tmp/minimal
```

关键轨迹应接近：

```text
execve("/tmp/minimal", ["/tmp/minimal"], ...) = 0
write(1, "hello from _start\n", 18)             = 18
exit(0)                                          = ?
+++ exited with 0 +++
```

注意 `execve` 是运行 `strace` 的进程或其子进程发起、随后成功后映入新程序的；
`minimal` 自己的 `_start` 只发起 `write` 和 `exit`。
这个程序没有 libc、没有 `printf`、没有 `main`，
但它已经是能被 Linux 加载的完整应用。

### 4.4 系统调用 ABI：同一概念，不同指令与寄存器

系统调用不是可移植 C 语言机制，而是操作系统与体系结构共同规定的 ABI。
三种常见架构的“陷入内核”指令是：

| 架构 | 指令 | Linux 系统调用号位置 | 前几个参数位置 |
|---|---|---|---|
| x86-64 | `syscall` | `rax` | `rdi, rsi, rdx, r10, r8, r9` |
| RISC-V | `ecall` | `a7` | `a0` 至 `a5` |
| AArch64 | `svc #0` | `x8` | `x0` 至 `x5` |

表格说明概念，不应代替目标平台 ABI 文档。
同名系统调用的号码、参数约定和可用性都可能不同。
通常应用调用 libc 包装函数，由 libc 负责装入寄存器、执行特殊指令，
并把内核的负错误码转换成 `-1` 与 `errno`。
本节汇编绕过 libc，才需要直接面对原始约定。

### 4.5 为什么 `syscall` 是整门课的关键边界

普通用户指令只能在硬件和内核允许的范围内改变当前程序状态：
计算寄存器、访问已映射内存、跳到自己代码中的地址。
它不能凭空读取任意磁盘块，也不能修改另一个进程的页表。

执行 `syscall` 时，程序主动触发受控的特权级切换：

1. 硬件按照预先配置的入口保存必要用户状态；
2. 控制流进入内核指定的入口，而非应用任选的内核地址；
3. 内核读取系统调用号和参数，检查指针、权限与对象状态；
4. 内核可修改地址空间、文件偏移、进程状态乃至终止进程；
5. 若服务正常返回，内核恢复适当状态，用户程序从 `syscall` 后继续。

原讲义用“全身麻醉”作类比：
程序暂时失去对自己的控制，把权限交给更高特权级的执行者；
回来时可能一切正常，可能得到错误，也可能因 `exit`、信号或致命错误永不返回。

类比帮助建立控制权直觉，但不要误解为内核可以无规则行事。
内核实现受系统调用契约、安全策略和硬件保护约束；
内核 bug 确实可能破坏这些保证，这正是系统软件需要严密验证的原因。

“只有系统调用能主动越过边界”还隐含了“由应用主动请求”这个限定。
缺页、非法指令等同步异常，以及信号、设备中断等异步事件，
也能使控制流离开当前用户指令序列；它们将在硬件视角中进一步展开。

## 5. 操作系统上的应用世界

### 5.1 我们日常感知的是进程，不是抽象的“内核”

用户开机后看到窗口、编辑器、浏览器和终端，
感知到的是操作系统上运行的程序及它们形成的界面。
内核大多在幕后，只在应用通过 API、设备事件或故障边界时显露影响。

讲义把程序分成三组，不是为了制造严格分类，
而是让我们看清一个系统的软件生态：

| 类别 | 典型例子 | 主要作用 | 通常是否直接交互 |
|---|---|---|---|
| Applications | VS Code、Chrome、LibreOffice、GIMP、OBS、VLC | 完成开发、办公、浏览、创作和媒体任务 | 是 |
| Utilities | `cp`、`grep`、Shell、GCC、GDB、`ip`、`ssh`、`curl`、FFmpeg | 操作文本、文件、程序、网络与媒体，供人或脚本组合 | 经常是短命令或被别的程序调用 |
| Daemons / services | `systemd-udevd`、`cron`、`sshd`、D-Bus、`auditd` | 后台响应事件、提供长期服务、维护系统状态 | 通常间接交互 |

类别会重叠：
浏览器也包含后台进程，IDE 会调用编译器和语言服务器，
守护程序也可能附带命令行客户端。
从操作系统角度，它们仍由同样的进程、地址空间、文件描述符和系统调用构成。

### 5.2 Applications：直接面向人的复杂程序

开发类应用包括 VS Code、Cursor、编译器、Node.js、GDB、tmux、Vim 和 htop；
日用应用包括办公套件、图像编辑器、浏览器、录屏和媒体播放器。

它们的源码规模可能达到数百万行，也可能采用多进程架构，
但复杂性主要来自程序内部状态、库、协议和工程抽象。
内核不需要知道“这个进程是一款浏览器”；
它只根据身份与权限处理进程、内存、文件、socket、设备等对象。

### 5.3 Utilities：UNIX 可组合工具箱

Core Utilities 是文本和文件操作的标准工具集合。
常见 Linux 发行版通常提供 GNU Coreutils，如 `ls`、`cp`、`mv`、`cat`、`sort`。
BusyBox 把大量工具收进一个紧凑可执行文件，常见于嵌入式和救援环境；
Toybox 提供另一套简洁实现，并成为 Android 命令行用户空间的重要组成。

工具程序远不止 coreutils：

- Shell 负责启动、连接和控制其他程序；
- Binutils 的 `as`、`ld`、`objdump`、`readelf` 处理目标文件和二进制；
- `apt`/`dpkg` 管理软件包；
- `ip`、`ssh`、`curl` 操作网络；
- FFmpeg、GStreamer 处理媒体；
- 新一代编码 Agent 也可以被理解成更高层的交互式工具入口。

UNIX Philosophy 的力量在于组合：
一个工具不必理解整个任务，只要输入输出接口稳定，
Shell 就能用文件、管道和进程把它们拼起来。
后续课程会专门解释 `fork`、`execve`、文件描述符和管道如何支持这种世界。

### 5.4 后台程序：看不见并不等于不存在

守护进程长期运行，等待定时器、网络请求、硬件热插拔或其他进程消息。
现代 Linux 常由 systemd 启动和监督大量服务，
例如 `systemd-networkd`、`systemd-logind` 和 `systemd-udevd`。

其他典型后台程序包括：

- 系统管理：`cron`、`udisksd`、`unattended-upgrade`；
- 网络与 IPC 服务：`httpd`、`sshd`、D-Bus；
- 安全组件：`auditd`、`firewalld`；
- 图形与媒体：Wayland compositor、PulseAudio、PipeWire，以及使用 Video4Linux 的组件。

“daemon” 不是一种特殊机器代码格式。
它通常只是生命周期更长、启动方式和会话关系不同、
通过日志或 IPC 而非前台终端交互的普通进程。

## 6. 一切应用为何“都是一样的”

### 6.1 ELF 是初始状态的描述

`minimal.S`、`gcc` 和浏览器的功能差异巨大，
但在 Linux 装载边界上，它们都可归结为可执行文件及其依赖。
常见 ELF 文件描述：

- 文件类型、目标架构和 ABI 信息；
- 入口地址；
- 哪些文件片段要映射为可执行、只读或可写内存；
- 指令与初始数据；
- 动态链接器和共享库相关信息；
- 供链接、调试或分析使用的符号与节信息。

因此可以把可执行文件理解成“程序状态机初始状态的一份描述”。
这句话是抽象，不表示 ELF 保存运行中所有寄存器和动态堆；
内核、加载器和运行时会依据文件及执行参数共同构造真正初始状态。

用文本编辑器打开 ELF 看见“乱码”，并不说明文件没有结构，
而是说明工具把二进制字节错误地解释成字符。
选择 `readelf` 后，同一批字节会按 ELF 规范变成文件头、Program Headers 和 Sections。

### 6.2 共同生命周期：`execve` 到 `_exit`

任何普通程序的生命周期都可画成：

```text
某个已有进程调用 execve
          ↓
内核用 ELF 与参数建立新程序的初始状态
          ↓
执行普通指令：计算、分支、读写用户内存
          ↓
通过系统调用管理进程、文件、设备和地址空间
          ↓
调用 exit/_exit/exit_group，或因信号等原因终止
```

常见系统调用族包括：

- 进程：`fork`、`clone`、`execve`、`wait4`、`exit`；
- 文件与设备：`openat`、`close`、`read`、`write`、`ioctl`；
- 内存：`mmap`、`munmap`、`mprotect`、`brk`；
- 进程间通信与网络：`pipe2`、`socket`、`sendto`、`recvfrom`；
- 查询与等待：`statx`、`getdents64`、`poll`、`epoll_wait`。

不同架构或内核版本上的实际名字与组合会变化。
高级库也可能缓存结果、批处理操作或选择另一条系统调用路径。
共同点不是“每个应用调用完全相同序列”，
而是它们都只能通过受控 API 请求内核对象服务。

### 6.3 不同之处在哪里

“任何程序 = `minimal.S` = 状态机”是在底层模型上的同一性，
不能误解成所有程序功能相同或复杂度相同。

浏览器复杂在 HTML/CSS/JavaScript 语义、网络协议、渲染、多进程隔离与大量库；
编译器复杂在词法语法、优化和代码生成；
杀毒软件复杂在文件格式、规则、行为模型与权限集成。
这些高层结构最终都由指令和 API 实现，
但理解它们仍需要选择合适抽象，不能只盯着每一条汇编。

## 7. 二进制逆向：用正确工具屏蔽不关心的细节

### 7.1 从一个存档文件的好奇心说起

原讲义用约 2000 年盗版游戏光盘与《大富翁 4》存档作个人回忆：
光盘里一个名为 “Elf” 的神秘目录（不是 UNIX 的 a.out/ELF 文件格式），
或 `GAME.SAV` 中的字节，可能编码了 CG 解锁进度。
当时面对 `00 00 01 00 ...`，很难知道偏移、字段和校验规则；
但反复修改存档、比较字节差异，就是最朴素的逆向工程。

这则故事承担的论证不是鼓励破解版权内容，
而是说明：**任何复杂文件最终都是有规则的状态表示，困难在于找对观察层次。**
同样的方法可以用于合法分析自己的程序、开放格式、崩溃转储和兼容性问题。

### 7.2 工具体系比“肉眼读二进制”重要

面对 ELF，可以分层提问：

| 想知道什么 | 合适工具 | 屏蔽了什么细节 |
|---|---|---|
| 文件大类与架构 | `file` | 原始魔数和头字段解析 |
| 装载入口与段 | `readelf -h -l` | ELF 二进制布局 |
| 依赖哪些共享库 | `readelf -d`、`ldd` | 动态节与加载器协议的部分细节 |
| 有哪些符号 | `nm`、`readelf -s` | 符号表编码 |
| 机器指令是什么 | `objdump -d` | 指令字节解码 |
| 有哪些可见字符串 | `strings` | 非文本区域 |
| 运行到某刻的状态 | `gdb` | 不关心路径的静态细节 |
| 如何请求内核服务 | `strace` | 程序内部绝大多数计算 |

工具可以自由组合和复用。
AI 也能帮助生成命令、解释字段和编写小型分析器，
但应让实际文件、手册和可重复实验验证结论。
“Curiosity is all you need” 的落点不是盲猜，
而是把好奇心变成一个个可检验问题。

### 7.3 逆向并不要求一次理解全部

分析 `minimal` 时，我们可以只看入口附近几条指令；
分析存档时，可以只比较改变一个游戏选项前后的字节；
分析大型程序时，可以先跟踪某个文件名或一次系统调用。

这正是抽象与工具的意义：
主动屏蔽暂时不关心的部分，把问题压缩到人脑能验证的范围。
现代 Agent 降低了组合工具和编写临时脚本的成本，
但“观察什么、证据如何支持结论”仍由分析者负责。

## 8. `strace`：打开程序的执行边界

### 8.1 Trace 到底观察什么

trace 是沿着某个对象从开始到结束记录事件；
例如 `traceroute` 试图展示数据包到目的地所经过的网络跳点。
`strace` 主要跟踪进程进入/离开 Linux 系统调用时的边界事件，
把系统调用号、参数与返回值解码为较可读文本。

它让我们直接检查本讲的中心命题：

```text
应用执行 = 大量看不见的用户态计算 + 一串可观察的系统调用
```

但 `strace` 不是逐条指令追踪器。
两个系统调用之间执行了十条还是十亿条普通指令，默认轨迹都不显示。
若要观察函数、指令或性能事件，应选择 GDB、`perf`、eBPF 等其他工具。

### 8.2 实验四：比较最小程序和动态链接程序

先跟踪上一节的静态最小程序：

```bash
strace -o /tmp/minimal.trace /tmp/minimal
cat /tmp/minimal.trace
```

再跟踪系统自带的 `echo`：

```bash
strace -o /tmp/echo.trace /bin/echo hello
less /tmp/echo.trace
```

你通常会在 `/bin/echo` 的轨迹中看到更多调用，例如：

- `openat`/`read`：动态加载器或 locale 代码读取文件；
- `mmap`/`mprotect`：映射共享库并设置内存权限；
- `write`：最终向标准输出写文本；
- `exit_group`：结束整个线程组。

这并不意味着“输出 hello 必须调用这么多内核服务”。
最小程序已证明核心只需一次 `write` 和一次 `exit`；
额外调用来自动态链接、libc 初始化、国际化等通用功能。

可以只保留最关心的调用：

```bash
strace -e trace=write,exit,exit_group /bin/echo hello
strace -c /bin/echo hello
```

第一条做事件过滤，第二条给调用次数与时间统计。
统计受追踪开销和调度影响，适合建立概貌，不应直接当精密基准。

### 8.3 实验五：为什么跟踪 GCC 要加 `-f`

准备一个最小源文件 `/tmp/a.c`：

```c
#include <stdio.h>

int main(void) {
    if (puts("compiled") == EOF) {
        return 1;
    }
    return 0;
}
```

跟踪编译器创建进程和访问文件的行为：

```bash
strace -f -o /tmp/gcc.trace \
  -e trace=process,file \
  cc /tmp/a.c -o /tmp/a.out
less /tmp/gcc.trace
```

`-f` 表示继续跟踪 `fork`/`clone`/`vfork` 产生的子进程。
常见编译驱动会启动预处理/编译、汇编和链接相关程序，
具体是否合并阶段取决于工具链版本。

在轨迹里寻找：

- `execve`：编译驱动启动了哪些阶段；
- `openat`：搜索了哪些头文件、启动对象、库和配置；
- 失败的 `ENOENT`：路径搜索的候选，不一定是故障；
- 最终输出文件如何创建和改名。

这也是 UNIX Philosophy 的现场证据：
一个看似单独的 `gcc` 命令，背后可以协调多个专门工具。
轨迹是普通文本，可以继续交给 `grep`、编辑器或脚本处理，例如：

```bash
grep 'execve(' /tmp/gcc.trace
vim /tmp/gcc.trace
```

Vim 中的 `:%!grep execve` 还能让外部工具过滤当前缓冲区；
重点是“工具输出仍能成为另一个工具的输入”。

### 8.4 图形程序也只是进程与协议

原讲义以 `xedit` 为图形程序代表：

```bash
strace -f -o /tmp/xedit.trace xedit
```

在 X11 模型中，应用并不必亲自操纵显卡每个像素，
而是通过 Unix domain socket 或网络连接向 X server 发送协议消息。
经 SSH X11 forwarding 运行时，这些消息还可能经 SSH 转发到宿主机显示服务。

所以 GUI 没有打破“计算 + 系统调用”：
绘图命令先成为进程间通信数据，服务端再借助设备和内核接口显示。
Wayland 的协议和职责划分不同，但同样依赖进程、共享内存、socket 和设备对象。

无图形环境时无需强行安装 `xedit`；
可以跟踪已有 GUI 程序，或用 `strace -e trace=network` 观察一个本地客户端。
某些沙箱或安全策略会禁止 ptrace，此时 `strace` 可能报权限错误。

### 8.5 阅读轨迹的五条纪律

1. **先看返回值。** `openat(...) = -1 ENOENT` 是失败，不能只看调用名。
2. **区分搜索与故障。** 程序尝试多个候选路径，前几个失败可能完全正常。
3. **注意进程编号。** `-f` 输出交错时，不同 PID 的事件属于不同状态机。
4. **不要把库函数名当系统调用。** `printf` 可能最终变成 `write`，也可能先缓冲很久。
5. **不要把“没看到”当“没发生”。** vDSO、用户态缓存、普通内存访问不会都出现在 `strace` 中。

## 9. 从系统调用反推复杂应用

### 9.1 窗口系统：能画一点，就能组合整个界面

窗口管理器或 compositor 需要：

- 通过设备节点、`ioctl` 或 `mmap` 与显示/GPU 栈交互；
- 接收键盘、鼠标和触摸事件；
- 通过 socket 或共享内存与客户端通信；
- 管理窗口层级、焦点、合成与帧时序。

“能画一个点，理论上就能画任何东西”强调最小能力的可组合性，
不表示现代图形栈真的逐点系统调用。
实际系统用批量命令、共享缓冲区和 GPU 加速降低边界切换成本。

### 9.2 任务管理器：读取操作系统暴露的进程对象

任务管理器不需要魔法窥视 CPU。
在 Linux 上，它可以读取 `/proc` 中的目录和文件，
使用 `getdents64`、`openat`、`read` 获取进程、线程、内存和统计信息。
也可以通过 netlink 或其他内核接口接收事件。

你在 `strace htop` 中看到的往往就是周期性查询、终端 I/O 与等待。
高层“CPU 占用率”来自两次累计计数之差，
而不是内核直接交付一张漂亮百分比表格。

### 9.3 杀毒与安全软件：扫描、观察和拦截

静态扫描器用 `openat`/`read` 读取文件并分析格式与特征；
主动防御可能借助 `ptrace`、审计、fanotify、eBPF 或内核安全框架观察行为。

权限边界在这里尤其重要：
普通进程不能任意跟踪其他用户或高权限进程。
安全软件若需要强能力，必须由系统策略明确授权；
能力越强，漏洞造成的破坏面也越大。

### 9.4 操作系统提供的是舒适的对象与 API

如果每个应用都要自行理解磁盘扇区、网卡队列和显存时序，
软件几乎无法移植或并存。
操作系统把资源包装成进程、地址空间、文件描述符、文件、socket 和设备等对象，
再用系统调用规定操作方式。

“舒适”包含多层含义：

- 稳定：应用不必随每块硬件改变全部代码；
- 共享：多个程序可以复用 CPU、内存与设备；
- 隔离：对象和权限限制错误传播；
- 可组合：统一接口让 Shell、库和服务共同工作；
- 可观察：`/proc`、日志、trace 等机制帮助诊断。

后续一学期的课程，就是依次打开这些对象和 API：
它们为什么出现、最小模型是什么、真实系统如何实现、代价与边界在哪里。

## 10. 概念辨析与常见误区

### 10.1 语言语义、编译器、libc、系统调用、内核、硬件

| 层次 | 负责什么 | 本讲例子 |
|---|---|---|
| C 语言语义 | 定义表达式、对象、函数调用及可观察行为 | `+` 的操作数顺序未普遍固定 |
| 编译器 | 在保持语义的前提下生成目标代码 | DCE、寄存器分配、生成 ABI 调用序列 |
| C 运行时/libc | 提供 `_start`、`printf`、系统调用包装等用户态设施 | 缓冲输出、设置 `errno` |
| 系统调用 ABI | 规定用户态请求内核的号码、寄存器和返回约定 | x86-64 `syscall` |
| 内核 | 校验请求并管理进程、内存、文件与设备对象 | 实现 `write`、`mmap`、`execve` |
| 硬件 | 执行指令、提供特权级和受控陷入机制 | 执行 `syscall`，跳到配置好的入口 |

遇到现象时先定位层次。
例如 `printf("x")` 没有立即出现 `write`，可能是 libc 缓冲；
`write` 返回 `EPIPE` 是内核对象状态；
某条加法被删除可能是编译优化；
用越界数组让结果“偶尔正确”则可能已落入 C 未定义行为。

### 10.2 高频误区

- **“程序就是源代码。”** 源代码是表示之一；运行时程序还包括寄存器、内存、栈帧和外部交互。
- **“函数只由参数决定返回值。”** 有副作用的 C 函数还读取或修改全局、堆、文件和设备状态。
- **“一行 C 对应一条机器指令。”** lowering 与优化都可能一对多、多对一或完全删除。
- **“编译优化可以任意改程序。”** 只能在源语言允许范围内保持可观察行为。
- **“程序从 `main` 开始。”** ELF 从入口开始，常见入口是运行时 `_start`。
- **“`exit()` 就是一条普通函数返回。”** libc 的 `exit` 最终请求内核终止进程，并可能先做用户态清理。
- **“系统调用就是普通库函数。”** 函数调用通常不切换特权级；系统调用通过受控入口交权给内核。
- **“ELF 是乱码。”** 字节有结构，只是文本编辑器采用了错误解释方式。
- **“daemon 是特殊类型的可执行文件。”** 它主要是运行方式和职责不同的普通进程。
- **“`strace` 显示了程序所做的一切。”** 它主要显示系统调用边界，看不到全部用户态计算。
- **“系统调用越多，程序必然越慢。”** 次数只是线索；数据量、缓存、等待、调度与实现都影响性能。
- **“所有应用调用相同 API，所以都很简单。”** 底层接口统一不等于高层协议、算法和工程复杂度消失。

## 11. 本讲小结

本讲建立了从源代码到真实应用的一条连续解释链：

1. 程序可以定义成状态、初始状态和迁移规则；
2. 函数调用通过栈帧和继续位置机械实现，副作用使调用次序可观察；
3. 解释器直接迁移语言状态，编译器生成行为等价的机器状态机；
4. ELF 描述可加载映像与入口，`_start` 才是常见的第一段用户代码；
5. 用户程序通过 `syscall`/`ecall`/`svc` 把控制权交给内核；
6. 最小汇编、编译器、浏览器和守护进程都可还原为计算与系统调用；
7. `readelf`、`objdump`、GDB 和 `strace` 让我们按问题选择观察层次；
8. 操作系统的核心价值，是提供舒适、可共享、受保护、可组合的对象与 API。

最值得带走的不是某个系统调用号，而是一种分析方法：

```text
先写出状态机模型
→ 明确边界上什么可观察
→ 选择能观察该边界的工具
→ 用实验验证预测
→ 再扩大到真实系统
```

## 12. 思考题与延伸练习

原讲义没有指定书本阅读材料，而是建议主动建立命令行工具地图。
下面的练习可以与 AI 对话配合，但每个结论都应回到手册和本机实验验证。

1. 递归函数的每个栈帧为什么必须保存自己的继续位置？只保存一个全局 PC 会发生什么？
2. 如果两个函数都向同一文件写数据，交换调用顺序为什么可能改变语义？
3. “相同 API 调用序列”在哪些情况下不足以完整定义程序等价？考虑终止、信号与并发。
4. 修改 `/tmp/minimal.S`，把标准输出描述符从 `1` 改为无效值。为什么必须检查 `rax` 的符号？
5. 比较 `readelf -S` 和 `readelf -l`：节表与装载所需的段表分别服务于谁？
6. 用 `strace -e trace=%file` 跟踪 `ls`。哪些失败的路径探测是正常的？
7. 用 `strace -f -e trace=process` 跟踪一条 Shell 管道。你能找出每个 `execve` 对应哪个工具吗？
8. 为什么 `printf` 调用次数不一定等于 `write` 系统调用次数？终端和普通文件重定向时有何不同？
9. GUI 应用若不直接控制显卡，窗口内容如何跨进程到达显示服务？试列出可能的 OS 对象。
10. `strace` 会显著增加某些程序的运行时间。为什么观测工具本身会扰动被观测系统？
11. 浏览 GDB 手册中的 Reverse Execution 与 TUI。它们分别屏蔽了调试中的哪类复杂性？
12. 任选一个 GNU Coreutils 命令，在 BusyBox 或 Toybox 中找到简化实现；比较它们的功能与依赖。

## 13. 与下一讲的衔接：硬件为什么允许内核接管

本讲站在应用侧，把 `syscall` 看成“把整个状态机交给操作系统”的特殊动作。
但还有一半没有解释：

- CPU 怎样区分用户态和内核态？
- 应用为什么不能选择任意内核跳转地址？
- 一个死循环为何没有让整个系统永远停住？
- 计算机上电时还没有进程，第一条指令从哪里来？
- 固件怎样把机器交给操作系统？

第 3 讲将从硬件状态机出发，补上寄存器、内存、外部设备、Reset、异常/中断和固件。
届时会看到：硬件并不知道“操作系统”这个概念；
它只是忠实执行指令和响应事件，而恰当的硬件机制让内核能够建立今天的应用世界。
