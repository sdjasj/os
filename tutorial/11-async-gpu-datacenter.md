# 第 11 章：异步、事件循环、GPU 与数据中心

> 对应讲义：[第 19 讲](../sources/notes/lect19.md)、[第 20 讲](../sources/notes/lect20.md)、[第 21 讲](../sources/notes/lect21.md)，配套实验：[epoll_timer.c](../examples/epoll_timer.c)

本章把并发视野从 pthread 扩展到用户态协程、事件循环、SIMD/SIMT 和数据中心。一条共同主线贯穿其中：先理解 workload，再选择能把调度与数据搬运成本摊薄的抽象。

## 11.1 Fast path 与 slow path

高性能系统常把常见、简单情况留在用户态快速完成，把少见、昂贵情况交给通用机制：

- mutex 无竞争时原子操作，竞争时 futex 睡眠；
- malloc 从线程本地 freelist 分配，耗尽后访问中央 arena；
- 网络数据先走缓存/批处理，异常和拥塞走复杂控制路径；
- JIT 把热点编译成本机代码，冷路径继续解释。

优化不是“把每一行都写得更低级”，而是让高频路径短、局部、可预测，并保留正确 slow path。

## 11.2 一个连接一个线程的代价

内核线程提供自然的阻塞式控制流，但每条执行流都要占用：

- 用户栈的虚拟地址与已触碰物理页；
- 内核栈和调度元数据；
- 上下文切换、TLB/缓存扰动；
- 锁和共享调度队列开销。

几十或几百线程通常很合理；十万 mostly-idle 连接若各占一线程，就会遇到 C10K 类问题。关键不是线程“坏”，而是 workload 主要在等待 I/O，昂贵栈与调度不匹配。

## 11.3 协程：用户空间可暂停函数

栈式协程保存寄存器和栈指针，在用户态切换；语言运行时可把大量 goroutine/fiber 映射到少量内核线程。优势是：

- 保留直观的顺序代码；
- 创建和切换通常比内核线程轻；
- 运行时知道哪些任务在等待，可进行 work stealing。

但若协程在内核线程上执行真正阻塞调用，整个承载线程都会停下；运行时需要非阻塞 I/O、专门阻塞线程池或系统调用集成。协程也没有消除数据竞争，多个协程并行运行时仍需同步。

Go 的 channel、C++ coroutine、Rust async task 和 Java virtual thread 各自选择了不同的栈、调度与 I/O 整合策略，不能只看语法判断成本。

## 11.4 事件循环：一个线程等待很多对象

把 fd 设为非阻塞后，程序不在某个连接上睡死，而是让内核报告“哪些对象现在可继续”。Linux 常用 `epoll`：

```c
epoll_ctl(epoll_fd, EPOLL_CTL_ADD, source_fd, &interest);
int n = epoll_wait(epoll_fd, ready, capacity, timeout);
for (int i = 0; i < n; i++)
  advance_state_machine(ready[i]);
```

运行 [epoll_timer.c](../examples/epoll_timer.c)：

```bash
./examples/epoll_timer
```

一个线程同时响应两个不同周期的 `timerfd`。网络 socket、管道、`eventfd`、`signalfd` 也能进入同一事件循环。每个请求的“局部变量与下一步”不再天然放在线程栈中，而是显式状态机或由 async/await 编译器生成的状态对象。

## 11.5 Level-triggered 与 edge-triggered

- Level-triggered：只要 fd 仍可读，后续 `epoll_wait` 还会报告；较易写。
- Edge-triggered：只在状态从不可读变为可读等边沿报告；需一直读到 `EAGAIN`，否则可能再也收不到提醒。

非阻塞读写都要循环处理 short I/O、`EINTR`、`EAGAIN` 和关闭。事件循环中的某个回调若执行长 CPU 任务，会阻塞所有连接；应切片、交给工作线程/GPU，或建立优先级与超时。

## 11.6 回调、Promise 与 async/await

异步逻辑本质上仍是计算图：I/O 完成、定时器、取消和依赖共同决定节点何时 ready。

```text
callback：把“下一步”作为函数传入
Promise/Future：把未来结果变成对象
async/await：编译器把顺序语法改写成可暂停状态机
```

async/await 改善局部可读性，不会自动解决背压、取消传播、资源关闭或并发上限。一个健壮请求必须明确 deadline，并让下游在取消后停止无用工作。

## 11.7 CPU 如何榨取并行

现代 CPU 通过流水线、乱序执行、分支预测和多个执行单元挖掘 **ILP**（指令级并行）。只要指令间无数据依赖，单个核心每周期就可能完成多条微操作。

功耗墙后，单核频率增长放缓，处理器增加核心并发展 SIMD：一条指令处理向量中的多个元素。SIMD 高效要求连续数据、规则控制流和合适对齐；分支与散乱内存访问会降低利用率。

```text
标量：  a0+b0
SIMD： [a0 a1 a2 a3] + [b0 b1 b2 b3]
```

编译器可自动向量化简单循环，先用 `-fopt-info-vec`/反汇编验证，再考虑 intrinsics。

## 11.8 GPU 与 SIMT

GPU 从固定图形管线演化为可编程 shader，再成为 GPGPU。SIMT 让大量线程执行同一 kernel：硬件把一组线程（warp/wavefront）成束调度。

优势来自海量规则并行和隐藏内存延迟；限制包括：

- 同一 warp 分支分歧会串行执行不同路径；
- 全局内存访问要尽量 coalesced；
- CPU↔GPU 数据搬运可能吞掉计算收益；
- kernel 启动和同步有固定成本；
- 显存容量与通信拓扑决定多卡扩展。

Mandelbrot 每个像素独立，天然适合 CPU 线程池和 GPU 对照。复杂链表遍历则通常局部性差、分支多，未必适合 GPU。

## 11.9 一个 Token 的系统旅程

用户向 LLM 发送请求，路径可能包括：

```text
浏览器/客户端
  → DNS/TLS/HTTP
  → 边缘代理、负载均衡、API 网关
  → 鉴权、限流、排队
  → 模型服务调度器
  → 分词与输入准备
  → 多 GPU 张量/流水线并行
  → 逐 Token 解码与流式返回
```

每层都在做调度、隔离、缓存与故障处理。数据中心不是一台“大电脑”：网络会延迟或分区，机器会部分失败，时钟不完全一致，重试还可能重复执行副作用。接口常因此设计成幂等、带请求 ID、deadline 和可观测 trace。

CAP 不是“随便选两个”的产品菜单。发生网络分区时，一个复制数据系统必须在一致响应与继续接受可能冲突的操作之间作取舍，具体语义还取决于读写协议和故障模型。

## 11.10 从线程模型到服务模型

大规模服务常组合多种机制：

```text
每核一个事件循环
   ├── 管理大量网络连接
   ├── 把 CPU 任务交给有界工作池
   ├── 把矩阵任务批处理后提交 GPU
   └── 用异步 RPC 等待其他服务
```

“有界”至关重要。无限队列只会把过载变成长尾延迟和内存耗尽；背压、拒绝、降级与负载削峰也是正确性的一部分。

## 11.11 常见误区

- 异步一定比线程快：低并发或 CPU 密集任务可能只增加复杂度。
- `epoll` 返回可读就能一次读完整消息：只表示现在至少能推进，仍需协议缓冲。
- async 函数不会阻塞：内部若调用阻塞 API，执行器线程照样被卡住。
- GPU 核数可与 CPU 核数直接比较：执行模型和单核能力完全不同。
- 批量越大吞吐越高所以总更好：批量也增加排队和首 Token 延迟。
- 重试能解决分布式失败：非幂等副作用会重复，重试风暴还会压垮恢复中的服务。
