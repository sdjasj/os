# 第 10 章：并发 Bug、检测工具与可扩展性

> 对应讲义：[第 17 讲](../sources/notes/lect17.md)、[第 18 讲](../sources/notes/lect18.md)，配套实验：[parallel_sum.c](../examples/parallel_sum.c)

并发程序不仅要在某次运行中得到正确答案，还要对所有允许交错保持安全与进展；性能还必须随 workload 和硬件规模增长。测试、检测与结构化设计缺一不可。

## 10.1 死锁的四个必要条件

经典资源死锁需要同时满足：

1. 互斥使用资源；
2. 持有部分资源并等待更多；
3. 资源不可被强制剥夺；
4. 等待关系形成环。

破坏任一条件就能避免这一类死锁。工程上最常用的是全局锁顺序：给锁建立严格偏序，只允许沿一个方向获取，等待图便不可能成环。

```text
错误：T1 holds A → waits B
      T2 holds B → waits A

规则：永远先拿 min(id)，再拿 max(id)
```

超时只能帮助恢复或报警，并不能把操作自动变得一致；拿到部分资源后超时，还需要可靠回滚。

## 10.2 不只有死锁

- **数据竞争**：没有同步的冲突内存访问；在 C/C++ 中通常是 UB。
- **原子性违反**：逻辑上应一起完成的步骤被其他操作插入。
- **顺序违反**：事件 A 应先于 B，但协议没有建立相应顺序。
- **活锁**：线程不断响应彼此却没有实际进展。
- **饥饿**：系统整体前进，但某个参与者长期得不到资源。

TOCTTOU（检查时与使用时不同）是典型顺序/原子性问题：

```c
if (access(path, W_OK) == 0)
  fd = open(path, O_WRONLY); // 两次调用之间 path 可被替换
```

安全做法是直接 `open`，再对得到的 fd 检查；或使用 `openat2` 等把路径解析约束交给一次内核操作。

## 10.3 历史教训：并发错误会伤人

Therac-25 等案例提醒我们，安全关键系统不能把“操作员应该按正常速度操作”当同步协议。竞态、错误提示复用、缺少硬件联锁与不可审计状态叠加，会把偶现软件错误变成灾难。

安全工程需要 defense in depth：

- 软件状态机显式检查危险组合；
- 独立硬件联锁限制物理输出；
- 故障默认进入安全状态；
- 日志能重建决策路径；
- 测试覆盖异常速度、重试、取消和断电，而非只覆盖 happy path。

## 10.4 Harness Engineering：让 Bug 无处藏

课程反复强调为程序搭“围栏”和“仪表盘”：

- 编译期：`-Wall -Wextra`、静态分析、类型/所有权系统；
- 运行期：ASan、UBSan、TSan、lockdep、断言；
- 测试期：压力调度、随机种子、超时、故障注入；
- 生产期：指标、trace、watchdog、core dump 与可回放日志；
- 设计期：缩小共享状态，写清锁顺序和状态机不变量。

TSan 找数据竞争，不能证明业务原子性；lockdep 根据实际/静态锁顺序发现潜在环，不能理解所有自定义等待关系。工具报告必须结合协议解释。

## 10.5 从正确到可扩展

最简单的并行求和可以让所有线程每个元素都锁一次更新全局和，结果正确却把热点集中到一条缓存行。更好的分解：

1. 数组按连续区间分片；
2. 每线程在寄存器/本地变量累计；
3. 每线程只写一次自己的结果；
4. join 后由主线程归约。

运行：

```bash
./examples/parallel_sum 1 10000000
./examples/parallel_sum 4 10000000
perf stat ./examples/parallel_sum 4 10000000
```

[parallel_sum.c](../examples/parallel_sum.c) 还把每个结果对齐到缓存行：

```c
alignas(64) uint64_t sum;
```

若不同线程频繁写同一缓存行里的不同变量，一致性协议仍会在核间来回转移整条缓存行，这叫 **false sharing**。变量逻辑上不共享，硬件粒度却让它们互相干扰。

## 10.6 Thread-local storage 与分片

TLS 让每个线程拥有独立实例：

```c
static _Thread_local unsigned local_hits;
```

它适合统计、缓存、临时 arena 等 fast path，最终再合并。分片哈希表则根据 key 把操作散到多把锁；读多写少场景还可采用不可变快照、RCU 或版本校验。

代价是跨线程汇总、线程退出清理和内存膨胀。线程数很多时，每线程缓存乘法效应非常明显。

## 10.7 workload 决定优化

评价并行数据结构前至少说明：

- 读写比例、key 分布和热点；
- 操作粒度与临界区长度；
- 线程是否固定到核、NUMA 拓扑；
- 数据规模是否装入缓存；
- 关注延迟尾部还是总吞吐；
- 正确性与持久化要求。

“无锁”不自动更快：原子重试会制造缓存争用，内存回收（ABA、hazard pointer、epoch）也很复杂。低竞争 mutex 往往具有极短 fast path。

## 10.8 Scale Up 与 Scale Out

- **Scale Up**：增加单机核数、内存、GPU，仍要解决共享资源争用和 NUMA。
- **Scale Out**：把任务拆到多机，避免共享内存，却引入网络延迟、部分失败和一致性协议。

“Embarrassingly parallel” 的任务几乎无需通信，最容易扩展；Mandelbrot 每个像素可独立计算就是课程示例。真正困难的工作负载常受串行阶段、数据搬运或全局同步限制。

## 10.9 常见误区

- 给测试加大循环次数就能证明无死锁：只能提高触发概率，不能覆盖无限调度空间。
- TSan 没报告就没有竞态：未执行路径、进程间共享和自定义同步可能看不到。
- 更多线程一定更快：创建、切换、缓存和同步都有成本。
- CPU 利用率 100% 就优化好了：可能全在自旋和缓存争用。
- 锁拆得越细性能越好：管理成本、死锁风险和局部热点会反噬。
- 只测平均延迟：暂停、队头阻塞和资源抖动往往先伤害 p99/p999。

## 10.10 自测与实验

1. 删除 `parallel_sum` 的 64 字节对齐，增加线程数并用 `perf stat` 比较 cache miss；结果为何依机器而异？
2. 为 `mutex_transfer` 写一个锁顺序断言或简单 lockdep 包装。
3. 给生产者—消费者注入随机 `sched_yield`，再用 TSan 运行。
4. 设计一个不会永久等待的超时事务：列出部分完成时的补偿动作。
5. 为一个读多写少配置表比较全局 mutex、读写锁和不可变快照的复杂度与 workload。
