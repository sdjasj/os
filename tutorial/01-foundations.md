# 第 1 章：建立世界观——状态机、抽象与系统启动

> 对应讲义：[第 1 讲](../sources/notes/lect01.md)、[第 2 讲](../sources/notes/lect02.md)、[第 3 讲](../sources/notes/lect03.md)、[第 4 讲](../sources/notes/lect04.md)

学完本章，你应该能用同一个“状态机”模型解释程序、处理器和操作系统，能说清机器从复位到运行第一个用户进程的路径，并知道为什么学习 OS 的重点不是背 API，而是理解抽象边界。

## 1.1 操作系统到底是什么

先别急着背定义。站在应用一侧看，操作系统提供进程、文件、网络连接、窗口和设备等对象；站在硬件一侧看，它接管处理器、内存和 I/O，在正确的时刻运行正确的代码。

因此可以先抓住三个作用：

1. **抽象**：把磁盘扇区变成文件，把处理器时间片变成进程，把网卡数据包变成 socket。
2. **复用**：让很多程序在时间上共享 CPU、在空间上共享内存与磁盘。
3. **隔离与保护**：一个程序崩溃时，通常不应该改坏另一个程序的内存或文件。

```text
应用程序       shell  浏览器  数据库  编译器
                    │ 系统调用
操作系统       进程  地址空间  文件  socket  设备
                    │ 指令/中断/MMIO/DMA
硬件           CPU  内存  磁盘  网卡  GPU
```

这个图不是三层“静态积木”。应用需求会推动新系统调用出现，硬件能力也会反过来改变 OS 的实现；UNIX、GPU、容器都是这种共同演化的结果。

## 1.2 一把通用钥匙：Everything is a state machine

一个顺序程序的完整状态可以粗略写成：

\[
S = (PC, Registers, Memory, I/O)
\]

执行一条指令就是状态迁移 `S -> S'`。C 函数看起来像数学函数，但只要它修改全局变量、堆、文件或终端，它就有副作用，调用顺序便会影响结果。处理器同样如此：寄存器、内存和设备寄存器组成状态，时钟或事件推动迁移。

运行配套模型：

```bash
./examples/state_machine
```

[完整代码](../examples/state_machine.c) 中，每个 `Task` 保存 `pc` 和 `acc`，调度器每次只执行一步：

```c
Task *current = &tasks[tick % task_count];
step(current);
```

这几行已经包含了操作系统调度最重要的直觉：

- 暂停任务时保存状态；
- 选择另一个任务；
- 恢复其状态并继续；
- 任务不必知道自己曾被暂停。

真实上下文切换保存的是通用寄存器、栈指针、程序计数器以及必要的处理器状态。地址空间切换还可能更换页表根，并影响 TLB；所以“切一下线程”并非零成本。

## 1.3 应用视角：计算加系统调用

用户程序的大部分指令只是本地计算。只有需要受保护的资源时，才通过系统调用进入内核：

```c
int fd = open("notes.txt", O_RDONLY);  // 请求一个文件对象
ssize_t n = read(fd, buf, sizeof(buf)); // 请求对象执行读操作
close(fd);                              // 释放当前进程的引用
```

可把一个应用粗略还原为：

```text
纯计算 → 系统调用 → 纯计算 → 系统调用 → … → exit
```

`strace` 正适合验证这个模型：

```bash
strace -f -o /tmp/trace.txt /bin/echo hello
less /tmp/trace.txt
```

你会看到动态加载器先映射共享库，程序再 `write`，最后 `exit_group`。高级语言、标准库和框架隐藏了细节，但最终仍要落到 CPU 指令与操作系统 API。

## 1.4 硬件视角：从 Reset 到第一个进程

处理器上电后不会“自动找到操作系统”。它只把内部状态设为体系结构规定的初值，从 reset vector 开始取指。典型启动链如下：

```text
CPU Reset
   ↓
固件（BIOS/UEFI/OpenSBI）：初始化内存和设备
   ↓
引导程序：找到并装入内核
   ↓
内核：建立页表、中断、调度器和驱动
   ↓
第一个用户进程（如 init/systemd）
   ↓
服务、登录会话、桌面和普通应用
```

三个事件容易混淆：

- **异常（exception）**：当前指令同步触发，如缺页、除零、系统调用指令。
- **中断（interrupt）**：设备或定时器异步通知 CPU。
- **陷阱返回**：内核恢复用户上下文，回到较低特权级继续执行。

从硬件看，“内核”也只是内存中的指令和数据。特殊之处是它运行在高特权级，配置了异常入口、页表和设备。硬件并不知道这些代码在人类概念中叫“操作系统”。

## 1.5 为什么历史很重要

很多看似古怪的 API 都是当时约束下的合理答案：

- 早期机器没有 OS，程序直接控制硬件；
- 计算机昂贵而 I/O 缓慢，批处理和中断提高利用率；
- 内存变大、MMU 出现，时间共享与进程地址空间成为可能；
- UNIX 用少量稳定对象与 API 支撑可组合工具；
- 网络、云、GPU 和 AI 又把“共享与隔离”的尺度扩展到数据中心。

学习 API 时追问“它当时要解决什么矛盾”，通常比死记参数更牢。比如 `fork()` 的整体复制很奇特，但它让 Shell 能在 `exec()` 前自然修改文件描述符，从而组成重定向和管道。

## 1.6 AI 时代的系统学习法

第 4 讲强调 Scaling Law、Agent 与复杂性分解。对 OS 学习最实用的落点是：让工具帮助提出假设，但让可重复实验负责裁决。

一个可靠循环是：

1. 写出预测，例如“父子进程的指针数值相同，但修改互不影响”。
2. 写最小程序，不把无关框架带进实验。
3. 用 `strace`、`gdb`、`/proc` 或 `perf` 收集证据。
4. 如果结果不同，先区分语言未定义行为、库实现、内核机制和硬件行为。
5. 把结论写成能再次运行的测试。

AI 可以解释手册、生成观察脚本和提示调试方向；不能把未经验证的输出当成事实。系统软件最迷人的地方，正是每个关键猜想几乎都能被实验触碰。

## 1.7 常见误区

- “操作系统就是内核”：日常所说的 Linux 系统还包含 libc、Shell、服务和发行版生态；内核只是核心资源管理层。
- “系统调用就是普通函数”：库函数可直接返回；系统调用要经过受控特权级切换，并由内核校验参数。
- “一行 C 对应一条指令”：编译器可以删去、合并和重排代码；处理器还可能乱序执行。
- “程序从 `main` 开始”：真正入口通常是 `_start`，运行时初始化后才调用 `main`。
- “机器启动就运行内核”：先有 reset vector 和固件，再有引导程序与内核。

## 1.8 自测与实验

1. 把 `state_machine.c` 的时间片从一步改成两步，输出发生了什么变化？最终结果为何不变？
2. 用 `strace -f` 比较静态链接和动态链接的 Hello World，启动阶段多出了哪些调用？
3. 为什么定时器中断是抢占式多任务的关键？如果没有它，一个恶意死循环会怎样？
4. 系统调用时 CPU 仍在执行状态迁移；“进入内核”究竟改变了状态中的哪些部分？
5. 试着用一句话分别从应用、内核和硬件视角描述 `read(fd, buf, n)`。
