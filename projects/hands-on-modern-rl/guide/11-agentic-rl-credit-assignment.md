# 11. Agentic RL：从一次工具选择到多轮轨迹的信用分配

前面的 LLM 对齐把一段回答视为一次采样。工具型智能体会先搜索、再计算、读取工具结果、修正计划，最后才给出答案。一次任务包含多个决策，早期工具调用会改变后续可见信息。训练对象因此从“回答的偏好”扩展为“整条交互轨迹的质量”。

仓库用三类轻量代码展示这次变化：[工具选择策略](tool_use_agent.py) 说明动作如何参数化，[多轮奖励模拟](multi_turn_rl.py) 说明最终奖励如何传播，[Mini Deep Research GRPO](mini_deep_research_grpo.py) 展示一个更接近真实训练器的奖励接口。本章先读两个纯 NumPy 模拟，再讨论接入模型和工具运行时所需的边界。

## 把工具任务写成序列决策问题

设用户要求“查找两个事实，计算它们的比值，并给出来源”。一个可能的轨迹是：

```text
用户问题
  -> 选择 search，生成查询词
  -> 读取搜索结果
  -> 决定是否再次搜索
  -> 选择 calculator，传入表达式
  -> 读取计算结果
  -> 组织带引用的最终回答
```

可以把它写成 MDP 或部分可观测决策过程：

| 要素 | 工具型智能体中的含义 |
| --- | --- |
| 状态 \(s_t\) | 用户问题、历史消息、工具结果、剩余预算、当前计划 |
| 动作 \(a_t\) | 生成 token、选择工具、填写参数、停止并回答 |
| 转移 \(P\) | 工具执行、网页变化、错误返回和上下文追加 |
| 奖励 \(r_t\) | 最终正确性、逐步有效性、成本、安全与格式评分 |
| 终止 | 给出答案、达到轮数/成本上限、进入不可恢复错误 |

真实 Agent 的状态往往不满足完全马尔可夫性。搜索结果可能不完整，外部网页会变化，工具内部状态也未完全暴露。工程实现仍可用轨迹近似建模，但评估时要保留这种不确定性。

## 两种动作粒度

LLM Agent 同时存在两个时间尺度：

1. token 级动作：模型每次选择下一个 token；
2. turn 或 tool-call 级动作：一段结构化调用被视为一个语义步骤。

token 级目标能精细更新生成概率，却使轨迹很长。逐轮目标更容易解释信用分配，却要决定一整段调用参数如何共享奖励。实际训练常在逐轮构造奖励和掩码，再把该步优势广播到属于该动作的 token。

一个概念化记录可以写成：

```python
record = {
    "prompt_tokens": ...,
    "action_tokens": ...,
    "tool_output_tokens": ...,
    "action_mask": ...,
    "step_reward": ...,
    "episode_id": ...,
    "turn_id": ...,
}
```

`action_mask` 只标记策略真正生成、应参与梯度的 token。用户提示和工具返回可以进入上下文，但通常不应当被当成策略动作优化。

## 第一个实验：学习选择工具

`ToolPolicy` 为三个查询类型分别维护一行 logits：

```python
self.query_type_logits = {
    "search": np.zeros(n_tools),
    "calculate": np.zeros(n_tools),
    "run_code": np.zeros(n_tools),
}
```

给定查询类型 \(s\)，softmax 把 logits 转为工具概率：

\[
\pi(a_i\mid s)=\frac{\exp z_i}{\sum_j\exp z_j}
\]

采样动作 \(a_k\) 后，对数概率对 logits 的梯度为：

\[
\nabla_z\log\pi(a_k\mid s)=e_k-\pi(\cdot\mid s)
\]

代码直接实现这个解析梯度：

```python
probs = self.get_probabilities(query_type)
grad = -probs.copy()
grad[action] += 1.0
self.query_type_logits[query_type] += self.learning_rate * grad * reward
```

若选对工具得到正奖励，被选动作的 logit 会增加，其余动作相对下降；选错后的负奖励会反转更新方向。

### 这个实验真正学了什么

`get_query_type` 已经用关键词把文本分类为 `search`、`calculate` 或 `run_code`。策略只学习“三种已知类型到三个工具”的映射，没有从原始文本端到端学习语义表示。

这个边界很重要。实验适合验证策略梯度如何改变离散动作概率；它不能证明模型能对未见过的自然语言选择工具。把关键词分类器替换成神经网络编码器，才会出现表征学习和泛化问题。

### 运行与观察

```bash
cd <project-root>/code
python chapter10_agentic_rl/tool_use_agent.py
```

记录每类查询的三项概率，而不只记录总准确率。建议做三组修改：

- 把错误工具奖励从 `-0.1` 改为 `-1.0`，观察策略变得确定的速度；

- 让训练分布中搜索问题占 90%，分别报告宏平均和微平均准确率。

## 从一步奖励到多轮信用

在 [多轮奖励模拟](multi_turn_rl.py) 中，每个场景包含 3 至 5 次工具调用。代码比较两种奖励布局。

### 结果奖励 ORM

```python
rewards = [0.0] * n
all_correct = all(turn.get("correct", False) for turn in turns)
rewards[-1] = 1.0 if all_correct else 0.0
```

只有最终一步拿到奖励。若最终成功，早期动作通过折扣回报间接得到信用：

\[
G_t=\gamma^{T-t}R_T
\]

优点是标签便宜且直接对准最终目标。缺点是失败轨迹中的所有步骤都得到零信号，模型无法知道错误从哪一步开始。

### 过程奖励 PRM

```python
if correct:
    base_reward = 0.7 + np.random.uniform(0, 0.3)
else:
    base_reward = np.random.uniform(0.0, 0.3)
```

每一步都有独立评分，早期错误可以立即被区分。代价是过程标签需要可靠判据；评分器若偏爱冗长、固定格式或某个工具，就会把这种偏差传给策略。

源代码中的 PRM 分数由正确性加随机数模拟。它用于画出密集信号的形状，没有训练过程奖励模型，也没有验证工具参数是否真的支持最终结论。

## 奖励、回报与优势不能混用

即时奖励 \(r_t\) 评价当前步骤。折扣回报把后续奖励传播回来：

\[
G_t=r_t+\gamma G_{t+1}
\]

优势还要减去同状态下的基线：

\[
A_t=G_t-V(s_t)
\]

GRPO 则可在同一任务的多条轨迹之间做组内比较。三个量分别回答“这一步得几分”“从这里往后总共得几分”“相对预期好多少”。日志字段如果都叫 `reward`，调试时会失去这些区别。

### 折扣因子如何传播最终信用

一条四步轨迹只在最后得到 1 分：

| \(\gamma\) | 第 1 步回报 | 第 2 步回报 | 第 3 步回报 | 第 4 步回报 |
| ---: | ---: | ---: | ---: | ---: |
| 0.5 | 0.125 | 0.25 | 0.5 | 1.0 |
| 0.9 | 0.729 | 0.81 | 0.9 | 1.0 |
| 0.99 | 0.970 | 0.980 | 0.99 | 1.0 |

较大的 \(\gamma\) 让早期动作得到更强信号，也更难区分哪一步真正造成结果。较小的 \(\gamma\) 强调临近结果的动作，可能忽略必须很早执行的搜索或规划。

## 多轮训练需要正确的掩码

假设序列由以下片段拼接：

```text
[用户提示][assistant 工具调用][工具返回][assistant 最终回答]
```

一个常见动作掩码是：

```text
[0 0 0 ...][1 1 1 ...][0 0 0 ...][1 1 1 ...]
```

计算策略损失时只聚合掩码为 1 的位置：

\[
L=-\frac{
\sum_t m_t\log\pi_\theta(a_t\mid s_t)A_{step(t)}
}{\sum_t m_t}
\]

这里的 \(m_t\) 是动作掩码，`step(t)` 把 token 对应到工具调用或最终回答。若把工具返回也置为 1，模型会被训练去“预测环境已经给出的文本”；若连提示 token 一起平均，长提示会稀释真正动作的梯度。

## 轨迹数据必须保留哪些事实

只保存最后一段文本无法重放或审计 Agent 决策。最小轨迹应包含：

- 原始任务和不可变任务 ID；
- 每轮模型输入、结构化动作和采样参数；
- 工具名称、规范化参数、输出或错误类型；
- 每步开始/结束时间、token 与外部调用成本；
- 终止原因，而不只保存成功布尔值；
- 原始奖励分量、聚合规则、评分器版本；
- 策略与参考模型版本；
- 可训练 token 掩码和旧策略对数概率。

网页内容会变化，外部 API 也可能不可重放。需要保存允许保留的证据快照或内容哈希，同时遵守数据许可和隐私边界。

## 工具执行的安全边界

`multi_turn_rl.py` 中的 `tool_code_executor` 只返回模拟结果，并不执行传入字符串。真实代码工具必须把模型输出视为不可信输入，至少需要：

- 隔离的进程、容器或虚拟机；
- 明确的文件系统和网络策略；
- CPU、内存、进程数、输出和墙钟时间限制；
- 每次任务独立的临时工作区；
- 超时与取消后对子进程树做可靠清理；
- 结构化审计日志，且不记录秘密值。

上游 `docs/chapter22_agentic/code/environment.py` 是教学骨架，其中声明的 `max_memory` 没有形成操作系统级强制限制，并会直接运行模型生成的 Python。它不能作为安全沙箱使用。

## On-policy、离线轨迹与数据陈旧

PPO/GRPO 假设轨迹来自某个明确的旧策略。Agent rollout 成本高，工程上会并行生成并排队训练；策略持续更新后，队列中的旧轨迹越来越陈旧。需要记录策略版本，并监控：

- 当前策略与行为策略的 KL；
- 重要性采样比率的分布；
- 轨迹从生成到训练的延迟；
- 不同版本轨迹在每批中的占比。

离线轨迹可用于 SFT、行为克隆或离线偏好学习。若直接把它们当成当前策略的 on-policy 数据，PPO 比率和优势解释会失真。

## 动手实验：制造一条早期错误

运行多轮模拟：

```bash
cd <project-root>/code
python chapter10_agentic_rl/multi_turn_rl.py
```

然后固定一个四步场景，让第 1 步错误、其余步骤正确。分别计算：

1. “所有步骤都正确才成功”的 ORM；
2. 当前 PRM；
3. 只奖励第一次关键检索和最终答案的混合方案。

对 \(\gamma=0.5,0.9,0.99\) 打印每步回报。检查奖励设计能否明确指出第 1 步错误，同时不鼓励无意义地增加中间步骤。

## 动手实验：奖励分量消融

对同一个 Deep Research 响应集合，保存四个原始分量，逐次移除一个分量：

```text
accuracy
citation_support
search_validity
format
```

比较排序前五的轨迹发生什么变化。若移除准确率后充满格式漂亮但结论错误的回答，说明格式只能作为辅助约束；若引用奖励提高但来源不支持结论，需要升级证据匹配方式。

## 本章小结

Agentic RL 把策略学习扩展到多轮、带外部状态变化的轨迹。训练系统需要同时决定动作粒度、逐步奖励、回报传播、动作掩码和轨迹版本。仓库的工具选择与 ORM/PRM 代码把这些概念压缩为可在 CPU 上运行的实验；它们没有端到端训练语言模型，也没有提供真实安全沙箱。读懂这种边界后，再接入真实 rollout 和训练器才不会把模拟指标当成系统能力。
