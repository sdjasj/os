# 00｜学习指南：如何真正读懂 Pi

## 1. 学习目标分层

不要一开始就试图记住每个类。Pi 更适合从“稳定抽象”向“产品细节”逐层学习：

1. **数据层**：消息、工具、模型、事件分别长什么样。
2. **控制层**：流式响应、代理循环、取消和队列如何工作。
3. **编排层**：`AgentSession` 怎样把扩展、会话、压缩和 UI 串起来。
4. **呈现层**：CLI/TUI 如何展示状态、处理输入和减少重绘。
5. **扩展层**：用户如何在不修改核心代码的情况下添加能力。

每学完一层，都要能画出输入、输出、状态和失败路径，而不是只知道函数名称。

## 2. 开始前需要具备什么

建议基础：

- 能阅读 TypeScript，理解 `interface`、联合类型、泛型和 `async/await`；
- 会使用 Git、npm 和 Node.js；
- 知道大语言模型的 prompt、token、上下文窗口和 tool calling；
- 了解终端程序，但不要求写过 TUI；
- 了解 JSON；不了解 JSONL、CBOR、ANSI 也没关系，01 会补齐。

本快照要求 Node.js `>= 22.19.0`。先检查：

    node --version
    npm --version
    git --version

源码已经克隆到 `../pi-mono/`。如果你在其他机器上学习，可执行：

    git clone https://github.com/earendil-works/pi-mono.git
    cd pi-mono
    git checkout 4e494929998d6bc4fccf75e0a233f727db4b70ee
    npm install --ignore-scripts

固定提交不是硬性要求，但能保证源码位置与教程一致。

## 3. 推荐的源码阅读循环

面对一个陌生模块时，采用以下七步法：

1. **先找公共类型**：通常是 `types.ts` 或包的 `index.ts`。
2. **找构造入口**：例如 `createAgentSession`、`new Agent`。
3. **找状态所有者**：谁保存消息、当前模型、运行状态和取消控制器？
4. **找主循环**：例如 `runLoop`、`doRender`。
5. **列事件**：哪些事件被发出？谁订阅？哪些进入持久化？
6. **找边界实现**：模型 Provider、文件操作、终端输出、网络 Transport。
7. **用测试反证理解**：测试往往比注释更清楚地表达异常和边界行为。

以 Agent 为例：

    packages/agent/src/types.ts       # 先认识 AgentMessage/AgentEvent/AgentTool
    packages/agent/src/agent.ts       # 找状态所有者和公共 API
    packages/agent/src/agent-loop.ts  # 找控制流
    packages/agent/test/              # 验证取消、工具执行、消息队列等边界

建议在纸上或笔记中固定记录四栏：

| 问题 | 示例 |
| --- | --- |
| 输入是什么？ | `AgentMessage[]`、工具集合、模型 |
| 状态放在哪？ | `Agent.state`、`SessionManager.leafId` |
| 输出是什么？ | 新消息、事件、JSONL 条目、终端行 |
| 如何失败？ | abort、认证缺失、schema 校验失败、上下文溢出 |

## 4. 四周学习路线

### 第 1 周：打通主路径

- 第 1 天：00、01，练习异步迭代器与判别联合。
- 第 2 天：02、03，能说出各包边界。
- 第 3 天：04，手画 `text_start → text_delta → text_end → done`。
- 第 4～5 天：05，跟踪没有工具、有一个工具、工具报错三条路径。
- 第 6 天：07，只追踪 `main → createAgentSession → prompt`。
- 第 7 天：用自己的话写一页架构总结。

验收标准：不看教程，能解释“一次用户输入为什么可能产生多个模型请求”。

### 第 2 周：工具、状态与扩展

- 第 1～2 天：08，比较 read/edit/bash 的执行契约。
- 第 3～4 天：10，手工构造一棵有分支的 JSONL 会话树。
- 第 5～6 天：09，运行并修改一个官方扩展示例。
- 第 7 天：完成项目一或项目二。

验收标准：能新增一个参数有运行时校验、支持取消且有测试的自定义工具。

### 第 3 周：界面与工程质量

- 第 1～3 天：06，从最小组件追到差量渲染。
- 第 4 天：11，理解为何核心只依赖 telemetry 接口。
- 第 5～6 天：13，写 Faux Provider 驱动的确定性测试。
- 第 7 天：阅读两组你感兴趣的现有测试。

验收标准：能区分业务消息、AgentEvent、TUI 局部状态和持久化条目。

### 第 4 周：集成与独立设计

- 第 1～2 天：12，比较 SDK、RPC 和远程协议。
- 第 3～6 天：完成项目三，或选择项目四。
- 第 7 天：利用 15 做一次“从问题反查源码”的闭卷练习。

验收标准：能设计一个新能力，并说明它应放在哪个包、为何不应放在其他包。

## 5. 读代码时要主动追问的背景问题

### 为什么大量使用事件？

模型生成、工具执行、TUI 更新都不是瞬时完成。事件把“结果尚未完成”变成一等状态，使 UI 能显示增量文本、工具进度和取消结果。

### 为什么消息和事件不能混为一谈？

消息需要进入模型上下文或会话记录；`text_delta` 只是在运输过程中的碎片。若把每个 delta 都持久化，会话将膨胀且难以重建。

### 为什么接口中显式传入依赖？

`ReadOperations`、`StreamFn`、`TelemetryContext` 等接口允许核心逻辑在本地文件、远程文件、真实模型和测试假实现之间切换，而不把环境细节写死。

### 为什么少量核心功能反而有利于扩展？

核心越少，长期兼容面越小。Pi 把特定工作流交给 extensions、skills、prompt templates 和 packages；学习时要不断辨别“通用机制”与“某种偏好”。

## 6. 做实验的方式

每次只改变一个变量。例如研究工具执行：

1. 使用 Faux Provider，排除真实 API 和网络波动；
2. 只注册一个内存工具；
3. 记录完整 AgentEvent；
4. 再加入第二个工具观察并行；
5. 最后加入 abort 和错误路径。

不要用真实工作目录做危险命令实验。为练习创建专用目录，并在其中放可丢弃文件。

## 7. 每章的完成定义

一章不是“读完”就完成，至少应做到：

- 能画出本章核心数据流；
- 能定位两个公共类型和两个实现函数；
- 能解释一个正常路径和一个失败路径；
- 完成至少一道“动手练习”；
- 把不理解的名词添加到自己的术语表。

遇到教程与源码不一致时：

1. 运行 `git rev-parse HEAD` 检查版本；
2. 用 `rg "函数名" packages` 按符号搜索；
3. 阅读同目录测试；
4. 以当前源码为准，并记录接口发生了什么变化。
