# 系统安全导论：资产、主体、边界与不变量

对应官方模块：Introduction  
官方页面：https://pwn.college/system-security/introduction/

## 1. 从“一个程序”扩展到“一个系统”

系统由进程、内核、用户、网络、文件系统、凭据、硬件和运维流程共同组成。安全事故往往发生在接口处：

~~~text
浏览器 -> 网络服务 -> 解析子进程 -> 数据库
                |          |
              文件系统    密钥代理
                \          /
                    内核
~~~

每个组件都可能“按自己的契约正确运行”，但双方对编码、身份、路径、时序或权限的理解不一致，组合后就出现漏洞。

## 2. 四个建模对象

### 2.1 资产

需要保护的东西：机密数据、完整配置、计算资源、服务可用性、身份凭据、审计记录。

### 2.2 主体

能够发起操作的实体：用户、进程、容器、线程、设备或远端对等方。不要只把“用户名”当身份；同一用户下的两个进程也可能处于不同信任级别。

### 2.3 对象

被操作的资源：文件、内存页、socket、IPC 队列、内核对象、数据库行。

### 2.4 安全不变量

任何执行路径和时序都应保持的条件，例如：

- 只有密钥代理可以读取私钥；
- 解析器永远不拥有写生产目录的权限；
- 未认证请求不能影响其他租户对象；
- 审计日志追加后普通服务进程不能修改。

“使用了容器”不是不变量；“容器进程无法取得宿主写权限”才是可以验证的陈述。

## 3. 信任边界与数据流

以文件上传服务为例：

~~~text
[互联网字节]
     |
     v  边界 A：协议解析
[低权限解析器]
     |
     v  边界 B：验证后的内部消息
[存储服务]
     |
     v  边界 C：文件系统与内核
[磁盘对象]
~~~

每跨越一个边界都要问：

1. 身份怎样证明？
2. 数据是否重新解析或规范化？
3. 权限在哪一侧检查？
4. 检查结果与实际使用是否绑定到同一对象？
5. 失败时默认允许还是默认拒绝？
6. 日志能否关联同一次操作？

## 4. CIA 只是起点

经典目标：

- **机密性**：不向未授权主体泄露；
- **完整性**：不被未授权改变；
- **可用性**：授权主体能在需要时使用。

系统分析还常加入：

- **真实性**：实体或数据来源可验证；
- **可追责性**：操作可归属且日志难以抵赖；
- **最小权限**：每个主体只拥有完成任务所需能力；
- **隔离性**：一个租户或组件失败不蔓延。

这些目标可能冲突。例如更详细的日志提升可追责性，却可能泄漏敏感数据；解决办法是日志最小化、脱敏和独立访问控制，而不是只选一个目标。

## 5. 威胁模型不是攻击清单

一个实用模板：

~~~text
系统范围：
资产：
攻击者初始能力：
信任假设：
不在范围内：
关键边界：
最坏可接受后果：
检测与恢复：
~~~

攻击者能力必须具体。以下差别巨大：

- 能发送一个网络包；
- 有普通本地账户；
- 控制某个容器内 root；
- 能运行同核 CPU 线程；
- 能物理接触设备；
- 已掌握内核执行。

如果模型默认攻击者已经拥有你试图保护的最高权限，很多目标会变得无意义；如果模型假设过弱，又会得到虚假的安全感。

## 6. 一个最小权限的本地例子

下面的 Python 程序读取标准输入、计算 SHA-256，不需要网络、写文件或高权限：

~~~python
# digest_worker.py
import hashlib
import sys

data = sys.stdin.buffer.read(1024 * 1024 + 1)
if len(data) > 1024 * 1024:
    raise SystemExit("input too large")
print(hashlib.sha256(data).hexdigest())
~~~

~~~bash
printf 'hello' | python3 digest_worker.py
# 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
~~~

系统设计问题不是“Python 是否安全”，而是：

- 为什么该工作进程能看见整个主目录？
- 为什么它可能继承监听 socket 或云凭据？
- 输入无限时会不会耗尽内存？
- 超时、CPU、进程数是否受限？

可通过独立用户、干净环境、关闭继承文件描述符、资源限制和 syscall 沙箱缩小后果。

## 7. 完全仲裁与引用监视器

访问控制的理想“引用监视器”有三个性质：

1. 每次访问都经过检查；
2. 监视器不可被绕过或篡改；
3. 足够小，能够分析和验证。

现实系统常因缓存结果、直接对象引用、备用接口或竞态而破坏第一条。例如入口层检查一次路径，但后续进程再次解析符号链接，检查对象与使用对象不再相同。

## 8. 攻击面与可信计算基

**攻击面**是攻击者可交互的入口集合。  
**可信计算基（TCB）**是若出错就能破坏安全目标的组件集合。

最小化两者的方法不同：

- 减少开放端口、解析格式和 API 可减攻击面；
- 把解析器降权、将密钥放入窄接口代理可减 TCB；
- 去掉不必要依赖同时有助于二者。

“代码量少”通常有帮助，但边界清晰、权限窄和接口简单更关键。

## 9. 纵深防御的正确理解

纵深防御不是堆叠同一种过滤器，而是在不同失效模式上布置独立约束：

~~~text
输入验证
 -> 内存安全
 -> 进程隔离
 -> 最小权限
 -> 内核缓解
 -> 监控
 -> 密钥轮换与恢复
~~~

如果所有层都依赖同一个易错字符串规范化函数，它们并不独立。要检查共同失效原因。

## 10. 常见误区

- **“内网就是可信”**：身份和完整性仍需验证。
- **“容器就是虚拟机”**：容器通常共享宿主内核。
- **“root 是单一绝对能力”**：namespace、capability、LSM 会改变其范围。
- **“没有 RCE 就没有风险”**：越权、泄漏、资源耗尽同样重要。
- **“拒绝异常输入即可”**：竞态和组合错误可能使用完全合法的输入。
- **“安全只发生在上线前”**：补丁、监控、撤销和恢复是系统属性。

## 11. 纸面练习

### 题目

图片解析服务以 root 运行，但只把结果写入数据库。列出至少三项不必要权限及相应收缩方式。

### 答案

它通常不需要读取用户主目录、绑定低端口、加载内核模块或任意写文件系统。可使用专用 uid、只读根文件系统、仅开放到数据库代理的 socket、删除 capabilities、关闭多余文件描述符，并设置 CPU/内存/进程数限制。具体权限要依据真实数据流验证。

### 题目

前端验证用户只能访问 /tenant/A，后端接受前端传来的任意绝对路径。哪条系统原则被破坏？

### 答案

后端把前端的判断当作不可伪造授权，却没有在自己的信任边界上基于身份重新仲裁；绝对路径也扩大了接口。应传递受认证身份和对象 ID，由后端做权限检查并安全解析。

## 12. 小结

系统安全始于明确的资产、主体、对象、边界和不变量。之后的沙箱、竞态、内核与侧信道只是这些模型在不同层面的具体表现。
