# 程序安全基础：注入、内存错误与缓解

对应官方模块：Program Security  
官方页面：https://pwn.college/program-security/program-security/

## 1. 学习目标

读完本章，你应当能够：

- 解释代码、数据和控制流为何必须分开建模；
- 区分 shellcode 注入与代码复用；
- 从越界读、越界写和生命周期错误推导安全影响；
- 说明 NX、栈金丝雀、ASLR、PIE、RELRO 分别保护什么；
- 看见一次崩溃时，按“根因—原语—约束—影响”分析，而不是直接猜偏移。

## 2. 程序安全究竟在保护什么

一个进程可以抽象成三部分：

1. **状态**：寄存器、内存、文件描述符等；
2. **规则**：机器指令规定状态怎样变化；
3. **权限**：内核允许这个进程访问哪些资源。

正常执行时，输入只应影响设计者允许的数据。漏洞的本质通常是输入越过了预期边界：

~~~text
预期：输入 -> 普通数据 -> 业务判断
漏洞：输入 -> 指针/长度/返回地址/格式描述 -> 非预期行为
~~~

因此“程序崩溃”不是漏洞的完整描述。真正要问的是：攻击者能否稳定地读到不该读的数据、改写不该写的位置，或改变下一条执行的指令。

## 3. 从字节到指令：为什么会有代码注入

CPU 不知道某段字节“本来是图片”还是“本来是指令”。它只会从指令指针指向的位置取字节并解码。早期系统若允许栈同时可写、可执行，那么攻击者可能：

1. 把机器码作为输入写入栈；
2. 破坏返回地址；
3. 令处理器跳到输入区域。

这就是代码注入的基本形态。现代系统用 W^X（可写与可执行不可兼得）或 NX 位阻止数据页执行。

下面的程序只演示字节表示，不执行动态输入：

~~~c
// bytes.c
#include <stdint.h>
#include <stdio.h>

int main(void) {
    const uint8_t code_like_data[] = {0x48, 0x31, 0xc0, 0xc3};
    for (size_t i = 0; i < sizeof(code_like_data); i++) {
        printf("%02x%s", code_like_data[i],
               i + 1 == sizeof(code_like_data) ? "\n" : " ");
    }
    return 0;
}
~~~

编译与预期输出：

~~~bash
cc -Wall -Wextra -O2 bytes.c -o bytes
./bytes
# 48 31 c0 c3
~~~

这四个字节作为数组时只是数据；若指令指针被引向它们且页面可执行，x86-64 会把它们解码为指令。安全边界不在“字节长什么样”，而在**页权限和控制流是否允许 CPU 把它们当指令取用**。

## 4. 内存错误的三种根因

### 4.1 空间错误

访问对象边界之外，例如数组只有 8 字节却写入第 9 字节。

~~~c
// bounds.c
#include <stdio.h>
#include <string.h>

static int copy_name(char dst[8], const char *src) {
    size_t n = strlen(src);
    if (n >= 8) {
        return -1;
    }
    memcpy(dst, src, n + 1);
    return 0;
}

int main(int argc, char **argv) {
    char name[8] = {0};
    if (argc != 2 || copy_name(name, argv[1]) != 0) {
        fputs("name must contain at most 7 bytes\n", stderr);
        return 1;
    }
    printf("hello, %s\n", name);
    return 0;
}
~~~

这里要注意三个细节：

- 容量 8 包含字符串结尾的零字节；
- 先验证长度，再复制；
- 复制 n + 1 字节是为了包含终止符。

仅仅把 strcpy 换成 strncpy 并不自动安全，因为 strncpy 在源串过长时可能不写终止零。安全来自清晰的容量不变量，而不是某个函数名。

### 4.2 时间错误

对象已释放却仍被使用，称为 use-after-free；同一对象释放两次称为 double-free。它们破坏的是生命周期，而非数组边界。

~~~c
struct session {
    int authenticated;
};

void close_session(struct session **slot) {
    free(*slot);
    *slot = NULL;          // 同时撤销所有权，减少悬空指针
}
~~~

把一个指针置空只修复这个别名。如果别处仍保存同一地址，错误仍然存在。真正的办法是明确谁拥有对象、何时转移所有权、何时所有借用都失效。

### 4.3 类型错误

程序按错误的类型解释内存，例如把短缓冲区强制转换成更大的结构体，或把带符号长度转换为无符号长度。

~~~c
int read_payload(const unsigned char *src, int length) {
    if (length < 0 || (size_t)length > 4096) {
        return -1;
    }
    size_t safe_length = (size_t)length;
    /* 此后只使用 safe_length */
    return consume(src, safe_length);
}
~~~

顺序很重要：如果先把 -1 转成 size_t，它会变成一个很大的正数。

## 5. 栈溢出的机械过程

典型函数栈帧可简化为：

~~~text
高地址
+------------------+
| 调用者的数据      |
+------------------+
| 保存的返回地址    |  <- ret 将从这里取 RIP
+------------------+
| 保存的帧指针      |
+------------------+
| 局部缓冲区        |  <- 输入写入此处
+------------------+
低地址
~~~

若一个向高地址增长的顺序写操作越过局部缓冲区，就可能依次覆盖保存的帧指针和返回地址。不同编译器、优化级别和 ABI 会改变布局，所以图是模型，不是可以硬背的固定偏移。

可用下面的安全观察程序确认对象地址会随编译而变化：

~~~c
// frame.c
#include <stdio.h>

static void observe(void) {
    char local[16] = {0};
    void *frame = __builtin_frame_address(0);
    printf("local=%p frame=%p\n", (void *)local, frame);
}

int main(void) {
    observe();
}
~~~

~~~bash
cc -Wall -Wextra -O0 -fno-omit-frame-pointer frame.c -o frame
./frame
# 地址每次可能不同；重点是二者属于当前栈区域
~~~

不要从一次输出推断跨机器的固定距离。严谨分析应检查该二进制的反汇编和调试信息。

## 6. 从根因到“原语”

漏洞研究常用“原语”描述已经获得的最小能力：

| 原语 | 含义 | 可能带来的下一步 |
|---|---|---|
| 越界读 | 读取对象之外的字节 | 泄漏地址、密钥或相邻对象 |
| 受限写 | 只能写特定值或特定范围 | 修改标志、长度或低位指针 |
| 任意地址读 | 选择地址并读取 | 绕过 ASLR、理解进程状态 |
| 任意地址写 | 选择地址和值并写入 | 修改数据或控制流目标 |
| 控制 RIP | 影响下一条执行地址 | 代码复用或跳到合法目标 |

“有溢出”不等于“有任意写”；“能控制 RIP”也不等于一定能执行任意行为。输入字节限制、地址未知、调用约定、页权限和进程权限都会约束利用链。

## 7. 主要缓解机制各自做什么

### 7.1 NX / DEP

把栈和堆标成不可执行，阻断直接运行输入字节。它不修复越界写，也不阻止复用已有可执行代码。

检查 ELF 的 GNU_STACK 标志：

~~~bash
readelf -W -l ./frame | sed -n '/GNU_STACK/p'
~~~

通常会看到 RW 而不是 RWE。

### 7.2 栈金丝雀

编译器在局部对象与关键控制数据之间放置一个难以预测的值，函数返回前检查它是否变化。

~~~bash
cc -O2 -fstack-protector-strong bounds.c -o bounds-protected
readelf -sW bounds-protected | grep stack_chk_fail
~~~

金丝雀主要检测某些栈覆盖。它不能覆盖所有函数，也不能阻止越界读、堆错误或不触碰金丝雀的精确写入。

### 7.3 ASLR 与 PIE

ASLR 随机化栈、堆、共享库等映射地址；PIE 让主程序代码也能被随机化。随机化增加“地址未知”这一约束，但信息泄漏可能消除它。

~~~bash
cc -fPIE -pie frame.c -o frame-pie
readelf -h frame-pie | grep 'Type:'
# 通常为 DYN，表示可重定位的 PIE 映像
~~~

### 7.4 RELRO

动态链接需要全局偏移表等可重定位数据。Full RELRO 在启动时完成重定位并把相关区域变为只读，从而缩小可写控制数据面。

~~~bash
cc -Wl,-z,relro,-z,now frame.c -o frame-relro
readelf -d frame-relro | grep BIND_NOW
~~~

### 7.5 CFI 与安全语言

控制流完整性限制间接跳转目标；Rust 等内存安全语言在安全子集内消除许多空间和时间错误。它们仍无法代替业务授权、协议验证和 unsafe 边界审计。

## 8. 调试一次崩溃的正确顺序

假设程序收到输入后 SIGSEGV：

1. **固定输入和环境**：记录参数、标准输入、环境变量、版本；
2. **定位故障指令**：查看 RIP 和反汇编；
3. **判断读、写还是执行故障**：检查指令操作数和页权限；
4. **回溯污染来源**：哪个输入字段最终控制了寄存器或内存；
5. **测量能力**：可控多少字节、是否有零字节限制、能否重复；
6. **枚举缓解**：NX、PIE、金丝雀、RELRO、CFI；
7. **回到根因修复**：容量、生命周期、整数检查或类型边界。

GDB 的基本观察命令：

~~~gdb
break main
run
info registers
x/16gx $rsp
disassemble /m main
info proc mappings
~~~

这些命令用于理解自己的程序。地址和布局不应从别人的一次运行中照抄。

## 9. 常见误区

- **“崩溃就是远程代码执行”**：崩溃只证明可用性受影响，尚未证明可控性。
- **“开启 NX 就没有内存漏洞”**：NX 只限制执行权限。
- **“ASLR 让地址永远猜不到”**：低熵、派生地址和信息泄漏都可能削弱随机化。
- **“换成安全函数即可”**：若长度的单位、符号或所有权仍不清楚，问题只是换了形式。
- **“偏移是源码属性”**：偏移属于具体编译产物，会受 ABI、优化和编译器影响。

## 10. 纸面推演

### 题目一

某函数有 32 字节局部数组，使用一个外部给出的 32 位有符号长度。代码先把长度转成 size_t，再判断是否大于 32。输入长度为 -1 时发生什么？哪种修复更可靠？

### 答案

在常见 64 位平台上，-1 转为 size_t 后成为很大的无符号数，因此“大于 32”的判断通常会拒绝它；但如果代码在转换后又截断到更小类型，或判断与实际复制使用了不同变量，仍可能产生绕过。可靠做法是先在原有有符号域拒绝负数，再转换一次，并让验证与复制共用同一个已验证的 size_t 值。

### 题目二

一个二进制同时开启 NX、PIE、栈金丝雀和 Full RELRO。发现堆上的越界读。哪些缓解直接阻止这次读取？

### 答案

没有一个直接阻止越界读。它们分别保护执行权限、地址布局、某些栈覆盖和动态链接写目标。越界读本身必须通过边界检查、内存安全或隔离敏感数据修复；更糟的是，它还可能泄漏地址并削弱 PIE/ASLR。

## 11. 小结

程序安全分析的核心不是记 payload，而是持续维护四个问题：

1. 哪条程序不变量被破坏？
2. 由此得到什么读、写或控制流原语？
3. 当前编译产物和运行环境施加了哪些约束？
4. 根因修复与缓解机制分别在哪里生效？
