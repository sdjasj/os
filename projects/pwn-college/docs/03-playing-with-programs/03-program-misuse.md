# 03 · 程序误用：能力、信任边界与最小权限

> 对应官方模块：[Program Misuse](https://pwn.college/fundamentals/program-misuse/)

## 学习目标

- 用“程序拥有什么能力”分析风险，而不只看程序原本的用途。
- 理解调用者身份、进程权限、环境、输入与可扩展功能如何共同决定攻击面。
- 用最小权限、明确参数、受限路径和干净环境减少误用空间。
- 建立可用于审计任意工具的防御性检查表。

## 用途不等于能力

一个程序的说明可能是“查看文档”“处理文本”或“备份文件”，但安全分析关心它实际上能做什么：

- 它能读取或写入哪些对象？
- 能否启动其他程序或脚本？
- 能否加载插件、配置、模板或动态库？
- 它信任哪些环境变量、当前目录和搜索路径？
- 它的输出能否进入另一个更高权限的组件？

如果一个进程拥有某个权限，那么进程内所有可到达的功能都可能成为该权限的代理。一个原本“方便”的子命令、扩展钩子或文件导入功能，在权限边界上可能变成不应有的通道。

本篇只建立通用的能力与防御模型，不复刻站内 challenge，不提供 flag、精确利用载荷或逐关操作。

## 权限来自执行上下文

在类 Unix 系统中，程序文件只是代码；运行后的进程才拥有身份、打开的文件描述符、工作目录、环境和其他资源。可以从五个方向画出边界：

~~~text
调用者输入 ──> [ 程序代码 ] ──> 文件 / 网络 / 子进程 / 输出
                    ↑
          进程身份、环境、当前目录、已打开资源
~~~

其中任何一项比调用者更有权，程序就成了“受托代理”。安全目标是：只让它代表调用者完成经过授权的窄操作，而不是把全部内部能力间接开放。

现代系统可能同时存在用户/组身份、细分的内核能力、容器边界和强制访问控制。不要只检查一个数字化身份就断言“没有权限”；也不要因进程不是管理员就认为它无法接触敏感资源。实际能打开、修改、连接或启动什么才是能力事实。

## 审计程序的六个问题

### 1. 谁启动它，谁为结果负责？

区分交互用户、服务账户、调度器和上游服务。若 A 用户让 B 服务代为读取文件，B 必须验证 A 是否有权读取目标，而不能只依赖“B 自己读得到”。这类错误常被称为 confused deputy（混淆代理）。

### 2. 哪些输入可由低信任方控制？

不只有命令行参数。标准输入、文件名、文件内容、环境变量、工作目录、配置文件、网络响应、locale 和继承的文件描述符都可能影响行为。

### 3. 程序有哪些通用原语？

文件读取、文件写入、命令委派、模板求值、插件加载、归档解包、网络访问、权限或所有权变更都是高影响原语。单独看可能合理，但与额外权限组合时应重新审查。

### 4. 名称如何解析成对象？

相对路径依赖当前目录，程序名依赖 <code>PATH</code>，配置名可能在多个目录搜索，符号链接还可改变最终对象。验证字符串名称和实际打开对象之间可能发生变化，因此安全边界应尽量使用已经打开并验证的句柄。

### 5. 能力能否被组合？

一个功能只能写日志，另一个功能能让程序重新读取配置；两者结合可能使“只写日志”变成改变行为。审计不仅要列功能，还要追踪输出是否能成为下一项功能的输入。

### 6. 失败时是否更宽松？

解析失败、配置缺失、网络超时或检查异常时，应拒绝敏感操作并留下可审计记录。静默采用更宽权限的默认值，会让错误路径成为旁路。

## 完整安全示例：窄化一个外部工具的能力

下面程序只允许统计指定工作目录内普通文件的字节数。它在临时目录中运行，不需要任何额外权限，也不会访问网络。保存为 <code>least_authority.py</code>：

~~~python
#!/usr/bin/env python3
from pathlib import Path
import subprocess
import tempfile


class PolicyError(Exception):
    pass


def count_bytes(allowed_root, user_name):
    root = Path(allowed_root).resolve(strict=True)
    candidate = root / user_name

    # 本教学例拒绝符号链接，避免名称指向另一个对象。
    if candidate.is_symlink():
        raise PolicyError("symbolic links are not allowed")

    try:
        resolved = candidate.resolve(strict=True)
        resolved.relative_to(root)
    except (FileNotFoundError, ValueError) as error:
        raise PolicyError("path escapes allowed directory") from error

    if not resolved.is_file():
        raise PolicyError("target is not a regular file")

    completed = subprocess.run(
        ["/usr/bin/wc", "-c", "--", str(resolved)],
        cwd=root,
        env={"PATH": "/usr/bin:/bin", "LANG": "C"},
        stdin=subprocess.DEVNULL,
        stdout=subprocess.PIPE,
        stderr=subprocess.PIPE,
        text=True,
        timeout=2,
        check=True,
    )
    return int(completed.stdout.split()[0])


def main():
    with tempfile.TemporaryDirectory() as temporary:
        base = Path(temporary)
        allowed = base / "workspace"
        allowed.mkdir()
        (allowed / "note.txt").write_bytes(b"hello local")
        (base / "outside.txt").write_bytes(b"not delegated")

        print(f"bytes={count_bytes(allowed, 'note.txt')}")
        try:
            count_bytes(allowed, "../outside.txt")
        except PolicyError as error:
            print(f"rejected={error}")


if __name__ == "__main__":
    main()
~~~

运行：

~~~bash
python3 least_authority.py
~~~

预期输出：

~~~text
bytes=11
rejected=path escapes allowed directory
~~~

这个例子包含多层约束：

- 接口只暴露“计数字节”，而不是任意子进程执行；
- 参数以 argv 数组传递，没有 shell 解释层；
- 使用外部程序的绝对路径，并提供最小、确定的环境；
- <code>--</code> 表示后续内容是操作数，不再解释为选项；
- 解析后的目标必须位于允许目录内且为普通文件；
- 标准输入关闭，运行时间受限，输出被捕获。

最关键的一点是：这些检查减少了输入歧义，却不创造真正的系统隔离。子进程仍继承父进程能够使用的操作系统权限。若父进程本身能读取很多敏感文件，可靠设计应在操作系统层把服务账户、文件描述符、容器/沙箱或访问控制进一步收窄。

此外，示例中的“先检查路径、后由另一个程序打开”仍存在竞态窗口。高安全场景应使用不跟随符号链接的打开方式取得文件描述符，在打开后用元数据验证对象，并让后续处理直接使用该描述符。路径字符串验证适合说明原则，不是完整沙箱。

## 为什么应避免 shell 字符串

危险接口常把数据和命令语法放进同一个字符串：

~~~python
# 反例：不要把不可信 filename 拼进 shell 命令。
command = "wc -c " + filename
subprocess.run(command, shell=True)
~~~

此时空格、引号和 shell 元字符可能改变命令结构。更好的第一步是固定程序与选项，把数据作为独立 argv 元素传递，如完整示例所示。但 argv 数组并不能自动限制被调用程序自己的选项、配置搜索或扩展功能；仍要理解目标程序的能力。

## 最小权限不是“尽量少”，而是可证明的集合

可以为操作建立能力矩阵：

| 操作 | 需要的能力 | 不需要的能力 |
|---|---|---|
| 生成公开缩略图 | 读指定输入、写指定输出 | 读用户主目录、启动任意程序、外网访问 |
| 统计日志行数 | 读一个已打开日志句柄 | 修改日志、读取其他目录 |
| 提交本地打印任务 | 写打印队列 | 更改系统配置、加载任意插件 |

设计时先列出完成任务不可缺少的对象与动作，再让进程只得到这些能力。常见措施包括：

- 使用专用低权限账户和独立工作目录；
- 由可信父进程打开经过授权的资源，只传需要的文件描述符；
- 关闭无关的继承文件描述符和标准输入；
- 使用固定可执行路径、固定参数结构与干净环境；
- 将网络、文件系统写入和进程创建分别按需禁用；
- 为 CPU、内存、文件大小、进程数和运行时间设上限；
- 把解析复杂不可信格式的组件放进额外隔离边界。

不要给带有通用扩展、命令委派或任意文件功能的程序附加额外权限，然后希望用户只走“正常菜单”。权限边界必须约束实际可达行为，而不是文档建议的用途。

## 搜索路径、环境与当前目录

若程序通过短名称启动辅助工具，系统通常按 <code>PATH</code> 搜索；若以相对路径打开配置，则结果依赖当前目录；某些运行库还读取 locale、临时目录或插件相关环境变量。高权限边界不应继承低信任调用者提供的完整环境。

防御原则是显式化：固定工作目录、使用经过批准的绝对路径、只保留所需环境变量、设置安全的文件创建权限掩码，并记录实际启动的对象。清理环境不是为了“让命令更漂亮”，而是减少名称解析和加载行为的不确定性。

## 如何阅读 Program Misuse 类题材

即使不运行实验，也可以按下面顺序做纸面分析：

1. 写出进程的有效身份和额外能力；
2. 列出低信任方能控制的每个输入通道；
3. 将程序功能翻译为读、写、执行、加载、连接等原语；
4. 画出这些原语能接触的对象范围；
5. 检查两个普通功能能否串联成越界能力；
6. 提出在接口层和操作系统层各一道收窄措施。

这个方法比背诵某个工具的特殊行为更可迁移，也避免把练习答案误当成现实系统的通用操作指南。

## 常见误区

- **只看程序名称和正常用途。** 安全性取决于全部可达能力。
- **认为禁用 shell 就万事大吉。** 被调用程序自身仍可能有危险选项或加载机制。
- **先验证路径字符串，之后放心地再次打开。** 对象可能因链接或竞态发生变化。
- **把隐藏按钮当授权。** 服务端必须在执行动作时检查主体、对象和权限。
- **让高权限进程继承完整环境。** 搜索路径和配置加载会扩大控制面。
- **把输入过滤当成沙箱。** 真正隔离还需操作系统强制的能力边界。

## 纸面练习

一个缩略图服务只需要读取上传图片并写入结果目录，却还继承了用户主目录读权限、外网访问和启动任意辅助程序的能力。请指出至少三项不必要能力，并为“读取输入”设计一个比传任意路径更窄的接口。

### 答案

不必要能力包括读取用户主目录、访问外网和启动任意程序；若输出格式固定，也不应拥有结果目录之外的写权限。更窄的接口是由可信接收组件验证上传对象后打开文件，再把只读文件描述符交给缩略图进程。进程无需知道全局路径，也无法借参数请求其他文件；输出同理可由父进程提供一个限定目标的已打开描述符。

## 小结

程序误用的本质是“可达能力超过了授权意图”。把身份、输入、对象解析和功能组合画清楚，再用最小权限与强制隔离收窄范围，才是可迁移的解决方法。
