# 05 · 逆向工程：从字节、状态与证据恢复语义

> 对应官方模块：[Reverse Engineering](https://pwn.college/intro-to-cybersecurity/reverse-engineering/)

## 学习目标

读完本章，你应当能够：

- 区分文件格式分析、静态分析和动态分析；
- 从 ELF 段、节、符号、重定位和装载过程解释程序如何运行；
- 用调用约定追踪函数参数、返回值和保存寄存器；
- 从控制流与数据流恢复一个小函数的算法；
- 使用 `file`、`readelf`、`objdump`、`strings` 和 GDB 分层收集证据；
- 在隔离环境中审慎处理未知二进制，并避免把工具输出当成绝对真相。

## 1. 逆向不是“把机器码变回原源码”

编译会丢失大量高层信息：变量名、注释、类型别名、宏、源文件布局和部分控制结构。多个不同源码也可能生成等价机器码。因此逆向的目标通常是恢复足以回答问题的模型：

```text
输入从哪里来？
  -> 哪些函数处理它？
  -> 哪些状态影响分支？
  -> 关键数据在哪里读写？
  -> 程序最终产生什么可观察行为？
```

一个严谨结论应区分：

- **观察事实**：某地址处确实执行了 `cmp`；
- **工具推断**：反编译器把某区域识别为 `int`；
- **分析假设**：这个整数可能代表长度；
- **验证结果**：改变输入长度后，该值同步变化。

逆向不是猜函数名，而是不断让假设接受静态和动态证据检验。

## 2. 自建一个完全可控的样本

以下程序只计算命令行字符串的玩具分数：

```c
// toy_score.c
#include <stdio.h>
#include <string.h>

static int score(const char *text) {
    unsigned int total = 7;
    while (*text != '\0') {
        total = (total * 33u + (unsigned char)*text) % 997u;
        text++;
    }
    return (int)total;
}

int main(int argc, char **argv) {
    if (argc != 2) {
        fputs("usage: toy_score TEXT\n", stderr);
        return 2;
    }

    printf("len=%zu score=%d\n", strlen(argv[1]), score(argv[1]));
    return 0;
}
```

编译并运行：

```bash
cc -Wall -Wextra -O0 -fno-inline -g toy_score.c -o toy_score
./toy_score abc
```

预期输出：

```text
len=3 score=608
```

使用 `-O0 -fno-inline -g` 是为了让第一次观察更直观，不代表生产构建配置。后面应重新用 `-O2` 编译并比较，理解优化如何改变机器结构而不改变外部语义。

## 3. 第一层：确认文件身份与来源

在执行任何未知文件前先做静态识别。对自己的 `toy_score`：

```bash
sha256sum ./toy_score
file ./toy_score
readelf -h ./toy_score
```

输出中的哈希每个编译环境都可能不同；`file` 通常会指出：

```text
ELF 64-bit LSB pie executable, x86-64, ... with debug_info, not stripped
```

从中可以提出下一组问题：

- 架构和端序是什么？
- 是可执行文件、共享对象还是可重定位对象？
- 是否 PIE？
- 动态链接还是静态链接？
- 是否保留符号与调试信息？
- 文件来源、哈希和签名是否可信？

不要根据扩展名判断文件类型。Linux 执行格式由文件内容和内核加载规则决定。

## 4. ELF 中“节”和“段”回答不同问题

节（section）主要服务链接与分析，例如：

- `.text`：机器指令；
- `.rodata`：只读常量；
- `.data`：已初始化可写数据；
- `.bss`：零初始化数据；
- `.symtab`/`.dynsym`：符号信息；
- `.rela.*`：重定位记录。

段（segment）主要服务运行时装载。内核根据 program header 把文件区域映射进内存，并设置读、写、执行权限。

```bash
readelf -S ./toy_score
readelf -W -l ./toy_score
```

同一个可装载段可能包含多个节。不能简单地说“内核把 `.text` 节加载为一个进程”；更精确的描述是加载器按 `PT_LOAD` 等 program header 建立映射，节名在运行时甚至可能不再需要。

重点检查 W^X：包含代码的映射通常可读、可执行而不可写；数据映射可读、可写而不可执行。

## 5. 符号、动态链接与重定位

查看符号：

```bash
readelf -sW ./toy_score | grep -E ' main$| score$| strlen@'
nm -n ./toy_score | grep -E ' main$| score$'
```

由于保留了调试和普通符号，`score` 容易找到。若二进制被 strip，静态局部函数名可能消失，但导入函数、字符串引用、调用图和行为仍可提供线索。

动态链接程序在构建时不一定知道共享库的最终装载地址。重定位和过程链接表/全局偏移表帮助调用外部函数。可以观察：

```bash
readelf -d ./toy_score
readelf -r ./toy_score
objdump -d -M intel ./toy_score
```

看到 `strlen@plt` 不意味着 `strlen` 实现在主程序内；它通常是到动态链接机制的入口。具体实现位于运行时加载的 C 库。

## 6. 从调用约定开始读函数

在常见 Linux x86-64 System V ABI 中，前六个整数或指针参数通常依次放入：

```text
rdi, rsi, rdx, rcx, r8, r9
```

返回整数常放在 `rax/eax`。`rsp` 指向栈顶，`rbp` 在未省略帧指针时可作为栈帧基准。寄存器还分 caller-saved 与 callee-saved，决定谁负责跨调用保存值。

只反汇编玩具函数：

```bash
objdump -d -M intel --disassemble=score ./toy_score
```

具体地址和指令安排随编译器变化，但在 `-O0` 构建中通常能观察到：

1. `rdi` 中的 `text` 指针被保存到栈帧；
2. 局部 `total` 初始化为 7；
3. 循环读取 `*text` 并与零比较；
4. 乘以 33、加当前字节、计算模 997；
5. 指针递增并回到条件检查；
6. 把结果放入 `eax` 返回。

不要从某一次栈偏移推断源码变量永远位于那里。优化后 `total` 可能全程留在寄存器中，循环甚至会被重排。

## 7. 用控制流图恢复结构

反汇编器把代码切成基本块：一个基本块中间没有跳入或跳出，末尾通常是条件跳转、无条件跳转、调用或返回。

`score` 可抽象成：

```text
[入口: total = 7]
        |
        v
[读取当前字节] -- 是 0 --> [返回 total]
        |
       非 0
        v
[更新 total; text++]
        |
        +------------------> 回到读取
```

条件跳转方向不直接等于高层的 `if` 或 `while`。编译器可能翻转条件、复制块或使用条件移动。恢复结构时先记录块之间的边，再为整个区域选择最清楚的高层表达。

## 8. 数据流：追踪“值从哪里来”

控制流回答“可能走到哪里”，数据流回答“这个值由什么决定”。分析 `total` 时，可以建立递推式：

```text
T0 = 7
T(n+1) = (33 * Tn + byte[n]) mod 997
```

用一个独立 Python 跟踪器验证 `abc`：

```python
# trace_score.py
total = 7
for byte in b"abc":
    total = (total * 33 + byte) % 997
    print(chr(byte), total)
```

预期输出：

```text
a 328
b 952
c 608
```

这与程序最终输出一致，是对算法假设的一次交叉验证。若不一致，应回到指令检查：可能误判了整数宽度、符号扩展、模数或循环边界。

### 整数宽度很重要

x86 指令会明确操作 8、16、32 或 64 位值。写入 32 位寄存器通常会清零对应 64 位寄存器高半部分；`movsx` 与 `movzx` 分别做符号扩展和零扩展。把 `char` 错判为有符号或无符号，会在大于 `0x7f` 的输入上得到不同模型。

## 9. 字符串只是字节的一种解释

`strings` 可快速寻找可打印序列：

```bash
strings -a -n 5 ./toy_score | grep -E 'usage|score'
```

预期能看到格式串和用法文本。但要记住：

- 找到字符串不证明它一定可达；
- 没找到字符串不证明程序没有该语义，它可能被编码、构造或压缩；
- 偶然可打印的机器码也可能被误识别；
- 引用位置通常比字符串本身更有价值。

下一步应查找哪条指令引用该常量，再沿交叉引用追踪到函数和分支。

## 10. 动态分析：在运行状态上验证假设

只调试自己编译的样本：

```bash
gdb --quiet ./toy_score
```

可在 GDB 中使用：

```gdb
break score
run abc
info registers rdi rax rsp rbp
x/s $rdi
disassemble /m score
nexti
print $eax
continue
```

断在 `score` 入口时，`rdi` 应指向字符串 `abc`。具体寄存器中间值取决于断点位置和编译器，因此不要照抄固定地址。

动态分析适合回答：

- 这条路径是否真的执行？
- 某指针运行时指向何处？
- 间接调用的实际目标是什么？
- 解码后的数据长什么样？

它只能观察已运行的路径。一次执行没看到某行为，不代表其他输入或环境不会触发。

## 11. 系统调用视角

库函数最终通过系统调用请求内核操作文件、网络和进程。对自己的样本可观察：

```bash
strace -f -o toy.trace ./toy_score abc
sed -n '1,40p' toy.trace
```

输出会包含加载共享库、内存映射、写标准输出和退出等行为。`strace` 给出系统调用边界，不显示纯用户态计算，例如 `score` 循环本身。

分析时要避免把库函数与系统调用混为一谈：`printf` 是 C 库接口，可能做缓冲和格式化；真正写出时才触发 `write` 系统调用。

## 12. 优化如何改变形状

重新编译：

```bash
cc -Wall -Wextra -O2 toy_score.c -o toy_score_O2
objdump -d -M intel --disassemble=main ./toy_score_O2
```

可能看到：

- `score` 被内联到 `main`；
- 帧指针省略；
- 变量不再有固定栈槽；
- 模运算被替换为乘法、移位和减法；
- 循环条件被重新安排。

这不是算法变了，而是编译器选择了等价实现。逆向时应优先恢复行为不变量，而不是强迫机器码匹配某个熟悉源码模板。

## 13. 静态与动态分析如何互补

| 方法 | 强项 | 盲点 |
| --- | --- | --- |
| 文件格式与元数据 | 架构、映射、依赖、保护属性 | 不说明实际走哪条路径 |
| 静态反汇编/反编译 | 覆盖未执行路径、全局结构 | 间接跳转、运行时解码较难 |
| 调试器 | 寄存器、内存和分支的真实状态 | 一次只覆盖有限输入 |
| 系统调用跟踪 | 文件、网络、进程等外部行为 | 看不到纯用户态内部逻辑 |
| 对照实验 | 验证输入与输出关系 | 相关性不总等于因果 |

高置信度结论通常来自至少两类证据。例如静态分析认为某字段控制循环次数，再用两个玩具输入观察循环计数是否对应变化。

## 14. 安全分析与防御工作流

1. 记录样本来源、哈希、大小和时间；
2. 在不执行的情况下识别格式、架构、签名和依赖；
3. 建立隔离快照，禁用不必要网络和共享目录；
4. 先看入口、导入、字符串和权限，再选择关键函数；
5. 用调用约定标注参数与返回值；
6. 画控制流，追关键数据的定义与使用；
7. 用最小动态实验验证一个假设；
8. 记录证据、工具版本和不确定性；
9. 恢复快照，避免分析环境污染其他工作。

对于来源未知或可能恶意的二进制，不要在日常主机、管理员账户或含真实凭据的环境直接运行。即使使用虚拟机，也要审查剪贴板、共享目录、USB、网络和宿主集成能力。

## 15. 常见误区

- **“反编译器输出就是源码。”** 它是基于模式和类型推断生成的近似表达。
- **“函数名没了就无法分析。”** 行为、调用关系、常量和数据流仍存在。
- **“一个地址可以写进教程永久使用。”** PIE、ASLR、链接和重编译都会改变地址。
- **“字符串出现就一定被用到。”** 可能不可达、未引用或只是偶然数据。
- **“动态运行没触发，所以不存在。”** 只说明当前输入路径没触发。
- **“节就是内存映射。”** 装载主要由段描述；节更偏向链接和分析。
- **“未知文件放进虚拟机就绝对安全。”** 配置不当的共享与网络仍会扩大风险。

## 16. 纸面练习与答案

### 练习一：证据等级

反编译器把某个参数命名为 `password`。这能否证明它真是密码？下一步如何验证？

#### 答案

不能，这只是工具或已有符号的提示。应追踪参数来源、用途、比较方式和输出影响，并用自建输入或调试观察验证。若样本保留调试符号，名称可信度较高，但仍不代表业务安全语义。

### 练习二：TCP 字节序列

反汇编中看到从内存读取 4 字节后执行字节交换，再用作长度。最合理的初始假设是什么？

#### 答案

可能在把网络字节序的大端 32 位字段转换为主机端序。还需检查数据来源、调用上下文和长度边界验证，不能仅凭一次字节交换下结论。

### 练习三：优化

`-O0` 中存在独立 `score` 符号，`-O2` 中消失，但程序输出相同。最可能发生什么？

#### 答案

编译器可能把 `score` 内联进调用者，或做了其他跨函数优化。应在调用者中寻找等价数据流，而不是断言功能被删除。

### 练习四：静态与动态矛盾

静态分析发现一个写文件分支，运行三次都未见 `open`。应该相信哪一边？

#### 答案

两者并不矛盾：该分支可能存在但当前输入不可达。继续求解分支条件、检查配置与环境，设计最小授权实验；同时确认静态反汇编没有把数据误判为代码。

### 练习五：调用约定

进入一个 x86-64 System V 函数时，第一参数是指针。通常先检查哪个寄存器？函数返回整数后通常看哪里？

#### 答案

通常先检查 `rdi`，整数返回值通常位于 `rax/eax`。但仍应确认目标平台、ABI 和是否存在包装函数。

## 小结

逆向工程是一套证据驱动的方法：先识别文件与装载结构，再用 ABI、控制流和数据流建立假设，最后通过调试和系统调用观察验证。最可靠的分析报告不仅写“我认为程序做什么”，还写清证据、条件、工具局限和仍未排除的解释。
