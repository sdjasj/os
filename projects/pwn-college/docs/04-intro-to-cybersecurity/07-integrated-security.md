# 07 · 综合安全分析：沿信任边界连接每一层

> 对应官方模块：[Integrated Security](https://pwn.college/intro-to-cybersecurity/integrated-security/)

## 学习目标

读完本章，你应当能够：

- 为一个小型系统列出资产、主体、组件、数据流和信任边界；
- 把 Web、网络、密码学、访问控制和二进制风险连接成攻击图；
- 区分根因防御、阻断防御、检测与恢复控制；
- 设计一项失败不会自动扩大到全系统的纵深防御；
- 用安全不变量和负面测试验证组件组合，而不只测试单个函数；
- 从日志和事件时间线判断“发生了什么、影响到哪里、如何恢复”。

## 1. 组合机制：组件安全不等于系统安全

一个系统可能同时使用 HTTPS、参数化 SQL、强密码哈希和容器，却仍然存在越权。原因是安全性质只在明确边界内成立：

- TLS 保护传输，不决定登录用户能读哪条记录；
- 参数化 SQL 保护查询语法，不保证查询条件包含租户 ID；
- 加密数据库保护静态副本，不阻止已授权进程把数据返回给错误用户；
- 容器限制进程资源，不修复应用级身份混淆；
- 内存安全减少内存破坏，不自动修复业务逻辑。

综合分析关注“保证在哪里开始，在哪里结束，以及下一组件是否错误地假定保证仍然存在”。

## 2. 先画系统，再谈漏洞

以一个只在 `127.0.0.1` 上开发的玩具笔记系统为例：

```text
[本地浏览器]
      |
      | HTTP（开发环境仅回环）
      v
[Web 路由 / Session]
      |
      +----> [SQLite 笔记表]
      |
      +----> [导出任务队列] ----> [受限导出目录]
      |
      +----> [带完整性标签的审计日志]
```

生产环境还会加入 TLS 终止代理、身份提供方、缓存、对象存储、消息队列和监控平台。每加一个组件，都要记录：

- 它以什么身份运行；
- 接受哪些输入；
- 信任哪些首部、字段或证书；
- 能访问哪些资产；
- 失败时是重试、拒绝、降级还是积压；
- 日志会流向哪里。

架构图不是装饰品，它是威胁枚举的索引。

## 3. 资产、主体和安全目标

对玩具笔记服务，可以列出：

| 资产 | 机密性 | 完整性 | 可用性 |
| --- | --- | --- | --- |
| 笔记正文 | 仅所有者可读 | 仅授权者可改 | 可容忍短暂中断 |
| Session | 不得泄漏 | 不得伪造 | 可要求重新登录 |
| 审计记录 | 按需脱敏 | 必须能发现篡改 | 允许异步写入但不能静默丢失 |
| 导出文件 | 继承笔记权限 | 内容与请求一致 | 有配额和过期清理 |

主体至少包括普通用户、管理员、Web 服务进程、后台 worker、数据库账户和运维人员。把“系统”笼统当成一个主体，会掩盖服务账户之间过宽的权限。

## 4. 用不变量代替模糊的“要安全”

可测试的安全不变量示例：

1. 任何笔记读取都满足 `session.user_id == note.owner_id`，除非存在显式共享记录；
2. 状态改变请求必须同时有有效会话和匹配的 CSRF 证明；
3. SQL 结构由程序固定，外部字段只作为绑定值；
4. 导出文件始终创建在受限根目录中，worker 不接受任意绝对路径；
5. 日志不包含密码、完整 session token 或笔记正文；
6. 每条敏感成功/拒绝事件都有不可歧义的主体、对象和请求 ID；
7. 单个请求使用的内存、CPU、数据库行数和导出大小都有上限。

不变量一旦写清，测试、审计和事件响应都有共同语言。

## 5. 一个组合了多层控制的玩具模型

下面的代码只使用内存 SQLite 和固定玩具密钥，不启动网络服务：

```python
# integrated_notes.py
from dataclasses import dataclass
import hashlib
import hmac
import json
import sqlite3

AUDIT_KEY = b"local-demo-audit-key"
audit_log: list[tuple[bytes, str]] = []

db = sqlite3.connect(":memory:")
db.execute(
    "create table notes ("
    "id integer primary key, owner text not null, "
    "title text not null, body text not null)"
)

@dataclass(frozen=True)
class Session:
    user: str
    csrf_token: str

def audit(event: dict) -> None:
    encoded = json.dumps(
        event, sort_keys=True, separators=(",", ":")
    ).encode("utf-8")
    tag = hmac.new(AUDIT_KEY, encoded, hashlib.sha256).hexdigest()
    audit_log.append((encoded, tag))

def valid_audit(entry: tuple[bytes, str]) -> bool:
    encoded, supplied = entry
    expected = hmac.new(AUDIT_KEY, encoded, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, supplied)

def create_note(session: Session, csrf: str, title: str, body: str) -> int:
    if not hmac.compare_digest(session.csrf_token, csrf):
        raise PermissionError("invalid request intent")
    if not (1 <= len(title) <= 80 and len(body) <= 1000):
        raise ValueError("note outside size policy")

    cursor = db.execute(
        "insert into notes(owner, title, body) values (?, ?, ?)",
        (session.user, title, body),
    )
    db.commit()
    note_id = int(cursor.lastrowid)
    audit({"action": "create", "note": note_id, "user": session.user})
    return note_id

def read_note(session: Session, note_id: int) -> str:
    row = db.execute(
        "select owner, body from notes where id = ?",
        (note_id,),
    ).fetchone()

    if row is None or row[0] != session.user:
        audit({"action": "read-deny", "note": note_id,
               "user": session.user})
        raise PermissionError("note unavailable")

    audit({"action": "read", "note": note_id, "user": session.user})
    return str(row[1])

ada = Session("ada", "ada-csrf")
lin = Session("lin", "lin-csrf")

note = create_note(ada, "ada-csrf", "Plan", "local-only draft")
print("created:", note)
print("ada reads:", read_note(ada, note))

try:
    read_note(lin, note)
except PermissionError as error:
    print("lin reads: DENY -", error)

print("audit entries:", len(audit_log))
print("audit valid:", all(map(valid_audit, audit_log)))
```

预期输出：

```text
created: 1
ada reads: local-only draft
lin reads: DENY - note unavailable
audit entries: 3
audit valid: True
```

这段代码展示了几项组合原则：

- CSRF token 验证“状态改变意图”，session 用户标识“主体”；
- SQL 参数化维持语法与数据边界；
- 读取时针对具体对象检查 owner，而非只检查“已登录”；
- 拒绝响应不区分对象不存在还是属于别人，减少枚举差异；
- 审计事件不记录正文或 token，并用规范序列化后 HMAC 检测修改。

它仍不是生产服务：固定密钥、不持久化、没有真正认证、日志没有序号和重放/截断检测，也没有并发控制。综合分析应同时写明控制与剩余风险。

## 6. 为什么“日志有 HMAC”仍不完整

上面的每条记录独立带标签，能发现单条内容被修改，却不能发现：

- 整条记录被删除；
- 两条合法记录被重排；
- 旧日志被整体回滚；
- 持有 HMAC 密钥的 Web 服务伪造记录。

更强设计可加入单调序号、前一条摘要形成链、外部只追加存储、独立日志服务和定期签名检查点。若威胁模型包含 Web 服务被完全攻陷，审计密钥不应与服务进程共享同一权限域。

这体现“防御要独立”：攻击者突破一层后，不应自动获得关闭所有告警的能力。

## 7. 用攻击图连接局部缺陷

假设一个生产化版本存在以下配置：

1. 调试错误页会显示内部对象 ID；
2. 读取接口只检查登录，不检查 owner；
3. 日志记录完整 session token；
4. 日志平台对大量员工开放。

攻击图可能是：

```text
看到调试错误
  -> 得到有效对象 ID 模式
  -> 利用缺失对象级授权读取别人的笔记

或：

拥有日志读取权限
  -> 取得未过期 session token
  -> 以用户身份访问服务
  -> 缺少高风险操作重新认证
```

这里没有任何单一“高级密码破解”。真正风险来自信息泄漏、授权缺失和日志权限组合。修复应切断多条边：关闭生产调试、对象级授权、日志脱敏、缩小日志访问、短 token 生命周期和敏感操作重新认证。

## 8. STRIDE 是提问框架，不是结论生成器

可以沿每条数据流使用 STRIDE：

| 类别 | 问题 | 玩具系统例子 |
| --- | --- | --- |
| Spoofing | 能否冒充主体？ | session 是否可预测、证书是否验证 |
| Tampering | 能否修改数据？ | 请求、数据库行、队列消息、日志 |
| Repudiation | 能否否认操作？ | 审计是否完整、时间与主体是否可信 |
| Information Disclosure | 是否泄露？ | 越权读取、错误页、日志敏感字段 |
| Denial of Service | 能否耗尽资源？ | 超大正文、慢请求、无限导出 |
| Elevation of Privilege | 能否获得更高权限？ | worker 接受任意路径、管理员接口漏检 |

完成表格后还要验证可达性、现有控制和业务影响。列出一个术语不等于证明漏洞存在。

## 9. 信任边界中的数据转换

综合漏洞常出现在“验证发生在一种表示，使用发生在另一种表示”：

- 网关验证原始 URL，后端再次解码后得到不同路径；
- 前端把用户 ID 写入受信首部，后端也接受公网同名首部；
- 服务验证 JSON 字段，队列消费者按字符串命令解释；
- 文件扩展名通过检查，图像库却按文件魔数解析另一格式；
- 授权检查针对逻辑对象，缓存键却遗漏租户 ID。

对每次转换记录：输入编码、规范化规则、长度上限、失败语义和责任组件。最佳做法通常是只规范化一次，并在规范形式上验证与使用；如果跨组件传递，使用类型明确、可认证的结构化协议。

## 10. 导出 worker：典型混淆代理边界

后台 worker 通常比 Web 请求处理器拥有更多文件或存储权限。危险接口是：

```text
{ "source_path": 用户提供, "destination_path": 用户提供 }
```

更安全的任务消息应表达业务意图：

```text
{
  "request_id": "不可重复 ID",
  "actor_id": "ada",
  "note_id": 17,
  "format": "text",
  "expires_at": "短时效"
}
```

worker 根据 `note_id` 重新查询对象并验证授权，只在预配置导出目录创建由服务生成的文件名。消息应有来源认证、重放防护和版本字段；队列 ACL 只允许指定生产者与消费者。

不要把 Web 层已经做过授权当作永久事实。排队期间用户、对象或共享关系可能变化，必须明确执行时重新验证还是使用短期授权快照。

## 11. 二进制组件会放大输入边界

Web 服务常调用图像、压缩、文档或媒体解析库。这些库处理复杂二进制格式，可能存在内存错误。即使 Web 应用本身使用内存安全语言，FFI 或外部工具仍是独立攻击面。

纵深控制包括：

- 在进入解析器前限制类型、大小、维度和压缩比；
- 使用当前受支持版本并跟踪依赖漏洞；
- 解析器使用无网络、只读输入、空临时目录和低权限账户；
- 设置 CPU、内存、文件数和运行时间限制；
- 通过单向结果协议返回必要数据，不共享整个文件系统；
- 把崩溃视为可观察事件并自动隔离样本。

文件类型检查不能保证解析器无漏洞，沙箱也不能代替更新；二者切断不同攻击图边。

## 12. 根因控制、缓解控制、检测与恢复

| 类型 | 目的 | 例子 |
| --- | --- | --- |
| 根因控制 | 消除不变量失效 | 参数化 SQL、对象级授权、边界检查 |
| 缓解控制 | 限制成功后的能力 | 最小权限、沙箱、网络分段、只读挂载 |
| 检测控制 | 及时发现异常 | 拒绝率、跨租户访问告警、日志完整性 |
| 恢复控制 | 缩短影响时间 | token 撤销、密钥轮换、备份恢复、隔离主机 |

成熟方案通常四类都有。只有检测没有阻断会持续泄漏；只有预防没有日志会在控制失效时失明；只有备份没有恢复演练则不能证明恢复时间。

## 13. 负面测试与安全回归

围绕不变量写测试，而不是围绕已知攻击字符串：

```text
授权：任意两个不同测试用户，默认不能读取彼此对象
解析：任意规范化后越过根目录的路径都被拒绝
SQL：包含引号和 Unicode 的合法名字仍按一个值处理
会话：过期、撤销、缺失或错误受众的 token 均拒绝
资源：超出大小、并发和时间预算的请求可预测地终止
日志：敏感字段永不出现，删除或修改能被监控发现
队列：重复 request_id 不重复执行副作用
```

属性测试和模糊测试很适合验证边界不变量，但测试生成器也要有限额，避免把 CI 自己拖垮。修复漏洞后应保留最小回归测试，防止未来重构重新引入。

## 14. 事件响应：从时间线到影响边界

发现异常读取后，不应立刻只“封一个 IP”。建议流程：

1. **保存证据**：保护相关日志、版本、配置和时间同步信息；
2. **建立时间线**：首次与最后一次异常、主体、对象和请求 ID；
3. **控制影响**：撤销会话、隔离组件、关闭脆弱入口；
4. **确定根因**：授权遗漏、凭据泄漏还是代理配置错误；
5. **评估范围**：哪些用户、记录、密钥和备份可能受影响；
6. **根因修复**：不是只添加一个临时黑名单；
7. **恢复与监控**：安全上线、增加针对性告警；
8. **复盘**：更新威胁模型、测试、运行手册和培训。

轮换密钥前应理解依赖关系：贸然删除旧密钥可能让合法历史数据不可恢复。先制定兼容和迁移顺序，再轮换与撤销。

## 15. 风险排序

可以用以下维度，而不是只看漏洞名称：

- 可达性：公网、内网、登录后、本地？
- 前置条件：普通账户、管理员、物理接触？
- 可重复性：单次崩溃还是稳定批量访问？
- 权限与资产：进程能读哪些数据、调用哪些服务？
- 影响半径：单用户、单租户、全平台？
- 检测概率：是否有可靠日志和告警？
- 恢复代价：能否撤销、回滚、通知和重建？

一个“低技术复杂度”的对象级越权可能比难以到达的内存错误更紧急，因为它可稳定批量泄露生产数据。

## 16. 安全与伦理边界

- 只在自己拥有或明确授权的 localhost/实验环境验证系统假设；
- 不把故意脆弱的样例监听到 `0.0.0.0` 或部署到公网；
- 不采集真实用户 token、密码、私钥或正文作为教程数据；
- 漏洞验证应采用证明最小影响的方式，并遵循协调披露；
- 本章不提供任何站内挑战的输入、flag 或逐步解法。

## 17. 常见误区

- **“每个组件都安全，组合就安全。”** 边界假设可能不一致。
- **“上游验证过，下游可以信任原始字段。”** 转换、代理和队列可能改变语义。
- **“有加密就没有越权。”** 加密端点内仍要对象级授权。
- **“容器能修复解析漏洞。”** 它主要限制影响范围，根因仍需更新或修复。
- **“日志带哈希就不可删除。”** 独立记录标签不能自动发现截断、回滚和重排。
- **“只要封禁来源 IP 就完成响应。”** 凭据、代理和多来源访问会让 IP 不是稳定身份。
- **“修复一个已知字符串就足够。”** 应恢复一般不变量并做属性测试。
- **“安全控制越多越好。”** 未明确责任和失败模式的控制会相互冲突或制造绕过。

## 18. 纸面练习与答案

### 练习一：租户缓存

缓存键只使用 `document_id`，数据库授权使用 `(tenant_id, document_id)`。两个租户恰好都有 ID 42，会发生什么组合风险？

#### 答案

数据库路径可能正确隔离，但缓存会把一个租户的对象返回给另一个租户。缓存键必须包含所有影响授权和内容的上下文，并在权限变化时正确失效；命中缓存也必须遵守对象级授权。

### 练习二：日志秘密

Web 服务把完整 bearer token 写入集中日志，日志平台本身启用 TLS。风险是否已经解决？

#### 答案

没有。TLS 只保护传输，日志读者、导出、备份和平台管理员仍可能取得可用 token。应避免记录秘密，必要时只记录不可逆指纹或短前缀，并缩小访问与留存。

### 练习三：队列重放

导出消息有有效签名，但消费者收到同一消息两次并生成两份副作用。签名为什么没有阻止？

#### 答案

签名证明消息来源和完整性，不证明它是第一次出现。消费者需使用唯一请求 ID、序号或业务幂等键记录已处理状态，并把这些字段纳入签名。

### 练习四：沙箱价值

文档解析器在低权限、无网络、只读输入的独立进程中运行。发现内存破坏后是否可以不升级解析器？

#### 答案

不可以。沙箱降低成功后的能力，是缓解而非根因修复；漏洞仍可能导致拒绝服务、读进程内数据或利用沙箱配置缺陷。应升级或修复，同时保留隔离作为纵深防御。

### 练习五：授权时间

用户创建分享链接后立即撤销。链接 token 本身有效期一天，服务只验证签名和到期时间。哪里缺失？

#### 答案

缺少撤销状态或足够短时效。若业务要求立即撤销，验证时需查询服务端撤销/版本状态，或让 token 引用可失效的 capability 记录；签名只能证明 token 未被改动。

### 练习六：控制分类

参数化 SQL、数据库只读账户、异常查询告警和每日备份分别属于哪类控制？

#### 答案

参数化 SQL 是根因控制；只读账户是限制影响的缓解控制；异常查询告警是检测控制；每日备份是恢复控制。实际分类可能重叠，但这样区分有助于发现防线是否完整。

## 小结

综合安全不是把漏洞名称相加，而是沿数据流验证每个组件的假设。先画资产、主体、边界和不变量，再构建攻击图；用根因、缓解、检测和恢复四类控制切断不同路径。最终标准不是“用了多少安全产品”，而是系统在一层失败后是否仍能限制、发现并恢复。
