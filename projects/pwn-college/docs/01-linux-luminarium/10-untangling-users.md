# 10 · 用户与身份

> 对应官方模块：[Untangling Users](https://pwn.college/linux-luminarium/users/)

## 学习目标

- 区分用户名、UID、主组和附加组。
- 理解真实身份与有效身份在权限判定中的角色。
- 用 `id` 和 `stat` 观察身份，不依赖管理员权限。

## 内核主要使用数字身份

用户名是便于人类使用的映射，内核权限判定主要依据数字 UID 和 GID。一个用户有主组，也可属于多个附加组。文件保存所有者 UID 和组 GID；显示工具再通过账户数据库把数字转换成名字。

进程还可能有真实 UID、有效 UID 等多个身份。普通程序通常相同；涉及 set-user-ID 或受控提权时，有效 UID 决定多数访问检查。`sudo`、`su`、登录和 setuid 程序是不同机制，不能只用“切换用户”概括。

## 安全示例：比较进程与文件身份

```bash
identity_dir=$(mktemp -d)
printf 'owned locally\n' > "$identity_dir/note.txt"
id
stat -c 'owner_uid=%u owner_gid=%g owner_name=%U group_name=%G' \
  "$identity_dir/note.txt"
rm -r -- "$identity_dir"
```

预期输出形态：

```text
uid=1000(alice) gid=1000(alice) groups=1000(alice),...
owner_uid=1000 owner_gid=1000 owner_name=alice group_name=alice
```

`mktemp` 由当前进程创建目录，文件通常继承创建进程的有效 UID，组归属受父目录和系统规则影响。具体数字、名字与附加组会不同。

只查看数字可减少名字映射造成的混淆：

```bash
id -u
id -g
id -G
```

三者依次显示有效 UID、有效 GID 和所有组 ID。

## 账户记录与凭据记录分离

<code>/etc/passwd</code> 历史上存过口令哈希，如今通常只保存公开的账户元数据：用户名、UID、GID、注释、HOME 和登录 shell。可以只查询当前账号：

~~~bash
getent passwd "$USER"
~~~

典型字段形态：

~~~text
alice:x:1000:1000:Alice:/path/to/alice:/bin/bash
~~~

第二字段的 <code>x</code> 表示密码验证数据通常在受保护的 shadow 数据库中。普通用户不应能读取其他账号的密码哈希；哈希一旦泄漏，攻击者可离线猜测，不再受在线登录速率限制。

密码存储不是普通快速哈希：

~~~text
stored = password_KDF(password, unique_salt, cost_parameters)
~~~

salt 阻止相同密码直接产生相同记录和预计算表复用；成本参数让每次猜测更贵。系统应使用发行版维护的现代密码 KDF、强口令/MFA、速率限制和泄漏后的凭据轮换。口令审计只可对自己拥有或明确授权的数据进行，本教程不提供破解流程。

## 真实、有效与保存身份

进程常见身份包括：

- real UID：谁启动了进程；
- effective UID：多数权限检查使用谁；
- saved set-user-ID：受控地在身份间切换时可恢复的值；
- filesystem UID（Linux 特有）：部分文件检查使用；
- real/effective/saved GID 与附加组。

普通程序中它们常相同，setuid 程序中可能不同。Shell 的 <code>id -ru</code> 与 <code>id -u</code> 可分别观察真实/有效 UID；是否支持选项以本机手册为准。

安全程序不能只在启动时检查一次 real UID，然后永久信任输入；每个高权限操作都应验证调用者、对象和动作，并尽快降权。

## su、sudo 与登录不是同一机制

<code>su</code> 通常认证目标账号或由 root 切换身份，并可启动新 shell；<code>su - user</code> 还建立接近登录会话的 HOME、工作目录和环境。它适合身份切换，不提供细粒度“只允许某命令”的策略。

<code>sudo</code> 根据 sudoers 策略判断当前主体是否可代表另一身份执行特定命令，并能记录审计信息。安全策略应明确：

- 允许的命令及精确参数范围；
- 目标用户；
- 可保留的环境变量；
- 工作目录与 PATH；
- 是否允许 shell、编辑器、插件或任意文件写；
- 日志、超时与撤销。

“只允许一个工具”也可能间接等于 shell 权限：许多编辑器、解释器、归档器和包管理器能运行子命令或加载插件。策略审计必须理解程序全部能力。

在自己的账户上，<code>sudo -l</code> 可列出当前策略；不要用不断试错的方式探测他人系统。sudoers 应通过 <code>visudo</code> 进行语法验证，配置变更还需同行复核和回滚入口。

## 组成员关系与会话缓存

管理员把用户加入附加组后，现有进程通常不会自动获得新组列表；登录会话在创建时取得凭据。重新登录或由受控工具建立新会话后才会反映变化。

组权限适合共享资源，但组越大、用途越混杂，授权越难审计。对敏感资源使用专用最小组，定期审查成员，并避免把“能读日志”的组同时赋予可修改服务代码的能力。

## 身份切换时的环境与文件描述符

即使 UID 已改变，进程仍可能保留：

- 切换前打开的高权限文件描述符；
- 当前工作目录；
- 环境变量和 PATH；
- 共享内存与 socket；
- capability；
- ptrace/debug 状态；
- 设置了危险权限的输出文件。

因此可靠降权需要清理组、capability、环境和 fd，并在打开高权限资源后把能力封装成窄接口，而不是只调用一次 setuid。

## 安全视角

“知道用户名”不等于获得授权，应用还需验证会话和操作范围。共享系统中，重复使用 UID、网络目录服务延迟或容器内外映射也会造成名称与数字身份错觉。审计记录最好同时保留稳定标识和足够上下文。

## 常见误区

- **认为用户名直接写进文件元数据。** 文件系统通常保存数字 UID/GID。
- **认为主组是唯一组。** 附加组也可授予访问权限。
- **把 `sudo` 与 `su` 当同义词。** 前者按策略执行命令，后者通常启动另一身份的会话。
- **为学习命令默认加 `sudo`。** 会扩大错误影响，也改变要观察的权限模型。

## 纸面练习

文件记录所有者 UID 为 `1001`。账户数据库后来把 UID 1001 映射到另一个名字，`ls -l` 可能显示什么？文件的数字所有权是否改变？

### 答案

`ls -l` 可能显示新的用户名，因为显示时重新查询映射；文件元数据中的数字 UID 仍是 1001，并未因名字变化而改变。这说明名字是解释层，数字标识才是持久元数据。

## 小结

Linux 身份模型以 UID、GID 和进程有效身份为基础，用户名只是映射。权限分析应同时观察进程身份、文件数字所有权和组成员关系。
