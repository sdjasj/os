# 16 · 危险的破坏性操作与恢复

> 对应官方模块：[Daring Destruction](https://pwn.college/linux-luminarium/destruction/)

## 学习目标

- 从进程、磁盘块、inode 和目录项理解资源破坏；
- 解释进程炸弹和磁盘耗尽为何能让系统失去可用性；
- 理解递归删除的范围、打开文件的残留行为和恢复限制；
- 建立预防、遏制、恢复和复盘四阶段思维。

本章**不会**给出可执行的 fork bomb 或根目录删除命令。资源耗尽只能在专用、可回滚、带硬限制的虚拟机中研究；阅读正文已经足以理解机制。

## 1. 进程炸弹：指数增长耗尽的是什么

每个进程都消耗 PID、内核任务结构、页表、文件描述符、调度时间和内存。若每个进程不断创建多个后代，数量可近似指数增长：

~~~text
第 0 轮：1
第 1 轮：2
第 2 轮：4
第 3 轮：8
...
第 n 轮：2^n
~~~

下面只做数学模拟，不创建子进程：

~~~python
processes = 1
for generation in range(8):
    print(f"generation={generation} processes={processes}")
    processes *= 2
~~~

预期最后两行：

~~~text
generation=6 processes=64
generation=7 processes=128
~~~

真实系统达到限制前，交互 shell、SSH、监控和管理员救援命令都可能难以获得调度或创建新进程，所以“再开一个终端杀掉它”未必可行。

### 防御不是寻找最快 kill

应在进程创建之前设置硬边界：

- systemd 单元的 TasksMax；
- cgroup v2 的 pids.max；
- PAM/limits 的进程上限；
- 容器运行时的 PID 限制；
- 服务账户隔离；
- 外部 watchdog 和管理通道。

查看当前 shell 的用户进程软限制：

~~~bash
ulimit -Su
~~~

输出可能是数字或 unlimited。它只描述当前继承上下文的一层限制；cgroup、系统全局 PID 空间和服务管理器还可能有其他上限。不要为了“试试看”把限制调高后运行自复制代码。

## 2. 磁盘空间耗尽不只有一种

文件系统可能耗尽：

1. **数据块**：大文件占满容量；
2. **inode**：海量小文件用完对象元数据；
3. **配额**：某用户/项目达到 quota；
4. **日志保留空间**：日志无限增长；
5. **已删除但仍打开的文件**：名字消失，块尚未释放；
6. **快照/COW 空间**：删除当前文件不一定立刻释放底层块。

常用只读观察：

~~~bash
df -h .
df -i .
du -sh .
~~~

<code>df</code> 从文件系统角度看整体块/ inode 使用；<code>du</code> 遍历当前可见目录项。二者不一致可能来自打开但已删除文件、稀疏文件、权限、快照或保留块。

### 安全的 1 MiB 示例

以下只在新临时目录创建一个小文件：

~~~bash
space_dir=$(mktemp -d)
head -c 1048576 /dev/zero > "$space_dir/one-mebibyte.bin"
truncate -s 1G "$space_dir/sparse-demo"
ls -lh "$space_dir/one-mebibyte.bin"
ls -lh "$space_dir/sparse-demo"
du -h "$space_dir/one-mebibyte.bin" "$space_dir/sparse-demo"
rm -r -- "$space_dir"
~~~

预期第一个文件的逻辑大小约 1.0M；稀疏示例的逻辑大小为 1.0G，却几乎不分配数据块。<code>du</code> 显示的实际分配量因文件系统而略有差异。这说明只看 <code>ls -l</code> 的逻辑大小也可能误判占用；示例中的两个对象都位于刚创建的专用临时目录，并在末尾一起清理。

### 服务端防护

- 按用户、租户和请求设置配额；
- 限制上传的声明长度与实际解压后长度；
- 对日志做轮转、速率限制和总容量上限；
- 给 /tmp、缓存、上传和审计日志分开分区/配额；
- 监控 blocks、inodes、增长率与删除未释放对象；
- 保留管理员和日志写入所需的应急空间；
- 压缩包解析防止高膨胀比数据。

“磁盘还有 5%”不一定安全：剩余可能是仅 root 可用保留块，inode 也可能先用完。

## 3. rm 的底层语义

普通文件名是目录中指向 inode 的目录项。删除通常调用 unlink 类操作移除名字。数据何时释放取决于：

~~~text
链接计数 == 0
并且
没有进程仍打开该对象
~~~

因此日志名字被删后，持有 fd 的进程仍可继续写，<code>df</code> 的空间也可能不下降。目录的删除权主要由父目录写/执行权限决定，而非目标文件自身的写位。

## 4. 递归删除为何极易放大错误

递归删除会遍历整个目录树。危险来源：

- 变量为空或指向错误位置；
- 未引用变量发生分词和通配；
- 相对路径基于意外工作目录；
- 绑定挂载、网络挂载或共享目录扩大范围；
- 脚本以高于必要的权限运行；
- <code>-f</code> 隐藏提示和部分诊断；
- 备份目录也位于同一被删除树。

GNU rm 对根目录通常有 preserve-root 保护，但实现和选项不同，且它不能保护“几乎等同于根”的错误子目录。不能把保护开关当授权模型。

## 5. 安全示例：精确预览后删除

~~~bash
delete_dir=$(mktemp -d)
printf 'keep\n' > "$delete_dir/keep.txt"
printf 'remove\n' > "$delete_dir/remove.txt"

find "$delete_dir" -maxdepth 1 -type f -printf '%f\n' | LC_ALL=C sort
rm -- "$delete_dir/remove.txt"
test ! -e "$delete_dir/remove.txt" && printf 'remove.txt deleted\n'
test -e "$delete_dir/keep.txt" && printf 'keep.txt preserved\n'

rm -r -- "$delete_dir"
~~~

预期：

~~~text
keep.txt
remove.txt
remove.txt deleted
keep.txt preserved
~~~

示例只删除由本段创建的专用目录。生产清理脚本应把解析、预览、授权与删除拆开：

1. 将目标解析成规范的预期路径；
2. 拒绝空值、<code>/</code>、HOME、工作区根和过宽目标；
3. 验证目标位于允许根、文件系统和挂载边界；
4. 以只读方式输出准确对象、总数与总大小；
5. 尽可能先移入同文件系统隔离区，保留恢复窗口；
6. 对精确路径使用 <code>--</code>；
7. 删除后检查退出码、剩余对象和监控。

<code>rm -i</code> 可辅助人工操作，但自动任务没有交互终端，它也不能修复错误目标。

## 6. “删除之后程序还在跑”不代表系统完好

若根文件系统的大量名字被删除：

- 已运行进程的代码页可能仍在内存中；
- 已打开文件描述符仍引用对象；
- shell 内建可能暂时可用；
- 新命令、共享库、配置和名称解析会陆续失败；
- 服务重启后无法恢复；
- 包管理数据库和安全策略可能已损坏。

这种半存活状态不可信，不应继续处理生产事务或输入高价值凭据。

## 7. 事故遏制与恢复

### 7.1 立即行动

1. 停止导致增长/删除的任务；
2. 隔离网络和自动化控制面，防止继续传播；
3. 避免大量新写覆盖潜在可恢复块；
4. 记录时间、命令来源、进程、挂载和日志；
5. 通知系统所有者与事件响应人员；
6. 不在不可信系统上输入新的管理员凭据。

若系统已无法 fork，新进程命令可能不可用，应依赖预先准备的带外管理、cgroup 控制或宿主/虚拟化管理面。

### 7.2 选择恢复方式

优先级通常是：

1. 从可信、测试过的备份恢复；
2. 从基础设施代码和不可变镜像重建；
3. 在救援介质中只读挂载并提取必需业务数据；
4. 文件系统取证/恢复工具只作为有限补救，不能保证完整；
5. 重建后轮换在事故期间可能暴露的凭据并验证数据一致性。

恢复“几个文件”不等于恢复系统完整性。包文件、权限、扩展属性、capability、SELinux 标签、引导文件和审计链都可能受损。生产系统通常应重建，而不是手工拼补到“看起来能启动”。

### 7.3 为什么备份也会失败

- 备份与源在同一目录树或同一账号权限下；
- 快照被同一删除流程清理；
- 从未做恢复演练；
- 备份静默损坏或缺少密钥；
- 恢复点已包含恶意修改；
- 只备份数据，未记录配置、权限和依赖。

3-2-1 原则（多份副本、不同介质、至少一份异地/离线）是起点，真正证明来自定期恢复测试和明确的 RPO/RTO。

## 8. 如何预防破坏性自动化

- 默认 dry-run，输出机器可审计清单；
- 删除 API 接受对象 ID，而非任意路径或 shell 片段；
- 使用最小权限专用账户；
- 对目录、文件数、总字节设上限；
- 高风险操作需要二人批准或延时撤销；
- 备份凭据与生产删除凭据隔离；
- cgroup 限制进程、内存与 I/O；
- 日志进入独立、追加受控的系统；
- 用临时 fixture 做回归测试，不在真实数据副本试跑。

## 常见误区

- **进程炸弹只是 CPU 满。** PID、内存和调度资源也会耗尽。
- **df 有空间就能创建文件。** inode、quota 或保留块可能先成为限制。
- **rm 后 df 必然下降。** 打开 fd、硬链接和快照会延迟回收。
- **只读文件不能删除。** 删除主要检查父目录权限。
- **根目录保护能兜住所有错误路径。** 子目录和其他实现仍可能造成灾难。
- **数据恢复工具等于备份。** 覆盖、SSD TRIM、加密和元数据丢失都会使恢复失败。
- **只要服务还在跑就无需重建。** 内存中的残留执行不能证明磁盘系统完整。

## 纸面练习

### 题目一

一个服务不能再创建文件，但 <code>df -h</code> 显示仍有很多容量。给出两个不同方向的原因。

### 答案

可能 inode 已耗尽（检查 <code>df -i</code>），也可能该用户/项目达到 quota；还可能目录权限、只读挂载或文件描述符上限导致同样症状。错误码和相应只读指标能区分。

### 题目二

一个 5 GB 日志名字已删除，空间没有释放。为什么？

### 答案

某进程可能仍持有打开文件描述符，链接计数虽然为零，内核对象仍有引用。应在授权环境识别持有者，让服务有序重新打开日志或重启；不要盲目强杀未知进程。

### 题目三

为什么事故后从包管理器“重装缺失文件”通常不足以证明恢复完成？

### 答案

包外配置、权限、扩展属性、数据库状态、密钥、日志与运行时持久化可能仍不一致或被篡改。可信重建加数据恢复、完整性验证和凭据轮换提供更强保证。

## 小结

破坏性操作的共同模式是失控增长或失控范围：进程数呈指数扩张，数据/ inode 持续消耗，递归删除把一个路径错误放大成整棵树。安全工程应在事前设置硬上限和可恢复备份，事中依靠带外控制遏制，事后从可信介质重建并验证，而不是赌一条救援命令。
